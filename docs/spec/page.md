# KDS Page Management

Page allocation, the buffer pool, the file layout, and the I/O path. Consistent with `docs/rules/rules.md`, `docs/spec/wal.md`, `docs/spec/waystone-concpets.md`, `docs/spec/sched.md`; frame replacement is `docs/spec/eviction.md`'s.

## 0. Decision Record

| # | Decision | Choice |
|---|---|---|
| S1 | Page layout abstraction | **Common 32-byte page header** at offset 0 for all header-bearing page classes |
| S2 | Store interface | **`PageRef`** — RAII pinned-page handle; the `PageStore` contract hands out no raw span |
| S5 | Disk layout | **Single data file**; `offset = page_id × 8192`; extent-based growth |
| S7 | Multi-core page access | **One buffer pool for the instance** (§6); every core reads and writes every page, and no core owns one |

| S11 | Paging mechanism | **Explicit buffer pool. mmap is rejected for data and WAL** (§15) |
| S12 | Page → relation resolution | **`owner_oid` in the common header** (§2a) — the page is the mapping, no auxiliary structure |
| S3/S4/S6/S8/S10 | Eviction, dirty tracking, space management, frame memory, observability | §§5, 7-9 and 11 state what is built |

## 1. Page Classes

Two page classes exist, and the distinction is load-bearing:

- **Headered pages** — heap, B+ tree, undo, catalog, superblock, var-heap, Waystone entry pages: carry the common header (§2), are checksummed, carry `page_lsn`, and participate in WAL and recovery. The free-map and headerless-map pages carry the header and its checksum too, but they are the store's own regions, not frames: written with no record, their `page_lsn` always 0, repaired at recovery by the allocation floor (§5).
- **Headerless pages** — **the Waystone directory's interior pages only.** Their tiling is an exact power of two (2048 × 4 B directory children = 8192 exactly), so a header would steal a slot and force division-based addressing, violating the shift/mask derivations in `docs/spec/waystone-concpets.md` §5–6. The exemption is safe *because of* Waystone's advisory contract: a damaged interior page leads a walk to a page that is not the instance's waystone, which the headered target's own check turns into a miss — always correct. A page is marked headerless durably, in a bitmap page of the free map's shape (`kHeaderlessMap`, §5), because the store is opened before there is a catalog to ask and a verify on first touch would otherwise reject the page. The rejected alternative — halving fanout to make header room — would double the directory's space cost for integrity it does not need.
- Consequences: WAL `FULL_PAGE_IMAGE` and checksum verification apply to headered pages only; recovery never replays onto headerless pages; the buffer pool records the class per frame so instrumentation can enforce both this rule and Waystone invariant 8.

## 2. Common Page Header

Fixed 32 bytes at offset 0 of every headered page. Type-specific content begins at offset 32.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | `page_type` | frozen append-only enum: `heap`, `btree_internal`, `btree_leaf`, `undo`, `catalog`, `superblock`, `freemap`, … (`0` = invalid/unformatted) |
| 1 | 1 | `format_version` | per-type layout version; bumps are format events |
| 2 | 2 | `flags` | unused: written 0, read by nothing (§2b) |
| 4 | 4 | `checksum` | CRC32C over the full 8 KiB with this field zeroed (§10) |
| 8 | 8 | `page_lsn` | LSN of the last WAL record applied (wal.md §9); 0 = never logged |
| 16 | 8 | `relayout_epoch` | bumped when tuples on the page move (`docs/spec/physical-optimizer.md` R4, `heap-and-tuple.md` §3.1a); 0 = never relayouted |
| 24 | 8 | `owner_oid` | oid of the owning object, 0 = unattributed (§2a) |

Codec rules as everywhere (rules.md §2/§5): field-wise memcpy helpers, mirror struct + `offsetof` `static_assert`s, fixed-width LE, no bitfields. A shared `page_header` codec module owns this layout; type-specific codecs compose it and must not re-implement it.

**A reserved word that gains a meaning under which 0 is the correct default is not a format event.** Every page ever written carries 0 there and reads correctly; no `format_version` bump, no backfill. Offsets 2, 16 and 24 were all assigned that way.

## 2a. Page Ownership — `owner_oid`

The engine's other mappings run forward only (relation → descriptor page, var-heap root, index roots); `owner_oid` is the one thing that resolves a page back to its owner. It is the catalog `Oid` (u64) of the owning object, at offset 24 of the common header. No map pages, no in-memory reverse index, no free-list extension: the page itself is the mapping, and the reverse query is a scan (below). A consumer that needs the reverse direction hot is a new proposal, not this one.

- **Stamping:** written once by `FormatPage` at page initialization and **immutable until the page is re-initialized** — the `min_key` discipline. Reuse re-stamps through re-initialization, never in place: a page id a dropped relation's reclaim freed (§5) is a new page when it is handed out again, formatted with its new owner's oid. Written under the initializer's exclusive access, read under an ordinary shared pin; inside the checksummed span like every header field, so flush/verify need nothing new. Every page-creating entry point of a relation's structures takes the owner - heap `CreateEmpty`/`CreateEmptyAs`, var-heap `FormatPage`/`CreateChain`/`ChainAppend`, btree `FormatRoot`/`BtreeInsert`, both index `CreateEmpty`s, `index::FormatRoot`/`IndexInsert` - though the common `FormatPage` and the var-heap's `FormatPage` default it to 0 for system callers, so a relation path that forgot it would stamp 0 rather than fail to compile; rebuilds (`SplitLeafAndInsert`, `DivideInternalNode`) re-read the page's own stamp; `CREATE TABLE` and `CREATE INDEX` issue the oid *before* the first page (the index oid via `IndexDef::index_oid`), so roots and backfill-split pages stamp from birth; an FPI-created page carries the stamp inside the image.
- **Per-class semantics:** heap pages and the relation's `kVarHeap` chain carry the relation's oid. System classes — undo, catalog, superblock, freemap — carry 0; `page_type` already identifies them. The catalog's fixed roots carry what bootstrap gave them - 0 for the fixed core, the relation's well-known oid for the three declaration relations, which `ChainInsert` grows - and **every page a catalog chain grows onto past its root carries its catalog relation's oid** since superblock 31 (`kCatalogRoots`, `crosscore.md` CC12 CR3; D5 of the catalog page ceiling, under the operator's ruling of 2026-10-18, "$!recommended"): `sys.access_stats`' mount discard tells its chain's pages by it, and reclaim, which frees only a dropped user relation's pages, passes it by. Headerless pages are exempt by class (§1). B+ tree pages carry their **immediate owner**: clustered-tree pages the relation's oid — the clustered tree *is* the relation's storage — and secondary-index pages the index's own oid. One uniform rule: the object whose structure the page is. Relations and indexes do **not** share an oid space: an index oid is a `sys.indexes` row id (`AllocateRowId(kSysIndexesTable)`), a separate issue-once sequence, and `DropIndex` *retires* the row rather than tombstoning it. Owner resolution is therefore discriminated by `page_type`, which the header carries next to the oid: `kIndexLeaf`/`kIndexInternal` owners resolve against `sys.indexes` (orphan = no row carries the id, sound because row ids are never reissued), every other class against `sys.objects` (orphan = the `kTypeDroppedTable` tombstone). A relation-level query over index pages takes the catalog's index → relation edge.
- **WAL:** redo reproduces the stamp. `PAGE_INIT`'s payload is 24 bytes — `owner_oid` at offset 16, four reserved bytes at 12 keeping the codec's mirror struct naturally aligned (rules.md §2), the 12-byte prefix unchanged — and the decoder accepts the 12-byte legacy form as owner 0, **discriminated by a length *floor*, never by equality**: `DecodeRecord` hands a payload codec the record's 8-byte-aligned tail rather than the exact payload, so a 12-byte payload arrives as 16 bytes of payload-plus-zero-padding and a 24-byte one as exactly 24, and an equality test would refuse every legacy record read through the envelope. `docs/spec/wal.md` §5.2 carries the payload.

What it answers, and at what cost:

1. **Owner of page P:** read the header. O(1) with the page in hand.
2. **Is P orphaned:** its `owner_oid` resolves to a `kTypeDroppedTable` tombstone row. The tombstone's retype-never-retire rule (`docs/spec/drop-table.md`) and the never-reissued oid floor make the test ABA-proof **for a tombstoned oid** — a stamped oid can never come to mean a *different* live relation. A **burned** oid - a failed or rolled-back `CREATE TABLE`'s, which leaves no row - can be issued again after a restart, so its pages would be attributed to the next relation that takes it; that is why the reclaim walks from a tombstone's roots rather than reclaiming by census (`instructions/v3.0.0/workorder-bf-drop-table-page-reclaim.md` BF-Q5). An **unattributed page is never reclaimable**.
3. **Pages of relation X:** a sequential full-file header scan, O(all pages). Deliberately unindexed: the reverse query is rare and sequential, and the single-file arithmetic layout (§4) makes the scan one forward read of the file.

What it does not give:

- **No free/allocated state.** The free map (§5) owns "is this page free"; `owner_oid` says who a formatted page belongs to, never whether it may be allocated. Neither substitutes for the other.
- **Nothing in recovery.** Redo is page-id-physical, and recovery undo's mount refusal on an identity mismatch stands; neither reads this field.

**oid 0 is unambiguous as "unattributed."** It is *not* free catalog-wide (`kNamespaceSys = 0` is a live persisted oid) but it names an object that owns no pages, and no page-owning object can carry it: system relations sit at oid 115+, user objects from `kUserOidStart` = 4000. Pages written before the field existed carry 0 permanently and are never reclaimable.

**Its consumers:** the anchor's identity check when a relation's access is filled (`catalog.cpp`); a dropped relation's reclaim, which frees a page only when it carries the oid its parent says it should (`drop-table.md` DT1, BF-R3); the one verifier of a remembered location, which misses on a page another relation owns (`exec/tuple_verify.hpp`, BF-R10); and a statement's bind, which checks that a relation's anchor and first page still carry its oid. None of them is a census: there is no scan of the file.

## 2b. The common `flags` word

The 2-byte `flags` word at offset 2 is written 0 by every format and
**read by nothing**. It held a stream stamp, `core_id + 1` of the core
that last wrote the page; BP-H5 stopped writing it, so a page last written
before that carries a stale nonzero value and nothing acts on it. It stays
in the header because removing it is a format event; a later stage that
wants the two bytes takes them with a version bump.

## 3. `PageRef` — the Pinned-Page Handle

Raw spans are unsafe the moment eviction exists; the interface fixes it structurally:

- `PageRef` is a move-only RAII guard: construction pins the frame, destruction unpins. It exposes `page_id()`, `bytes()` (fixed-extent span, valid exactly as long as the ref lives), `MarkDirty()`, and `page_class()`.
- `PageStore` contract: `CreateAt(page_id) → StatusOr<PageRef>`, `CreateNew() → StatusOr<pair<PageId, PageRef>>`, `Get(page_id) → StatusOr<PageRef>`, `GetForRead(page_id) → StatusOr<PageRef>`. Unbalanced unpins are impossible by construction; `Frame` is an implementation detail no caller names.
- **A page can be pinned with no latch** (`PageStore::PinUnlatched`, `UnlatchedPin`, `PinMode::kUnlatched`). The handle keeps the frame resident and nothing more: a later `Get` of the page is a hit that neither the pool nor the device can refuse, and the holder has taken no place in any latch order. It exists for a write that must not fail on a fault it reaches after it has written: a B+ tree split that grows a level pins the relation's anchor before it writes anything (`heap-and-tuple.md` §5). An unlatched pin counts against the pool like any pin (EV4) and is given back as soon as the latched access it prepared has been taken.
- Pin discipline: holding a `PageRef` across a task suspension point is legal but metered (§11) — suspended portals and long scans are the known holders.
- A stamp records the frame's `recLSN` (the lowest LSN stamped since the last clean, or since the copy of a clean the dirty generation skipped) — the hook feeding the checkpoint dirty-page table (§8).

## 4. Single-File Store

- One data file per KDS instance. Mapping is pure arithmetic: `file_offset = page_id × 8192`. No file/segment indirection, no mapping table.
- Capacity: `page_id` is u32 with `2³¹` target pages ⇒ 16 TiB file ceiling (design constant, asserted).
- Growth is extent-based and crash-safe (§14); sparse regions are permitted.
- Well-known pages (superblock, free-map and headerless-map pages, catalog bootstrap) keep their fixed low ids; the superblock at page 0 anchors the WAL anchor table (wal.md §14-3). It holds no free-map root: the map's pages are found by arithmetic (§5).
- Segmentation across files is a non-goal; the contract is one file and one arithmetic mapping.

## 5. SpaceManager

Owns "which page_ids exist / are free" inside the disk-backed store, behind the unchanged `PageStore` seam (`DevicePageStore`, `include/kds/storage/free_map.hpp`):

- **Free map:** bitmap pages (`page_type = freemap`), one bit per page id, 1 = allocated, addressed by explicit shift/mask over the page body. One headered free-map page covers `(8192 − 32) × 8 = 65,280` pages (~510 MiB of data file). The map is **region-based**: region N covers ids `[N × 65,280, (N + 1) × 65,280)`, and its two bitmaps — the free map and the headerless map (§1) — are the first two ids inside it, so locating the bitmap for a page_id is arithmetic, not lookup, up to the 2^31-page ceiling. Region 0's pair is pages 1 and 2, beside the superblock.
- **Extent = 64 pages** (`kDefaultExtentPages`) — the unit of file growth. Every core allocates from the one map, under its latch (below).
- **The free map is not logged.** `ALLOC` and `FREE` are reserved in the WAL record enum and emitted by nothing; recovery repairs the map by raising the allocation floor (`RaiseAllocationFloor`). A crash between extent growth and first use is benign (§14).
- **A page is freed by one primitive**, `PageStore::FreePage` (`instructions/v3.0.0/workorder-bf-drop-table-page-reclaim.md` BF-R5), and its one caller is a dropped relation's reclaim (`drop-table.md` DT1). In one hold of the frame table then the map, it discards the page's frame - dirty or not - and clears its bit. It defers while the frame is pinned, latched or claimed by a writeback, or while a fault or a `CreateAt` of the id is in flight. It refuses `Corruption` for an id in the system range, a map id, a headerless id and a Bound Cabin page. The system range is the fixed ids below `kFirstUserPageId` only: a page a catalog chain grew onto is above it, and **what keeps a catalog page from being freed is the caller's check**, not this refusal - a reclaim (`server/page_reclaim.cpp`) frees only a page whose owner is the oid of the dropped relation or of one of its indexes and whose kind is one the walk expects there - anchor, btree, index or var-heap - so a catalog page, `kHeap` with a catalog oid, is skipped, a re-drive meeting a freed id a catalog chain has since taken included; a failed index build's free (`exec/index_ddl.cpp`) takes only `kIndexLeaf`/`kIndexInternal` pages of the index's oid and refuses `Corruption` at any other. No refusal was added for it (D6 of the catalog page ceiling, under the operator's ruling of 2026-10-18, "$!recommended"); `CatalogPageCeilingTest`'s `AReclaimNeverFreesACatalogPageAndAFreedIdMayBecomeOne` and `AReclaimRedrivenAfterACrashPassesACatalogPageOnAnIdItFreed` pin the skip. The caller owns the precondition: no record that names the page can be replayed again (BF-R4), and no reader can reach it. **What this makes true:** no clear bit has a resident frame.
- **A freed id comes back through a free list** (BF-R6), in memory and under the map latch. `CreateNew` pops it ahead of the cursor, skipping an id that is resident or has a fault in flight. The cursor passes over a listed id, `CreateAt` takes one off, and `CreateNewHeaderless` never takes one. The cursor and the recovery floor never move for it: a clear bit below the floor can be an id the log names, while the list holds only ids a reclaim checked and gated. A crash forgets the list. After a clean restart the cursor finds the cleared bits again; after a crash the floor hides those below it for that run. A headerless create that lands on a freed id after a restart writes zeros over the dead image, durably, before its bit is set.
- A page the map calls allocated that the device holds as all zeros reads `NotFound`, not `Corruption` (§10).
- **The map has a latch of its own** (AM-S3), `map_latch_`, armed on the same word as the frame table's. It guards `map_regions_` and every region in it — the two bitmaps, the lazily installed headerless pointer (FM6), and the dirty flag. Three rules:
  - **Every public reader takes it** - `IsAllocated` (on the fault path, the writeback path and the WAL gate), `IsHeaderless`, `map_residency` - since an unlatched read races region creation's `insert`. Internal callers already holding it use the `...Locked` bodies.
  - **Device work never runs under it** (AM-S2). Region creation resolves the file grow and the device read *outside* the hold and publishes with `try_emplace` *under* it, so two cores creating one region both succeed and the loser returns the winner's bitmap rather than replacing a map the winner has already allocated out of. `FlushMaps` copies each dirty region's bytes under the hold, clears its flag there, and writes after — clearing at the copy rather than after the write is what makes a concurrent allocation re-dirty the region instead of losing its bit.
  - **The order is the frame table's latch and then this one, never the reverse.** Both halves are debug-asserted rather than stated: a public reader aborts if reached from inside the map hold, and the frame table's one structural mutation aborts if reached while holding the map.
- **Why a second latch and not the frame table's.** The two are *nested*: `FetchPinned`'s hit path holds the frame table across `Resolve`, and `Resolve` begins with `IsAllocated`; one latch would be a second acquisition on one thread, which `base/latch.hpp` says is a hang. Order: *structure → allocation, allocation the inner leaf* (AM-S2's ruling).
- **A claimed id is in use before its frame exists.** `CreateAt` sets the map bit under the hold and inserts the frame after releasing it, so between the two the page is allocated, not resident, and its device bytes are zeros - the signature the claim path reads as a *torn creation* and re-claims. The store therefore keeps a set of ids claimed and not yet resident (the fault path's in-flight shape), and the claim path refuses one in it, so a second caller is never handed the same page (AM-S3).
- **Who writes the map back when one store serves every core** is answered by the hold rather than by a rule: N checkpointers each call `FlushMaps`, the first to take it clears the dirty flags while it copies, and the rest find nothing and write nothing. **And a later caller waits for the first one's write** (BF-R5's map write barrier, `map_flush_latch_`, held from the copy to the last write): without it, a `Sync` that found every region clean returned before another core's copied state was on the device. A `PersistMaps` or `Sync` that returns now covers every region state copied before it began, which is what a reclaim orders its frees by.

## 5a. The var-heap page class

`kVarHeap` (`page_type = 10`, `include/kds/storage/varheap.hpp`): the out-of-line store for values too long for a tuple's fixed-width tagged cell (`docs/spec/heap-and-tuple.md` §3.4).

- **Headered, checksummed, logged** — an ordinary authoritative page class, with a `page_lsn` and a `VARHEAP_APPEND` record (`wal.md` §5.2). Waystone pages and the trail directory are *advisory*, and those rules must not be pattern-matched onto this one: losing a var-heap value loses a committed value, not a hint.
- **Layout:** the same slotted shape as a heap page — common header, an 8-byte page header (`flags`, `nr_slots`, `lower`, `upper`), a slot directory of `{offset u16, length u16}` growing down, values growing up from the tail `next_page_id` reservation. What it is *not* is a heap page: no MVCC tuple header, no delete-mark, no slot retirement, because a value has no lifetime of its own — it lives and dies with the version pointing at it.
- **Chain:** one per relation, rooted at `sys.tables.varheap_page_id` and allocated at `CREATE TABLE` for any schema that can spill, grown by tail append. The root never moves, which is what keeps it a cacheable fact (`catalog_cache.hpp`'s rule). No `min_key` and no ordering: values are reached only through the pointers in the tuples that own them, so a walk is never a search.
- **Relayout-exempt by construction.** Values are immutable per version, so the physical optimizer has no reason to touch a `kVarHeap` page and must not.
- **Max value = 8144 bytes**, one page's worth. A larger value would need a multi-page representation, so it is refused with `Unsupported` rather than answered by inventing one.
- **Release:** a rollback releases its own appends (`VARHEAP_RELEASE`, `heap-and-tuple.md` §3.4). A superseded or deleted version's value is not released; its bytes stay, so churn-heavy string updates consume space.

## 6. The Buffer Pool

- **One `DevicePageStore` for the instance**: a peer borrows core 0's store rather than opening its own (`include/kds/server/core_runtime.hpp`), so one frame table caches every core's pages and a page faulted on one core is served from the frame another loaded.
- **Unconditional.** The sharing rests on the volume having one WAL stream, because the writeback gate is a property of the log; a volume with more than one is refused at mount (`wal.md` §3, the superblock's `log_topology`), so every mountable volume has one pool.
- **What synchronizes it**: the frame table carries a **structure latch** (`frames_latch_`, `base/latch.hpp`), armed only at `cores > 1`, held across every structural mutation and every read of a `Frame`'s metadata — the insert, all three erasers, and the pin accounting. Fetch-and-pin is one operation under that hold (`FetchPinned`), and a miss publishes the page id to an in-flight set and drops the latch across the device read rather than holding one across I/O. Frame *bytes* need none of this: a page's bytes sit in a **slot** of a chunked array that never moves while the store lives (BE-R1), and a `PageRef` holds a raw pointer into the slot, so a pinned page's bytes survive any growth of the array or the table; the `Frame` itself is the page table's node, whose references outlive rehashing.
- **The page latch** (`include/kds/storage/page_latch.hpp`; `rules.md` §3's row): every resident frame carries one 32-bit word — an exclusive bit, the owning core, a count — operated on by CAS through `std::atomic_ref`, and **armed only at `cores > 1`** from the superblock's core count; an unarmed store never touches it. Taken with the pin and released with it: `Get` and the `Create*` accessors hold a frame exclusive, `GetForRead` shared. **Writeback takes it too since AT-S8 step 1b**: each page is copied under its latch, shared - waiting out another core's exclusive holder on a flush, trying once and leaving the frame dirty in the background drain - one page at a time and released before the WAL gate; and a frame is cleaned after its write only if its dirty generation, bumped at every dirty mark, has not moved since the copy - otherwise a writeback could persist half of another core's write with a valid checksum and drop the mark of a write that had not gone out. **And a writeback claims each frame from its copy to its clean since AT-S10e** (§8), so two writebacks of one page land in copy order; the claim is taken before the page latch, and its waiter holds no claim and - by the premise `HeldFrames::kWait` states and nothing enforces, that no flush caller holds a page latch across the flush - no page latch. Re-entrant for the owning **core** — a task may hold one page twice, and shared under its own exclusive — where "the owning core is the running task" is a discipline, not a gate: no task parks holding a pin, the suspend audit *records* a violation in debug builds only (`sched/coro.hpp`'s `NoteSuspension`, not fatal), and a park under a latch would be a silent second exclusive grant to the next task on that core; a per-task owner is AM-S2's escalation if the audit ever records one. **Never upgraded**: a shared holder asking for exclusive is a self-deadlock, aborted in debug and an unbounded spin on the reactor thread in release. The debug check is a thread-local multiset of the pages this thread holds shared now, exact on the same premise `CurrentCore()` rests on: one reactor per thread, no handle crossing threads. Acquisition order: **outer** to the WAL stream latch — a task appends while holding its page latches, and no WAL path asks for a page latch while holding the stream latch (recovery's redo is the one place `wal/` touches a frame at all, and it runs on the mount thread holding no stream latch) — **outer to the visibility window latch**, which is a leaf - it is taken by a visibility read, by undo growth's reclaim under whatever page the write holds, and by the delete-mark purge under a catalog page, and nothing holding it asks for a page latch (BB-S1's census) - never held across a park; and held across a writeback's durability wait by no path in the tree - a fault's sweep only queues a dirty frame (BB-S1's census). One wired would be sound only in `kSkip`, and only if it skipped a frame its own core holds: the writer thread takes no page latch, but a shared try re-enters this core's own exclusive hold (`page_latch.hpp`'s `Next`), so the writeback could copy a page mid-write. Page against page is **unordered, and nothing makes that safe**: two page latches are held on every split and chain growth (a descent holds one at a time), and one pool serves every core, so two holders can wait on each other. The pairs held at once are listed in `device_page_store.hpp`'s "The page latch" section — the split's old leaf and new sibling, a catalog chain growth's old tail and new page, and since AM-R8 a scan ring's shared hold on a heap leaf across its consumer's var-heap fetches — and **stating the order is still owed**. **One pair is stated since BB-S1, and this is its home** (`instructions/v3.0.0/workorder-bb-issue-under-the-leaf.md` BB-R4): a **user relation page** — the btree leaf a row lands on, then any parents its split secured — is **outer to a `sys.tables` chain page** (catalog page 7 and the pages its chain grows onto). Today the pair is taken by a `DELETE`'s reverse foreign-key check, whose catalog-cache miss reads page 7 shared under the parent leaf's exclusive hold (`InitTableAccess`); an insert fixes its id before its descent, holding no user page (BD-R6). It is stated beside the two cross-relation pairs declared where they are taken: a relation page before a Bound Cabin page (`assertion.md` §6.1), and page 9 before page 7 (`rules.md` §3's catalog row). **BB-R4's order** has four levels: (1) a user relation page, (2) a `sys.tables` chain page, (3) the lock table's partition latch, (4) the WAL stream latch. Nothing holds a level 2-4 latch and then asks for a user relation page, directly or through a third latch: BB-S1's census, in the work order's §6, is the proof and the list a new path is checked against, and a path that would is a defect. A page created under a hold is not a pair - no other core can reach it until it is linked. Two more items are owed with it. A re-validation after the re-fetch the two S-then-X fixes in `btree.cpp` and `index_tree.cpp` introduced: each decides on a read handle and acts after dropping it, which is unsound wherever another core can write the page between the two. **The clustered tree's is closed since AT-S5c** (`LeafStillCoversKey`, and a stale descent restarts), **and the secondary index's since AT-S15** (the same check, its bound the right sibling's first entry, which holds only while no index entry is removed - `index.md` IX14); and a split's walk back up is checked in both trees since AT-S16: every parent it writes is found, asked whether it still routes the key to the node below, and held exclusive before the first write - bottom-up, a level at a time, the one multi-page hold a tree takes besides a leaf's rightward read - and a root a level grows over is marked so no core naming it grows a second one (`heap-and-tuple.md` §5, `index.md`). And starvation — waits spin, then yield, with no queue and no writer preference, so steady shared holders of a hot page can starve an exclusive request; that one is not made worse by sharing, only reachable by more threads. **The latch is live in production at `cores > 1`** and inert at one core (AM-S1; `device_page_store.hpp`'s header).
- **Cross-core page access is what the pool is**, for writes as well as reads: **every core writes every page, the superblock and the catalog pages included**, under the page latch on the core its statement runs on; the free map, which lives in the store's regions rather than in frames, is written by every core under its own map latch (§5; `crosscore.md` CC11 names each).
- **No core owns a page.** `sys.tables.owner_core`'s bytes are reserved - written 0, never read (`docs/spec/crosscore.md` CC7). `PAGE_HANDOFF` is a retired record kind: nothing writes it, and analysis refuses a log carrying one `Corruption` (`wal.md` §3).
- **The device under them is shared, and that is declared** (`rules.md` §3): one `PageDevice` serves every core's store, and **any core grows it** (the operator's decision of 2026-09-08). What synchronises that: `page_capacity_` is a `std::atomic<uint32_t>` — a reader loads a bound that only rises, so a stale value under-reads and faults nothing it should not, and the class would not survive a shrink — and the grow is serialised inside the device (`FilePageDevice::grow_mu_` around the `posix_fallocate`, the new bound published after the file has the blocks; `MemoryPageDevice`'s one latch), so two cores running off the end at once produce one grow. The growth lock is a leaf — nothing is taken under it — and is never held across a park. **A page latch is outer to it**: what reaches the grow is a split or a chain growth, which holds its page exclusive across `CreateNew()`. Neither of this store's own latches is held there: the structure latch drops across the device read (the "what synchronizes it" bullet above) and §5's "device work never runs under it" is the map latch's rule. The order is the page latch, then this, and nothing under it.

## 7. Eviction

`docs/spec/eviction.md` owns replacement. What runs:

- **CLOCK** (second-chance) over unpinned frames, with a per-frame usage counter capped at `kClockUsageCap` = 5; the sweep decrements and reclaims at zero.
- The sweep runs **at a fill's reservation** - a miss or a creation reaching the `buffer_pool_frames` capacity - in bounded batches, before the fill's slot exists, and **on core 0's 50 ms writeback tick**, which keeps a free reserve between capacity / 16 and capacity / 8 and writes the dirty queue clean (`eviction.md` §3.2, §4). The capacity is required and a ceiling (BE-R3).
- **Clean-preferred:** a dirty frame at usage zero is queued for writeback, never reclaimed before it is written clean under §8. **The one exception is a freed page** (§5, BF-R5): its frame is discarded dirty or not, because no replay names it any more and its bytes are dead.
- **Resident classes** are pinned by class, never candidates: the fixed system pages below the resident limit, the catalog's fixed roots among them, and Bound Cabin pages (`eviction.md` EV3). A page a catalog chain grows onto is not resident by class: it is above the limit and evictable (`crosscore.md` CC12 CR3). A pinned frame is never reclaimed at any budget.
- A `SELECT`'s outermost walk faults its pages in cold (BE-R5), and the background group's bulk scans run through a small dedicated ring of frames that does not bump usage counters (`eviction.md` EV6).
- Exhaustion — every frame pinned or un-flushable — is a bounded re-walk then `ResourceExhausted`, admitted only outside a mutation's no-refuse window; the fault path writes back and waits only in drain mode - recovery, rollback, the assertion loops (`eviction.md` §3.3).

## 8. Dirty Tracking, Flush & Checkpoint Integration

The pool enforces the WAL contract in code, not by caller discipline:

- Each frame tracks `dirty`, `recLSN` (the lowest LSN redo must replay into it), and a `page_lsn` mirror. A mutation path appends its record, then `StampPageLsn()` with the record's LSN, which records the `page_lsn` the gate reads and lowers the frame's `recLSN` to it where it is unset or higher. **The minimum, not the first stamp**: a record logged after its page is released can be stamped after a higher one. A clean resets it; a clean the dirty generation skips moves it up to the lowest LSN stamped since the copy, where one was, and otherwise keeps it (`Frame::stamped_since_copy`, wal.md §11-2).
- `SetWalGate()` installs the default `WalDurability`, and `SetCoreWalGate()` gives one core a gate of its own (BA-S1). Every write path (`Flush`, `Sync`, `FlushPages`) asks the gate of the core it runs as (`CurrentCore()`), or the default where that core has none, and asks that same gate for the whole writeback. It first calls `EnsureDurable()` on the highest `page_lsn` among the pages it is about to write — wal.md §8-1 is unbypassable. One call per flush batch, not per page.
  - Each peer registers its attached manager in `CoreRuntime::Open`, before its first writeback, and takes it back in `~CoreRuntime`, before the manager is destroyed. Core 0 keeps the default, its owning manager. The reason is wal.md §8-1's: a manager's sync writes its own core's state, so a peer must never ask core 0's.
  - A core with neither a gate of its own nor a default writes ungated, which is sound only for a caller that logs nothing (the WAL-free unit tests; the simulator installs a default).
- **One writeback path.** `WriteBack()` — durable → checksum → write → clean — serves `Flush()`, the checkpointer's `FlushPages()` and the dirty-eviction-queue drain; the checkpointer is a consumer of the writeback machinery, not a parallel implementation. Ascending contiguous runs are coalesced into one `WritePageRun` of at most `kWritebackRunPages` = 8 (64 KiB), best-effort, never a correctness property.
- **A writeback holds each frame from its copy to its clean** (AT-S10e, `Frame::writing` in `device_page_store.hpp`, under the structure latch, in the frame's padding). The claim is set when a run is found, and released at the clean — cleaned or not — under the same hold, and on every early exit (the drain's truncated run, a WAL gate refusal, a failed device write). A writeback that meets a claimed dirty frame either waits for the claim and looks again (`HeldFrames::kWait` — `Flush`, `Sync`, `FlushPages`, so every checkpoint: still dirty means a write the other did not carry, and this one writes it) or leaves the frame to its writer (`kSkip`, the dirty-eviction-queue drain); a run stops at a claimed neighbour. The wait (`AwaitWritebackClaim`: brief yields, then 50 µs sleeps, because a claim spans a device write and possibly a WAL sync) holds no claim of its own — a run is claimed, written and released before the next is looked at — so two writebacks cannot wait on each other. Before AT-S10e the dirty generation made the clean honest but left the order of two writebacks' device writes to chance: the one that copied the older image could land after the newer one had written and cleaned the frame, leaving the disk one write behind a clean frame — a committed update lost with no crash.
- Checksum is computed inside writeback immediately before write-out (§10); `MarkClean` exists only as the completion step of the flush path.
- The dirty table `{page_id → recLSN}` is exported for `CHECKPOINT_BEGIN` (wal.md §11).

## 9. Frame Memory

Frames are slots in chunks of 1,024, each chunk's page bytes one allocation that never moves, grown a chunk at a time up to the capacity and never returned (BE-R1); a slot's bytes cost the process nothing until a page is read or built into it. There is no O_DIRECT. A coalesced write-out run (§8) is still a bounded copy into scratch: consecutive page ids sit in unrelated slots, and the copy is what freezes a page's bytes with its page_lsn.

## 10. Checksums

- CRC32C (hardware-accelerated where available — SSE4.2 `crc32` on x86-64; the software fallback is a correctness twin used by the deterministic sim, `include/kds/storage/crc32c.hpp`); field per §2; scope: all headered pages; computed at flush (§8), verified on every load from disk — never on buffer hits.
- Verification failure ⇒ `Status(DataCorruption)`; during recovery, a checksum-failed page with an available `FULL_PAGE_IMAGE` is restored from it (wal.md §10) — checksum *detects*, FPI *heals*.
- **A never-written page is not a checksum failure.** A page the free map calls allocated that the device cannot address or holds as all zeros reads `NotFound` ("allocated but was never written"), not `Corruption` — the same reading `DevicePageStore::Open` gives an all-zero free map. The state is ordinary because a page's bit is set when it is claimed and its bytes reach the device only at a write-back, so a crash between the two leaves it, and the distinction is what recovery needs: redo *creates* a page from `NotFound` under a `PAGE_INIT`, where a `Corruption` it could only poison and wait for an FPI. `CreateAt` accepts such an id after proving the device holds nothing. A torn page with a zero header and a nonzero body is not all zero and still fails verification. **A freed page keeps its dead image on the device** (§5), so a reused id is never the all-zero signature: every logged creation's first record is a `PAGE_INIT`, a whole-page image or a `BTREE_SPLIT` image, which redo applies over whatever is there, and the one unlogged headerless class never takes a freed id without zeroing it first (BF-S1's Census A). One case is refused rather than healed: a page that was flushed and later zeroed whole by device damage, whose first in-range record is ordinary and whose `FULL_PAGE_IMAGE` follows, is refused at redo — reachable only by damage between a checkpoint and a crash.
- Headerless pages are exempt by class (§1).

## 11. Configuration & Observability

- Config: `buffer_pool_frames` - **required**, the pool's maximum for the instance, refused at boot when absent, `0`, or below the volume's floor (`eviction.md` §6) - and checkpoint cadence (owned by wal.md). The extent size (`kDefaultExtentPages`, §5) and the resident-class list are build-time, not keys.
- Counters per store: live pins and the pin high-water (`live_pins()`, `pin_high_water()`), resident pages, and the pool's (`pool_counters()`, printed by `SHOW META` as `pool_*`: capacity, resident, slots, hits, misses, inline and background reclaims and batches, partial batches, steps, queued and drained dirty pages, refusals). A failed checksum verify is logged at Error and names corruption; allocation and write-back are logged at Trace, batch write-back and sync at Debug, every device-level failure at Error.

## 12. Read Path

- **Hit path:** a probe of the frame table (`std::unordered_map<PageId, Frame>`), a pin increment and a usage-counter bump — no syscalls. **Not lock-free**: the probe and the pin are one hold of the structure latch, and the page latch word is taken after it. Both are armed only at `cores > 1`, so a single-core instance pays no locks and no atomics.
- **Miss path:** a synchronous `pread` through the `PageDevice` seam (`FilePageDevice`; `MemoryPageDevice` under the simulator, with fault injection), then checksum verification (§10) — the hit path never touches it.
- There is no prefetch, no read coalescing and no asynchronous submission.

## 13. Write Path

- Every write-out runs through §8's one `WriteBack()` path and passes the WAL gate; commit latency itself is WAL group-commit territory (wal.md §6), not this path.
- Write-out is driven by `Flush()`, the checkpointer's `FlushPages()` and the drain of the dirty-eviction queue, which runs on core 0's 50 ms writeback tick (`eviction.md` §4). There is no writer thread.
- Batches coalesce ascending contiguous runs (§8); the single-file arithmetic mapping (§4) makes id-order literally file-order.

## 14. Growth

The file is growable to the 16 TiB ceiling:

- Growth unit is the extent (§5). `FilePageDevice` grows by `extent_pages` via `posix_fallocate` — real block reservation, not a size change — and a file whose size is not a whole number of pages is `Corruption` rather than rounded. Extension is idempotent on replay.
- The free map is unlogged (§5), so no `ALLOC` record precedes an extension; a crash between extension and first use leaves pages the allocation floor re-absorbs at recovery.
- **A creation can be claimed ahead of the write it serves** (`PageStore::ClaimNew`, `PageClaims`). A claim does everything a creation can fail at - it reserves the frame slot, claims the id (the free list first, then the cursor) and makes the device addressable for it - and publishing a claimed page cannot be refused by the pool or the device. A B+ tree split claims every page it will create once its parents are held and before it writes anything, so a file that cannot grow refuses the insert with the tree as it was; claims not used are given back, highest id first so the cursor steps back over them. A claimed id is in flight to `CreateAt` (refused `AlreadyExists`) and to `FreePage` (`kDeferred`). A store with no device claims nothing, and its claimed creations are ordinary ones.
- Shrinking/truncation is a **non-goal**. A dropped relation's pages are freed and their ids reused (§5), but nothing returns space to the filesystem.

## 15. mmap Evaluation — Rejected for Data & WAL

mmap was evaluated as the paging mechanism (map the single file, let the kernel page it). It is attractive on the surface — the arithmetic single-file layout is exactly mmap-shaped, and the kernel page cache comes free. It is rejected, for reasons that are well documented across DBMS engineering literature and are *worse* than usual under KDS's architecture:

1. **Write-ordering control is lost.** The kernel may flush a dirty mapped page at any moment. That silently violates WAL-before-data (§8, wal.md §8-1) and destroys torn-page/FPI guarantees — `msync` granularity and timing cannot reconstruct the ordering contract. This alone is disqualifying for a durability-bearing engine.
2. **Page faults stall the whole core.** A fault blocks the faulting *thread*. In a thread-per-core cooperative reactor, that is not one slow query — it freezes every task on the core for an unbounded device-latency window, gutting the SLO model (docs/spec/sched.md).
3. **Error handling is incompatible.** I/O errors surface as `SIGBUS` mid-instruction — irreconcilable with the no-exceptions/`Status` error rules and with any notion of a clean failure path.
4. **It breaks deterministic testing outright.** Kernel paging cannot be injected, scheduled, or fault-injected through the `PageDevice` seam; rules.md §4 (whole-engine simulation with torn-write injection) would be unenforceable. In KDS this is not a nice-to-have — it is how every guarantee in wal.md §16 is proven.
5. **Performance at scale is worse, not better:** TLB shootdown storms on eviction, kernel reclaim contention, 4 KiB kernel granularity vs 8 KiB engine pages, and no interposition point for checksums (§10) or the flush gate (§8).

**Verdict:** an explicit buffer pool with seam-injected I/O (decision S11), one for the instance. mmap may appear in offline tooling (e.g. read-only backup inspection utilities) but never inside the engine's data or WAL paths.

## 18. Testing Requirements

1. **Header codec:** round-trips; offset asserts; unknown `page_type` ⇒ error; version-bump gate.
2. **PageRef:** pin balance by construction; span validity bounded by ref lifetime under eviction pressure; ref-across-suspension metering.
3. **Eviction & residency:** pinned never evicted; resident classes never candidates; clean-preferred order; the full suite runs under a tiny frame budget (`KDS_TEST_FRAME_BUDGET` in debug builds) so every run exercises the sweep.
4. **WAL gate:** scripted `WalDurability` stub proves `Flush` waits for `durable_lsn ≥ page_lsn` under randomized deterministic schedules; `MarkClean` unreachable outside flush completion.
5. **Checksum:** flush-computed, load-verified, hit path untouched (instrumented); injected corruption ⇒ `DataCorruption`; FPI restoration with wal.md's crash matrix; hardware/software CRC32C equivalence.
6. **Write path:** flush batches are id-sorted and coalesced (assert on the I/O trace).
7. **Growth:** extension idempotent on replay; 16 TiB ceiling asserted.
8. **Single file:** arithmetic mapping property tests; sparse growth.
