# KDS Design Specification — Heap & Tuple

The authoritative specification for how KDS stores a row. Companion specs own the layers above and beside it: `waystone-concpets.md` (pattern-keyed access trails), `txn.md` (transactions and MVCC), `wal.md` (logging and recovery), `page.md` (page management and buffering), `parser-v2.md`, `protocol.md`, `docs/rules/rules.md` (C++ rules), `sched.md`.

---

## 1. Scope

This document specifies row storage only: heap organization, page layout, the tuple format, and the structures that address a tuple. What KDS *is* — positioning, differentiators, feature scope — lives in the project `README.md` and is deliberately not restated here.

## 2. Pages

- Page size is **8192 bytes**.
- Page ids are **unsigned 32-bit**. Capacity 16 TB = 2^31 pages, half the `uint32_t` space. `0xFFFFFFFF` is `kInvalidPageId`. Page ids are never stored in a signed type — 2^31 overflows `int32_t`.
- Status flags are never packed into a page-id field. Status bits get their own field.

## 3. Heap Organization

### 3.1 Heap pages and `min_key`

A heap page is the slotted page format (`heap::PageView`) three structures are built of: every **btree leaf** (§5), where a btree relation's rows live, every **data page of a heap relation** (`kHeapData`, §3.1b), and every page of a **system relation's catalog chain** (§3.1b). Each heap page header carries status flags and an **immutable `min_key`**, fixed when the page is created.

- **No tuple whose tuple key is below a page's `min_key` may ever be placed in it.** This holds for a leaf division as much as for insert.
- **A btree leaf is sorted by placement**: a row takes the slot its key sorts to, shifting the directory entries after it (invariant 4, §4.1). **Tuples within a catalog chain page are unordered** — append into free space.
- Because `min_key` never changes, a reader can prune pages by key range **without locking**. That is the property the immutability exists to buy.
- Moving tuples across key ranges means writing them into **pages with newly assigned `min_key` values**, never mutating an existing page's: a leaf division keeps the old leaf's `min_key` and gives the new leaf the split key (§4.1).

### 3.1a Per-page epoch counter

Every heap page header carries an **epoch counter**, bumped whenever the tuples physically on that page move. Unlike `min_key`, it is mutable by design.

Waystone records a page's epoch when it observes a tuple's location, and a consumer trusts that location only while the recorded epoch still matches the page's. This is how an advisory structure avoids becoming a second authoritative index: an operation that moves tuples bumps one counter instead of synchronously rewriting every entry that pointed into the page.

**R4 — the page epoch** (was `physical-optimizer.md` R4 and §7, last at `418670a3`, moved here on 2026-10-22 with its id kept). The epoch lives in the **common page header** as `PageHeaderFields::page_epoch` (offset 16, u64, the word that was `reserved0`), durable by construction (`page.md` §2), which trails need because trail pages are durable. Every page written before the field existed carries 0 there, so its arrival was **no format bump**: a zero reads as epoch 0, "never moved". Wraparound is unreachable at u64 width rather than handled. **Pairing rule:** no consumer may accept a location on epoch equality alone — the epoch is a fast whole-page invalidation layered over the Keystone-id check (K1), never a substitute for it.

- **Who moves it.** Only an operation that moves tuples: the btree leaf division and the in-place leaf compaction, each setting the rewritten page's epoch one past its old value (§4.1, §4.1c). An INSERT, UPDATE or DELETE that divides or compacts no leaf never bumps it; a mid-leaf placement shifts the slots after it without a bump, and the Keystone check at the slot turns a shifted entry into a miss (§4.1, BD-R3). No relayout mover exists (§7.1). `PAGE_INIT` and every page-format path leave it 0; it is read and written through `page_header.hpp`'s accessors.
- **Waystone**: the recorder stores the page's current epoch in the trail entry; replay compares recorded against current, and a mismatch is a per-entry miss with the ordinary fall-through (`waystone-concpets.md` §2 rule 2).
- **Cabin**: `CabinEntry::page_epoch` is recorded from the header and compared in `exec/tuple_verify.hpp` — the one shared verifier, so Waystone replay and Cabin hints get the real check at one site.
- **Required tests.** An epoch round-trip (field read/write and `PAGE_INIT` zeroing, `tests/page_header_test.cpp`), and the hand-bumped-epoch contract test in both suites: Waystone replay and a Cabin resolve against a page whose epoch the test bumped must fall through per entry, heal, and answer byte-identically to the authoritative path (`tests/waystone_contract_test.cpp`, `tests/cabin_contract_test.cpp`).

### 3.1b A heap relation, and the catalog's chains

**A heap relation is a set of data pages holding fixed-length rows in no key order, addressed by a rowid, and a Keystone index - its single `int64` primary key's where that is the Keystone, an engine-built one otherwise (DN-Q2), beside any other declared primary key's - through which every key access goes; a full scan reads the data pages and no index** (since DN, superblock 39, `instructions/v3.2.0/workorder-dn-heap-rowid.md`). `sys.tables.clustered_type` stores `kHeap` (2), and the `sys.tables` view reports such a relation `HEAP`, any other user relation `BTREE` and a system relation `CHAIN`. A volume older than superblock 39 is refused at its mount, naming DN's format event.

- **The pages.** `desc_page_id` is the head, a `kHeapData` page (15) created with the relation, `min_key` 1 (DN-Q16); every page is the slotted `heap::PageView` body and the chain is linked through `next_page_id`. A page never divides, is never compacted and is never freed while the relation lives, so **a row never moves**: its rowid, `page_id << 16 | slot` (`storage/heap/rowid.hpp`), names it for its life, an `UPDATE` being in place (invariant 13). A data page only appends a slot, so no slot index shifts.
- **The Keystone.** A single `int64` `PRIMARY KEY` declared first is the Keystone (DN-D5), named by an `INSERT` or issued when omitted, as a btree's tuple key is; declared anywhere else it is refused at its byte (DN-Q13 (c)). Any other primary key - several columns, another type, or none at all - leaves the Keystone the engine's hidden column 0, `int64 NOT NULL`, flagged `SysColumnRow::kColumnHidden` and named `$tuple_key` internally, and a declared primary key that is not the Keystone is a unique index beside it (DN-D3). A btree declares a primary key too, in the forms of §3.1c.
- **The Keystone index** (`kIndexFlagKeystone`, named `$keystone_<oid>`; a non-Keystone primary key's is `$pkey_<oid>`, DN-Q22) is created with the relation, in its transaction, and is unique on column 0. It is the one authoritative structure a heap finds a row by its Keystone through (K3): `exec::LocateRow` probes it and fetches the rowid's page, and a miss there is the row's absence. **A named key's uniqueness is the Keystone index's** (invariant 11), asked under the row's tuple unit before the row is placed.
- **Every index entry of a heap carries the row's rowid** after its tuple key (`index::IndexLayout::rowid_width`, `index.md` IX1), and a probe fetches that page instead of descending. **A rowid is resolved, never trusted** (DN-R3): the slot must hold a tuple whose Keystone is the entry's, else the entry is a miss - an entry that outlived its slot never answers another row - and an entry naming a page that is not this heap's is a miss too, the dangling entry a crash can leave (IX1).
- **Placement** (DN-Q7 (a), DN-Q17): a slot the release freed, then the page this core fills, then the head, each only where its `min_key` admits the row's Keystone (invariant 3, DN-R10, checked again by redo); else a new page, `min_key` the row's Keystone (DN-Q11 (a)), linked after the page that filled, so one core's rows are walked in the order it wrote them. A growth is logged as a split is - one BTREE_SPLIT imaging the new page and the page that links to it - and a row otherwise as one HEAP_INSERT at its slot. The hints are the instance's (`exec::HeapSpace`), memory only (DN-Q23).
- **A walk is page order.** The btree's leaf walk reads a heap's chain (a `kHeapData` page is a walk's leaf, `btree.cpp`'s `IsWalkLeafPage`), while every key-ordered descent refuses a data page. So on a heap no walk is bounded, seeked or pruned by a tuple key range - the range's conjuncts stay in the residual - the `ORDER BY <tuple key>` elision and the reverse walk are off, a parked walk resumes at its page and slot, and a build's resumable prefix marks a walk by place. Emission order without `ORDER BY` is no contract.
- **A slot is reused only once no entry of any index names it** (DN-D1, DN-R2): `exec::HeapSlotRelease`, stepped unasked by core 0's `system` task every 50 ms, `analytic`'s slice a step (DN-Q18). It collects the retired slots - on a hidden-Keystone heap retiring first each tombstone whose deleter every reader has passed, as `PURGE` does - purges every index (`index.md` §2.2), verifies by a walk of every index that no entry names a candidate, and frees the rest (`kSlotFlagFree`, SLOT_FREE). A heap `DELETE`, a taken-back insert, a rollback's compensation and a mount queue the relation. A declared-Keystone heap keeps its tombstones, whose Keystone entries refuse the key named again, until a `PURGE`.
- **The surface shows only the declared columns.** `*` and `rel.*` (native and the query layer), `RETURNING *`, `DESCRIBE`, the `sys.columns` view and an `INSERT`'s column count skip a hidden Keystone; a positional `INSERT` carries the declared columns and its key is issued. **`keyidentity` reads the Keystone by name on every relation** (DN-D6, DN-R5): reserved, it names no relation, column, index, namespace or alias, and every column reference resolves it to column 0 (`Schema::FindColumn`). An `INSERT` naming it names the key. The KWP load stream carries field 0, the Keystone (`bulkinsert.md` BI15).
- **A hidden-Keystone heap refuses a named key below its issue mark** (DN-Q14 (a), DN-Q20), so a deleted key is never named again and its slot is released as soon as no entry names it; a load into one names its keys ascending.
- **A declared primary key that is not the Keystone is a key over it** (DR, `instructions/v3.2.0/workorder-dr-primary-key-over-keystone.md`). The row's identity is its Keystone (DR-R2); the key is the unique index `$pkey_<oid>` (`catalog::PrimaryKeyIndexName`), which the catalog stores as any unique index and finds by that name, and `sys.columns`' `primary_key` shows its columns (`sys-views.md` §4).
  - **Unique on full values**, by `index.md` §10.2's check and no other (DR-R4): per row, at latest state, under the key's `kIndexKey` unit.
  - **Its value may change** (DR-Q1 (a)): an `UPDATE` of a key column is that index's key move. The new value is checked, a new entry is appended, and the row keeps its Keystone, its rowid, its undo chain and every reference held by Keystone, a foreign key child's among them (`foreign-keys.md` §3). K1 and K2 are the Keystone's and are not touched.
  - **A value is free as soon as no live row holds it**: after a `DELETE`, a move off it or a rollback, with no `PURGE`. A value taken again names another row, with another Keystone. This is where a key differs from a tuple key, which stays bound (K1).
  - **A statement naming the whole key is found by it**: a read by `IndexProbe` and, bounded inclusively, `IndexRange` (`index.md` §8); an `UPDATE`, a `DELETE` and a locking read by one descent per row the key's run names (DR-S3a, `parser-v2.md` I10).
  - **Its limits are a unique index's** (DR-Q3 (a)): four columns; no `NULL`; a per-row, immediate check; and a string column ordered by its first 32 bytes and decided on full values (IX6), so keys sharing those bytes cost each read and each insert a descent per key of the run sharing them.
  - **A moved key's old entry stays in the index** until the slot release's purge takes it out, which runs only beside a retired slot (`known-gaps.md`).
- **What a heap refuses**: on a hidden Keystone, `PURGE` (`Unsupported`, §4.1c). A declared-Keystone heap is purged by Keystone (DN-Q6 (a)). Every heap is a foreign-key parent by its Keystone, a hidden one read as `keyidentity` (DR-S3c, `foreign-keys.md` §3). `ON CONFLICT (<column>)` cannot name a hidden Keystone.
- The debug text port's `INSERTED … id= page= slot=` reply reports where the row was placed, as for every relation; it is no column.

### 3.1c A btree's primary key

**A btree relation carries a declared primary key in one of three forms, fixed at `CREATE TABLE` from the declaration alone and for the relation's life** (DR-S3d, DR-S3e, superblock 41; `instructions/v3.2.0/workorder-dr-primary-key-over-keystone.md` §2a, DR-R12). In each the Keystone is what it is everywhere: a 48-bit id, placed where it sorts, never rebound but by `PURGE`. What the form decides is how a row's id is chosen and what finds a row by its key.

| form | the declared key | the Keystone id | finds a row by its key | a range and an order by the key |
|---|---|---|---|---|
| **the Keystone** | one `int64`, the first column; or no declared key, and the first column, of any integer type | the column's value, named by the row or issued | the clustered descent | the tuple key's |
| **embedded** | up to four columns of `int8`, `int16`, `int32`, `date` and `bool` whose codes total 48 bits or less, each declared at a position below 256 | the key's code plus 1 (`exec/embedded_key.hpp`) | the clustered descent, at the id the key encodes to | a tuple key range: leaf order is key order |
| **hashed** | any other key within a unique index's limits (§3.1b) | in a hidden column 0: the key's home where that is free, else issued (`exec/hashed_key.hpp`) | the clustered descent at the key's home; where that does not answer, the unique index `$pkey_<oid>`, then the clustered descent | that index's range |

- **The Keystone form is the relation as it always was** (DR-R9): `PRIMARY KEY` on a btree's `int64` first column adds no column, no index and no step to any statement, and a single `int64` key declared anywhere else is refused at its byte, as on a heap. A btree with no declared key is this form.
- **A key that is not the Keystone is a key over a hidden one** (DR-R2), column 0 as §3.1b's heap has it: `*`, `DESCRIBE`, a positional `INSERT` and `RETURNING *` show the declared columns, `keyidentity` reads the id, and `sys.columns`' `primary_key` shows the key. A btree has no Keystone index: its tree is one.
- **The embedded form** (DR-Q7 (a) as revised). The code is each key column's index key encoding without its discriminator byte - big-endian, a signed type's sign bit flipped - most significant column first, read as one unsigned integer of the key's bits; the id is that plus 1, since 0 is no id. So ids ascend exactly as keys do, and one key is one id. **The mapping is a persisted format**, pinned by vectors (`tests/embedded_key_test.cpp`); `sys.tables` carries the form (`key_form`, 1) and the key's column positions, and the catalog refuses, where it loads the relation, a form this build does not know or a key the relation cannot have.
  - **An `INSERT` names its id by its key**: the row is placed at the id its key columns encode to, through the named key's path (§4.1). A row that writes `keyidentity` must write that id. A key column's `NULL` or a value its column cannot hold is the row's refusal. A key that fills all 48 bits has one combination past the id space, the largest value of every column together: refused `OutOfRange`.
  - **A key is unique because an id is** (K1): a second row with the key is refused `AlreadyExists` naming the key. **A deleted key stays bound until a `PURGE` frees it**, as a btree's named key does, and the refusal says so.
  - **A key column is never assigned** (K2, DR-Q14): `UPDATE ... SET <key column>` is `Unsupported`, and `DROP COLUMN` of one is refused. A key that must move is the indexed form's, or a heap's.
  - **A read**: every key column pinned by an equality with a literal is a lookup at the key's id; the leading columns pinned and an inclusive range on the next, or the leading columns alone, is a tuple key range (`exec::EmbeddedKeyWindowOf`). The conjuncts stay in the residual. A value that does not encode, a one-sided bound and a join key leave the step to the ladder's other arms.
  - **A write** by the whole key is the tuple key's point arm (`exec::WriteKeyOf`).
  - **`PURGE`** takes the key's own window (§4.1c).
  - **Not built, refused by name**: `ON CONFLICT` on the relation, whatever its target (`NotImplemented`).
- **A primary key has at most four columns**, on either kind and in every form: a fifth is refused at the key's byte.
- **The hashed form places a row at its key's home** (DR-S3f; DR-Q11 on the operator's bar, `instructions/v3.2.0/raft-marks-2026-11-23.md` §16). The key is the unique index `$pkey_<oid>` over a hidden Keystone, exactly as the next item says, and the id a row is first given is chosen from its key: `Hash47` of the key's full values, in `[1, 2^47)`.
  - **The index is the authority and the home is a fast path** (DR-R11, `[quiet-wrong]`). Uniqueness is the index's check on full values, after the placement, as for any row. An empty home says nothing. A row at a home answers a read only by passing the statement's whole residual, which holds the key's equalities.
  - **An `INSERT`** that writes no `keyidentity` computes the home from the row's key values, asks the home's row unit without waiting, and finds by one descent whether the id is bound. A free home takes the row. A home that is bound - by a live row another key hashed to, by a deleted row of this key until a `PURGE` frees it, by a row whose key moved away, by another writer's unit - costs the row its place and nothing else: it is issued an id, and the relation's issue mark starts at `2^47`, so an issued id is never a home. A key with no home (a value that does not coerce or encode) is issued one too.
  - **A read** whose residual pins every key column by an equality with a literal carries the home on its `IndexProbe` step (`IndexProbe::home`; `ANALYZE` prints `home=`), whichever index the ladder chose. The executor descends there first; a row that is visible and passes the residual is the answer and the index is not read, because the key is unique and no snapshot shows two rows with it. A missing row, an invisible one, one carrying another key and one the residual refused conclude nothing: the probe runs as if there were no home. A partial key, a range, a list and a join key are the index's alone, and so is every write (`exec::WriteIndexKeyOf`). **The home is tried only under a view that is a commit point** - a statement with no transaction id of its own: an autocommit `SELECT`, a `READ ONLY` transaction's. "No two visible rows share a unique key" is the unique check's promise about committed states; a read-write transaction's view adds its own writes, and under `REPEATABLE READ` it can show a row a later commit deleted beside the transaction's own row of that key. The probe returns what the view shows, so inside a read-write transaction the probe is what runs.
  - **A key that moves keeps its row's id** (DR-Q14): the row is then off its new key's home and read through the index, and its old home answers nothing for the old key, because the row there carries another.
  - **The mapping is a persisted format** (DR-R12), pinned by vectors (`tests/hashed_key_test.cpp`): per key column a tag byte, the value's length as four little-endian bytes and the value - a string's whole text, never its 32-byte prefix, and any other type's index key encoding - hashed by FNV-1a and MurmurHash3's 64-bit finish, folded to `[1, 2^47)`. `sys.tables` carries the form (`key_form`, 2). A change would leave every existing row off its home: slower, never wrong, and a format event all the same.
  - **A row that writes `keyidentity`** is placed at the id it names, as on any hidden-Keystone btree; an id below `2^47` may be another key's home, which costs that key's row its place.
- **The hashed form is otherwise §3.1b's key on a btree**: unique on full values, its value may move, a value is free as soon as no live row holds it, read by `IndexProbe` and `IndexRange` and written by one descent per row the key's run names. What differs from a heap: an entry resolves by the clustered descent (`index.md` §5), the relation keeps its delete-marked rows until a `PURGE` (§4.1c), and its key's dead entries until a `PURGE INDEX $pkey_<oid>` (`index.md` §2.2), since nothing releases a btree's slots unasked.
- **Which form a key takes is not a setting.** A key that can embed on a btree does; one that cannot is hashed. A heap never embeds and has no homes: its rows are in no key order, and its key is §3.1b's index alone.

**The catalog's chains.** The bootstrap catalog relations and the declaration relations (`sys.assertions`, `sys.transitions`, `sys.cabin_exprs`) are **chains of heap pages** linked through the `next_page_id` tail reservation (§3.2), their `sys.tables` rows carrying `ClusteredType::kCatalogChain`, on-disk 0. No user relation is a chain. **They grow by two inserts of one shape**: the declaration relations through `heap::ChainInsert` (`include/kds/storage/heap/heap_chain.hpp`: `ChainInsert`, `ChainVisit`, `ChainTail`, `ChainLength`), whose rows carry a Keystone id, and the bootstrap relations through `catalog.cpp`'s `InsertRow`, whose rows are fixed-offset structs that carry none (D3 of the catalog page ceiling, under the operator's ruling of 2026-10-18, "$!recommended").

- **Growth is a new page linked on after it is filled, never a split.** When the insert finds no room a new page is taken from the general supply (`CreateNew`), stamped with the chain relation's oid (`page.md` §2a), the tuple written into it, and only then is the page linked on - the link is what makes a page reachable.
- **`ChainInsert` appends at the tail.** It holds the tail exclusive **as** the tail: the walk takes each page exclusive while it reads the link and stops only where the link is still invalid under that hold, so a page another core linked on is walked on to, never linked over. A new page's `min_key` is the id of the tuple that caused the growth, and every id placed is above every id the chain holds, so each page's ids lie below the next page's `min_key`; a duplicate can therefore only be on the tail page, which is the only page `ChainInsert` checks (`AlreadyExists`), and an id below the tail's `min_key` is refused `OutOfRange` as a sequence gone backwards. No chain page is divided, compacted or revisited, and no tuple moves off one.
- **`InsertRow` places root-first.** It walks from the root, each page exclusive, and places the row on the first page whose free gap holds it - so a page before the tail with room left takes a row the tail would have - growing the chain only past a full tail, and its new page stays held exclusive until the row's record stamps it (AY-S7). A retired slot's bytes are not room: the insert appends a slot into the gap and nothing compacts a catalog page. Every page carries `min_key = 0`: a bootstrap row has no key to prune by, so no key orders the chain, and CT7's name check rests on the walk starting at the root (`catalog.md` CT5, CT7). It is not routed through `ChainInsert`, whose checks read a Keystone id these rows do not carry.
- **Walks are bounded by `kMaxChainPages`** (2^20 pages, `storage::kMaxPageWalkLength`), both inserts and every walk over a catalog chain; exceeding it is `Corruption` rather than a loop - except `sys.statistics`' guarded walk, which cuts the chain there (`crosscore.md` CC12). No catalog chain is bounded by a count of reserved pages. **A user relation's or an index's leaf chain is not**: it is as long as its data, and a budget refused every whole walk of a relation past 8 GiB of leaves `Corruption`, so since the audit's G19 every leaf walk - a scan, a whole-relation write, the index, assertion and transition builds, the foreign key's reverse walk, the leaf counts - is bounded by a cycle check (`storage::PageChainGuard`, Brent's check, `base/cycle_guard.hpp`) and by nothing else; a live tree never frees a leaf, so no legal walk revisits one.

### 3.2 Page layout

- The slot directory grows downward from the heap area offset; tuple data grows upward from the top; free space is the gap (`upper - lower`).
- The page tail permanently reserves `sizeof(PageId)` bytes for the `next_page_id` chain link, excluded from free-space accounting.
- The per-tuple MVCC header is **`trx_id` (48-bit writer, zero-extended to 8 bytes) + `undo_ptr` + `data_len` + flags — 20 bytes, with no `xmax`**. A version's death is the next version's birth: walking the undo chain already names the overwriting transaction, so storing that boundary a second time in the older version would be recording one fact twice. `trx_id` is whichever transaction last stamped the version — insert, overwrite, or delete-mark. The lock-slot role `xmax` plays in PostgreSQL is covered by `trx_id` itself and by nothing on the page: it was specified as the Keystone flags byte's, and AO-R3 decided the lock family persists no bit at all (§4, `txn.md` §5).
- Under the fixed-length rule (§3.3), a relation's row size is a schema constant, so a slot's `length` and the header's `data_len` carry no new information; they are retained for format stability and treated as **checked redundancy** — a value disagreeing with the schema constant is `Corruption`, never interpreted.
- **DELETE is a delete-mark**: the slot's `DELETED` flag plus the deleter's `trx_id`, with the tuple bytes left in place for snapshots that predate it. Physical reclamation is slot retirement (`DEAD`), a separate operation for a purge pass — hence two WAL records, `HEAP_DELETE_MARK` and `SLOT_RETIRE`.
- Slot entries carry their own `flags` (`DEAD`, `DELETED`) and `length`. Retirement marks a slot dead rather than compacting eagerly.

### 3.3 Fixed-length tuples & the tagged cell

**Every tuple is fixed-length.** A relation's tuple layout is a sequence of fixed-size cells at offsets computable from the schema alone; row size is a per-relation constant, asserted in the row codec rather than policed by convention. Fixed-width types occupy their natural widths — `char(N)` among them, fixed by its declaration. Every variable-width type (`TEXT`, future blobs) occupies exactly **one tagged cell**, regardless of the value stored; that cell is `kds.inline_cell_width` bytes wide — the instance's, or the column's own when it was declared `varchar(N)`.

**Reserved column slots are part of the constant** (`alter.md` AL11, BW): a relation's `SPARE n` slots - 16 bytes each, between the declared columns and the null bitmap, with a null bit each - are laid out at `CREATE`, so `ALTER TABLE ... ADD COLUMN` (a column in a free slot) and `DROP COLUMN` (a flag; the bytes stay) change catalog rows and never a row's size. `sys.columns` rows carry the dropped and in-slot flags and `sys.tables` rows the slot count; superblock 25 refuses 24.

The rule exists for tuple mobility: with fixed cells **an UPDATE can never migrate a tuple**, so with the immutable `min_key` a tuple's address is stable until a leaf division or compaction moves it on purpose (§4.1). The cost — variable-length management relocated into the var-heap (§3.4), and padding on short values — is accepted; the argument is `rule-fixed-length-tuple.md` §1.

Tagged cell layout, width `W = kds.inline_cell_width` (memcpy codec, `static_assert`ed, LE — `rules.md` §§2, 5):

| Tag (`u8` at offset 0) | Layout after tag | Meaning |
|---|---|---|
| `kNull` | zeros | SQL NULL; maps 1:1 to the wire NULL convention |
| `kInline` | `len u16`, then `len` bytes, zero padding | value fits: `len ≤ W − 3` |
| `kSpilled` | `len u32`, `varheap_ptr u64` (`page_id u32 · slot u16 · reserved u16`) | bytes live in the var-heap (§3.4) |

- The spill decision is a pure function of value length; an UPDATE crossing the boundary changes the cell's *tag*, never the tuple's size. A tag byte (rather than sentinels) is what lets NULL, empty, and spilled be distinguished without touching the var-heap, and is where future cell kinds land without a format bump.
- **`kds.inline_cell_width` is configuration-referenced but instance-pinned**: read once at bootstrap, written into the superblock, validated at every startup — a disagreement refuses to start, naming both values. On-disk layout depends on it, so it cannot be hot-changed; rewriting existing data for a new width is `Unsupported`.
- **It is the default, not the only width** (`docs/rules/rule-fixed-length-tuple.md` §4). `varchar(N)` declares `N` as *that column's* `kds.inline_cell_width` — the same number at a narrower scope, with the same `[16, 4096]` bounds from the same validator, and deliberately **no second name for it**. `N` is a width, not a length cap: a longer value spills as it always has. A bare `varchar` stores `len = 0`, which reads as the instance width. Widening a declared width is refused, because it rewrites every row.
- Default **64 bytes**. The semantics above hold regardless of the number.

### 3.4 Var-heap

The out-of-line store for spilled values. Its design goal is to be **boring**: the mobility problem was removed from the heap and must not reappear here.

- **Immutable per version.** Writing a spilled value appends `{len, bytes}` to a `kVarHeap` page and returns its pointer; values are never rewritten and never moved. Consequences, which are the rationale: an old-version reader follows the old pointer to bytes that cannot have changed, so MVCC correctness is free; pointers need no epoch, no validation, no forwarding; the var-heap is **relayout-exempt by construction**; and reclamation is a rider on purge. **Versions of one tuple share a value since BN-R3** (`instructions/v3.0.0/workorder-bn-opt-read-update-path.md`): an UPDATE re-encodes only the cells it assigns (`exec::EncodeAssigned`) and carries every other cell as it stands, so a spilled cell the SET list does not name points the new version at the old version's slot rather than at a fresh copy. **The release rule this binds** (BN-Q4 (a)): a value may be released only once **the newest version naming it** is reclaimed - never because an older version that also names it died. The releasers that exist honour it by construction: rollback releases only what its own transaction appended, which a carry never is, and `PURGE` releases only the retired tombstone's own cells, the newest version of its key; the deferred-release drain must take it as its rule. The accepted cost: a string a client re-assigns consumes space until purge catches up, making purge cadence a sizing input.
- **Logged, headered, checksummed** — an ordinary authoritative page class, `wal.md`'s `VARHEAP_APPEND` record. Waystone/trail pages are advisory; a var-heap value is committed data — losing one loses a value, not a hint. Advisory rules do not apply here.
- Update ordering: `UNDO_WRITE{kVarHeapAppend}` (the append's own rollback) → `VARHEAP_APPEND` (new value) → cell overwrite (`HEAP_OVERWRITE`, old cell image into undo), in one transaction, replayed by ordinary winner/loser recovery. The undo record comes first because redo alone must never resurrect an append the undo phase has no record to release; the append is a link in the transaction's own undo chain, so undo reaches it like any other loser write (`rule-fixed-length-tuple.md` §5). No var-heap-specific recovery logic may exist.
- Storage is invisible on the wire: `TEXT` is length-prefixed bytes to clients regardless of inline or spilled, and must stay so.

*In code.* The `kVarHeap` page class, the per-relation chain rooted at `sys.tables.varheap_page_id`, the `VARHEAP_APPEND` record and the spill/fetch path (`include/kds/storage/varheap.hpp`, `rule-fixed-length-tuple.md` §8a). `varheap::PageRelease` tombstones a slot by zeroing its offset — writing no value byte, so invariant 14 holds to the letter — and a `VARHEAP_RELEASE` record makes it durable. What releases is **rollback** and **`PURGE`**: a spill is a link in its transaction's undo chain, so both the live `Abort` and recovery's undo phase let a loser's values go, and `PURGE` releases the retired tombstone's own cells (§4.1c). A value whose version merely *died* — superseded or deleted — is not released; its bytes stay. Only an assigned spilled value appends (BN-R3; before it every UPDATE of such a row appended a fresh copy). **An append starts at the chain's last known tail since BN-R8**, not at its root: the store keeps a hint of the page the last append to a chain landed in (`PageStore::VarHeapTailHint`, memory only, 1,024 hashed slots each tagged with its root, so a slot another root took reads as no hint), reset to the root when a root is created (an id a dropped chain's root had, reused) - so a hint is always a page of its own chain - and the walk forward from it keeps every re-check the walk from the root makes, with the page's type and owner stamp checked as a backstop (`varheap.cpp`'s `ChainAppend`). **The walk is bounded by a cycle check, not a length** (the audit's G2): Brent's check refuses a link back into the chain `Corruption`, and a legal chain is bounded only by the page-id space - the hint lets a chain grow past any walk budget, and a budget refused such a chain at its first walk from the root, after a restart, and every spilling write to its relation with it. The first spilling write after a mount still walks the chain from its root. A value larger than one page (8144 bytes) is refused `NotImplemented` rather than chained across pages.

## 4. Keystone Column

Every tuple's **first column is mandatory**: one 64-bit word, the *Keystone word*. This is a self-imposed constraint of KDS and the tuple's identity lives in it.

| Field | Width | Purpose |
|---|---|---|
| `id` | 48 bits | Tuple key. Per-relation capacity ≈ 2.8 × 10^14 issued ids (K4). Bytes 0-5 of the word, which is stored little-endian (BK-R1). |
| `flags` | 8 bits | Reserved, and **written as zero** — `row_codec.cpp`'s encode is the only writer and passes 0. It was specified "Oracle lock-byte style; may reference a per-page transaction slot", and AO-R3 decided against that: M2's lock family holds **no persisted bit**, a row's exclusive tenancy being the MVCC header's `trx_id` stamp plus an in-memory table (`txn.md` §5). Tuple status such as `DEAD` lives in the slot directory, not here. Byte 6. |
| `reserved` | 8 bits | Writers set 0, readers ignore. Byte 7. |

**Every relation's tuple key is a unique 48-bit id that is never rebound - except by an explicit `PURGE` (§4.1c) - and never updated.** *Where* the id comes from is a per-**row** choice — the `INSERT` names it or omits it (§4.1) — but on a btree whose primary key is embedded, where every row's id is its key's code (§3.1c). An issued id ascends in issue order; a named key carries no order, and the leaf places it where it sorts (§4.1). What is not a choice is uniqueness: **a Keystone id is bound to at most one committed tuple in the lifetime of a relation, except across a `PURGE` that freed it** (K1), and every consumer rests on that - each re-checks a stored tuple key against the row now there, which is what makes the exception safe for it (§4.1c). The provenance of the value does not matter to any of them.

Uniqueness is obtained two ways:

- **The mark, for an issued id.** `sys.tables.next_id` never moves backwards, so an id at or above it is above every id the relation has ever placed. An omitted tuple key is the mark itself, unique among issued ids. A named key equal to an id drawn but not yet placed can be placed first; the placement's duplicate check (`SearchLeaf`) then finds it, and the issue burns the id and draws again, bounded at `kMaxIssueRounds`.
- **The descent, for a named key.** It lands on the one leaf that may hold the key, and one binary search over its keyed slots (`btree::SearchLeaf`) answers whether a slot is keyed `k`, live or delete-marked; one is a duplicate, `AlreadyExists` (§4.1). The mark gates nothing there (BD-R7). An issued id that a named key equal to it placed first is burned, and the issue draws again (§4.1).

What holds regardless:

- The cursor is **persistent, not derived**: `sys.tables.next_id`, a **high-water mark on what has been placed**. `Catalog::AllocateRowId()` returns it and advances; `Catalog::AdmitExplicitRowId()` advances it past a supplied id at or above it; one below it leaves it where it is and is refused nothing for it (§4.1). Deriving it as `max(id) + 1` would reissue an id after the highest tuple is deleted, handing a new tuple the identity of a retired one. It is what `SHOW BUDGET` and `DESCRIBE` derive K4's lifetime budget from, so it must never fall behind what was placed. The first id issuable is 1 (`kFirstRowId`); 0 stays reserved for "unset".
- **The two id sources share the one mark.** An issued id clears every key named and admitted before its draw, and a named key at or above the mark clears every id the engine has issued. A *below-the-mark* named key can meet an issued one, and the descent's duplicate check answers it as it answers any present key.
- Ids are unique by construction, **not gapless** — an insert that fails after allocating burns one, and a caller may skip a range outright. Nothing depends on gaplessness.
- **Issued ids are monotonic in issue order on every relation; named keys carry no order** (§4.1a). A btree leaf's slot order is its key order by placement (BD-R1), not by issue order. Page-wise `min_key` ordering is preserved by a leaf division as well, so range pruning (`kRange`'s tail prune, `src/exec/step_vm.cpp`) does not depend on slot order.
- The tuple key is carried **only** by the Keystone word, never also as a body column: `EncodeRow()` writes `[Keystone word][columns 1..n-1]`. Storing a key twice is how the two copies come to disagree. A supplied id is *named* in the statement's first position and still lands only in the Keystone word.
- The tuple key **cannot be updated**. It is the tuple's identity, not a field of it.
- A **declared tuple key** - a relation's first column, on every relation not created `HEAP` - must be declared with an **integer type** (`catalog::CheckKeystoneColumn`), checked at `CREATE TABLE`. A heap's tuple key is a single `int64` `PRIMARY KEY` declared first, or else the engine's hidden `int64` column 0, which the same check runs on, so a heap's first declared column otherwise takes any type (§3.1b). A declared tuple key's width is display metadata: the id lives in the 48-bit Keystone field regardless, so a narrow declared type does not cap the sequence in storage. On the binary wire the tuple key field is 8 bytes whatever the declared width (`protocol.md` §6, `wire::WireValueType`).

Implementation rules:

- Encode and decode with **explicit shift/mask helpers only**. **Never use C/C++ bitfields** for an on-disk format — their layout is implementation-defined and KDS must be portable across architectures.
- The whole word is updated with **atomic `uint64_t` operations (CAS)**. Fields must never tear across writes.
- External structures — B+ tree keys, `min_key`, Waystone entries — store the id as a **zero-extended `uint64_t`** with the upper 16 bits zero.
- **Superblock 22 refuses every version-21 volume** (BK-R4, no migration): a 21 volume's tuple words would read under this layout, but its Cabin bound entries' live flags sit in bits 40-47, which are the id's now (`cabin.md` §12.2, `assertion.md` §5.1), on their pages and inside every `ASSERT_RESERVE`/`ASSERT_BUILD` record.

**An id is consumed when a tuple carrying it commits** (BD-R4): the cursor never issues an id twice, and a committed key is never bound again unless a `PURGE` freed it (§4.1c). An id burned without placement, or placed and rolled back, is free, and a named key may take it. Sequence exhaustion is reported as `OutOfRange`, never wrapped.

### 4.1 Caller-supplied keys

> **Every relation takes a caller-supplied tuple key or issues one when the `INSERT` omits it, per row. The leaf places a named key where it sorts and refuses it because of its tuple key for exactly two reasons — a duplicate or an exhausted key (BD-R5). A heap's declared Keystone is named as a btree's tuple key is; a hidden one is named by the KWP load stream or an `INSERT` naming `keyidentity` (§3.1b) - under the same two reasons and a third, a key below the heap's issue mark (DN-Q14 (a)).**

There is no key mode and no `CREATE TABLE` declaration of who names the key: `INSERT` is the statement that names one, so the fact lives in the row's arity, and no relation that declares its tuple key refuses either arity (a hidden-Keystone heap's positional row never names it, §3.1b). There is no per-relation key-order state either: **a btree leaf places a row at the slot index its key sorts to** (`heap::PageView::InsertTupleAt`, which moves the directory entries at and after that index up one and no tuple byte), so every keyed slot of every leaf ascends by Keystone id, live and delete-marked alike, whatever order keys arrive in and at every core count (BD-R1, BD-R2, `instructions/v3.0.0/workorder-bd-sorted-leaf-named-keys.md`). A retired slot carries no key and sits anywhere. There is no exception for a relation to record (BB-R10).

*In code.* `catalog::KeyOrder`, its flip, `CatalogCache::MarkKeysUnordered`, `TableAccess::key_order`, the walk's per-page key-order emission and `DESCRIBE`'s `key_order=` are deleted (BB-R10, BB-Q11 (a)). The byte stayed at its offset (101), written 0 and read by nothing, until superblock 41 made it `SysTableRow::key_form` (§3.1c): 0, which every row before then holds, is a row that names its id or is issued one. **Superblock 20 refuses every version-19 volume** (BD-R8, no migration), because one an engine older than `1b5d252e` wrote at `cores > 1` can hold a leaf out of key order, which a fallback-free search reads wrong, and its log has no `BTREE_INSERT` or `BTREE_SPLIT` to replay. BB-R11's mount check, which read the byte and refused a relation still marked `kUnordered`, went with it. `Catalog::CreateTable` takes no key parameter.

**Syntax.** A trailing bare identifier in the same optional slot as the storage clause:

```sql
CREATE TABLE t (id int64, qty int64) BTREE EXPLICIT;
```

`EXPLICIT` is accepted and sets no field: it states what is true of every relation — the caller may name this relation's keys. `ASSIGNED` is `Unsupported` with its byte, because it means "the engine issues every id and supplying one is refused", and on the relation the statement would create, supplying one is admitted; accepting a spelling and enforcing something else is worse than refusing it. `HEAP BTREE` is an `InvalidArgument` repeat; `ASSIGNED EXPLICIT` is refused at the first word. All words are case-insensitive **identifiers, never reserved keywords**, so none of them moves a fingerprint hash. Storage follows the word: `HEAP` makes a heap of data pages found by key through a Keystone index (§3.1b), and every other user relation is btree-clustered.

**`default_key_mode` is not a config key.** It stays *known* so its absence can be reported: an instance file naming it is refused at startup with a message saying why, rather than falling to the generic unknown-key error.

**A named key is refused because of its tuple key for exactly two reasons** (BD-R5) - three on a hidden-Keystone heap, whose issue mark is the third (§3.1b), each carrying the tuple key token's byte as `(byte N)`, and `(row k)` in a multi-row statement:

1. **Exhausted — `OutOfRange`.** The key is outside `[kFirstRowId, kMaxKeystoneId]` = `[1, 2^48 − 1]`: zero, a negative number, one above 2^48 − 1, or a literal past 64 bits. It is judged from the literal's own digits, never from the lexer's wrapped value, so `2^64 + 5` is refused rather than landing as 5, and it is asked before the foreign-key and assertion steps. For an omitted key the same reason is the mark past 2^48 − 1, `OutOfRange` with its own text.
2. **Duplicate — `AlreadyExists`.** A slot keyed `k` in the leaf the descent holds, live (*"duplicate tuple key k already present at page p slot s"*) or delete-marked and not purged (*"duplicate tuple key k: a row with this key was deleted; PURGE frees its key"*, `btree::DuplicateKey`). A key named twice in one statement is a duplicate at its second occurrence.

Nothing else about the key refuses it but a hidden-Keystone heap's issue mark: after `tuple_key = 100`, `tuple_key = 99` is placed, and a multi-row `VALUES` names its keys in any order. Refusals the tuple key does not cause — the parse errors, arity, a non-integer literal (`InvalidArgument`), `max_locks_per_txn`, a lock wait, a foreign key, an assertion, `OutOfSpace` — are unchanged.

**The admission.** `Catalog::AdmitExplicitRowId(oid, id, above_mark)` refuses an id outside the space `OutOfRange` before the catalog page is touched, for a caller that did not judge its literal already. Then:

- **At or above the mark**: the mark moves to `id + 1`, persisted before the caller places anything. This runs before the descent, under no page hold (BD-R6).
- **Below the mark**: the mark is left where it is and nothing is refused — advance or nothing (BD-R7) — but where the caller passes `above_mark`, which the insert path does for a hidden-Keystone heap alone: there the key is refused `OutOfRange` (§3.1b, DN-Q14 (a)).

**Admitting before the descent is safe**: every placed id is below the mark, so a key at or above it cannot be a duplicate, and two statements naming one key serialise on its row unit.

**A refused borrow is judged once** (AO-S6c-c's rule: a key that can never be admitted never waits), so a granted borrow pays nothing. A slot keyed `k` whose latest writer has decided is a duplicate at once. Where that writer is in flight, its version chain is walked back while each earlier writer is in flight: a chain that ends is an **undecided insert**, not yet a duplicate because its rollback frees `k`, so the statement waits for its decide and the re-run answers by the outcome; a chain that reaches a decided writer is a committed row under an undecided update or delete, a duplicate at once. An absent key is a wait like any other, so **a key below the mark can meet a fence**: an open `DELETE … WHERE id < 50` makes a named insert of 10 wait (BD-R5, BD-Q9 (a)).

There is no mode check in this function, and none in `AllocateRowId` either: both run on every relation.

**The mark's advance outlives a rollback**, deliberately. It is made outside the caller's transaction (`wal::kNoTxnId`), so a `ROLLBACK` after a named key leaves the mark advanced. That costs nothing: both rollbacks retire the inserted row's slot keyless, the duplicate check does not see it, and **a rolled-back key named again is placed** (BD-R4, W12).

The mark is a **high-water mark** (BD-R7): the issue cursor for omitted keys, above every id ever placed, so an issued id needs no page read; K4's lifetime budget and the exhaustion check; what `DESCRIBE` and `SHOW BUDGET` read. A named key at or above it moves it to `k + 1`, logged outside the transaction. It refuses nothing.

**The descent is exact, and one search answers three questions.** It lands on the one leaf whose key range covers the id; `btree::SearchLeaf`, one binary search over the leaf's keyed slots that steps over retired ones, answers whether `k` is present, the slot it sorts to, and whether that slot is past every key (an append, or an append split when the leaf is full) or not (a divide when it is full). It is the one leaf search - placement, lookup, `BTREE_INSERT`'s redo and recovery undo's re-find all use it - and it has no linear fallback, because no leaf is out of order. Consequences:

- **A committed key stays bound until a `PURGE` frees it** (BD-R4, §4.1c). A `DELETED` slot keeps its key, and a divide carries a delete-marked row with its key, so a `DELETE`d tuple key named again is refused as the duplicate it is. **The delete-marked row is the tombstone**, and `PURGE` is the one statement that retires it. An engine-internal purge still owes a keyed, never-visible tombstone in the row's key position - which the duplicate check and the placement order read, and which walks and `VerifyTupleAt` treat as absent - or reclaims nothing (`docs/inflight/known-gaps.md`).
- **A rolled-back key is free** (W12). Both rollbacks retire the slot keyless and a divide drops it, so the duplicate check does not see it. That is sound because the rolled-back tuple was never visible to another snapshot, and every structure that keeps `(oid, tuple key)` past a write verifies against the row now there.
- **`PlaceUnderHold` still refuses an id below its landing leaf's `min_key`** as `OutOfRange`. The descent makes that unreachable — a separator *is* a child's `min_key` — so it is a defensive check on the two ever disagreeing, not a policy about ordering.
- **A placement mid-leaf shifts the slots after it and bumps no epoch.** Every holder of a btree row's `(page, slot)` past its hold is shift-safe (BD-R3): a Waystone trail entry, a Cabin hint and the probe memo verify the Keystone id at the slot and miss to a descent; recovery undo re-finds its row by key (`txn.md`); the inner-build probe verifies (`join-inner-build.md` JB4); JB6's resume mark is a key. The `INSERTED … page= slot=` reply names the slot at placement. A placement whose log record is never written is taken back at every failure exit before the record (index maintenance, the assertion reservation, the undo append). Without a split, the still-held leaf loses the slot (its entry removed, the entries after it moved down) and gives back the tuple's bytes. A split cannot give back a rebuilt page, so the row's slot is retired keyless, the split is logged as one `BTREE_SPLIT` under `kNoTxnId`, and a root it grew is published.

**A full leaf divides** (`SplitLeafAndInsert`, `src/storage/btree/btree.cpp`). An id above everything in a full leaf is an *append*, which opens a fresh leaf and moves not one byte. An id that sorts *inside* a full leaf forces a division, and SQL reaches it whenever a named key sorts below a full leaf's highest key (BD). Why a division is legal inside the invariants, stated precisely because it is the one place tuples move between pages without a mover:

- **Invariant 2 holds** — the old leaf keeps its `min_key` **unchanged**. A division moves the *upper* half out, so the low bound a lock-free reader may already have pruned by never moves.
- **Invariant 3 holds on both sides** — everything that stays was at or above the old bound already, and the new leaf's `min_key` is the split key, which is by construction the smallest id moved into it. Neither page ends up holding a tuple below its own `min_key`.
- **One merge, one cut.** The keyed versions are copied out in slot order, which is key order (a leaf found out of order is `Corruption`), the incoming row is merged in where it sorts, and the run is cut once. **The rightmost leaf cuts at the insertion point** (BD-Q11 (a)): the incoming id opens the new leaf with every key above it and the left leaf stays full, so ids arriving slightly out of issue order at `cores > 1` leave no half-empty leaf behind; the median takes over for an id below every key or a moving half no empty leaf holds. **Any other leaf cuts at the median.** A named key far below the rightmost leaf's top leaves the left leaf sparse, which costs space, never correctness.
- **The old page is rebuilt, not edited.** `RetireSlot` marks a slot dead without reclaiming its bytes — reclamation is a purge pass's job and no purge exists. Retiring the moved half would therefore leave the page exactly as full as it was, and the division would make room for nothing, which is the entire point of it. So the page is reformatted and the staying half written back.
- **The old page's `page_epoch` is set to `old + 1`.** Every tuple on it changed slot and half of them changed page, which is a relayout in everything but name, so §3.1a's pairing rule applies: every Waystone trail entry and Cabin hint pointing into that page becomes untrusted at once. It is set to one past the old value rather than bumped from the zero the reformat left, because an epoch that went backwards would let an entry recorded at the old value compare equal again — the one thing the field exists to stop.
- **Delete marks travel with the version they belong to.** A moved version carries its deleter's `trx_id` and arrives still marked; re-inserting the payload alone would resurrect a row some snapshot has already been told is gone.
- **Secondary indexes need nothing.** An index entry's sort key is the whole entry, `key || tuple key || covered` (`index_page.hpp`), and its payload is the tuple key — never a location — so a division is invisible to them. The undo chain is likewise addressed by `undo_ptr`, not by where a version sits.
- A leaf holding **fewer than two live tuples** cannot be divided: no boundary makes room, because the row is near page-sized. Reported as the `OutOfSpace` it is, naming the reason, rather than producing an empty leaf a descent would route to and never satisfy.
- **Every leaf's keyed slots are in key order**, through SQL and through `BtreeInsert`'s storage contract alike: both place where the key sorts, and each half of a division is written in key order. `SearchLeaf` relies on it and has no fallback.
- **A split is one log record.** Every page it writes - both leaves, every internal node created or amended, a new root - is imaged into one `BTREE_SPLIT`, whose CRC makes it replay whole or not at all, and no insert record follows it (BD-R12, `wal.md` §5.2).

**Promotion into a full internal node divides it** (`PromoteSeparator`). Two shapes, told apart rather than assumed. A separator sorting above every entry the node holds takes a right-split with no movement — a new node whose only child is the new subtree — which is the append case a monotonic sequence produces exclusively, and it is correct and free there. A separator sorting *inside* the entries, which a named key below the relation's highest reaches from SQL, divides them: the **median separator moves up** rather than being copied, its child becomes the new node's leftmost child, and the lower half is written back with the original leftmost child untouched. Copying the median instead — the leaf's rule — would route every key at exactly that value into a subtree that no longer holds it. Telling the two apart is not optional: promoting an interior separator by the cheap path would strand every subtree sorting above it, which is silent data loss rather than a wrong answer anyone would notice.

**`INSERT` arity is per-row and two-valued.** `ncols` values means the caller names the key and `values[0]` is it; `ncols - 1` means the caller omits it and the engine issues one. Both are legal on every relation, row by row, and a wrong length is refused naming **both** accepted counts — with two of them, a message naming one reads as an off-by-one against whichever the writer did not mean. The two counts cannot be confused: tuple-key-plus-*n* columns is *n* + 1 values, tuple-key-omitted is *n*; a positional `INSERT` (`parser/ast.hpp`'s `InsertStmt` with no column list) omits no body column individually, so a row's length names one reading and not the other, on every relation. **A `NULL` key at full width is the issued-key row too** (BW-Q9, `alter.md` AL11), as a KWP load row has always spelled it (`bulkinsert.md` BI15). **On a relation whose column set `ALTER TABLE` has changed, the short form is refused**: after an `ADD` its length is a row's written for the old columns with its key named, and admitting it would put every value one column over, so every row there is full width. The count does not catch every stale row: after a `DROP`, a row written for the old columns with its key left out has the full form's length and is admitted, its first value read as the key (`alter.md` AL11, `known-gaps.md`). **A column-listed `INSERT` has neither count** (BW-S6, `alter.md` AL11): each row has one value per listed name, the key is issued when the list leaves it out or its value is `NULL`, and the row is mapped to the shape below - key first when named, a NULL at every dropped and every omitted nullable position - so no column change can shift it. **A hidden-Keystone heap's positional row is its declared columns, one value each**, and its key is always issued, so neither count applies there (§3.1b).

The supplied tuple key must be an **integer literal** — the gate runs before anything is placed and must not depend on evaluation — and a non-integer value is refused `InvalidArgument`, an integer outside the id space `OutOfRange` (exhausted, above), each carrying the offending token's byte. When the row names its key, the tuple key is split off `values[0]` once, so everything downstream (the FK forward check, assertion admission, `EncodeRow`, the Cabin witness, index maintenance) receives the shape it expects: the columns *after* the key. `AdmitExplicitRowId` and `AllocateRowId` both sit after `enforcer_.AdmitInsert` and the foreign-key check, so a row those refuse burns nothing. **The borrow always precedes the encode**, because a spill is a trail entry. The orders (BD-R6, `CommandDispatcher::InsertOneRow`):

- **An omitted tuple key:** issue (`AllocateRowId`), borrow, encode, descend, place - no page hold covers the issue. A refused borrow burns the id, which is then free (BD-R4). A placement that finds the drawn id present - a named key equal to an issued id not yet placed borrowed it first and placed it - burns the id and draws again, bounded at `kMaxIssueRounds`.
- **A named key:** the exhausted check, borrow, encode, admit (advance or nothing), descend, the duplicate check, place.

**Bulk `INSERT`** runs every row through that same single-row pipeline in statement order, so a bulk statement may mix named and omitted rows, and each row is admitted, placed and indexed exactly as if it had arrived alone. A statement names its keys in any order, and a key it names twice is a duplicate at its second occurrence, with that row's ordinal.

**Every core issues and admits from the one mark.** Admitting a named key writes the relation's `sys.tables` row — the mark — and so does issuing an omitted one (`AllocateRowId`'s bump). Both happen before the descent, under no user page (BD-R6). Every core writes that row, under the page latch with no task parking inside the span (`catalog.md` CT5, §4.1a).

**The tuple key is not updatable** (K2). `exec::CompileAssignments` refuses a tuple key `UPDATE` at compile time as `Unsupported` with the column's byte, regardless of provenance. Naming a key at insert and changing one afterwards are unrelated permissions; only the first is granted.

**What none of this touches:**

- **Waystone, Cabin, secondary indexes and foreign keys**, which key on the id's *value* and never on its provenance or its order.
- **The 48-bit budget (K4)** bounds the id *space*, not the insert count. A relation fed sparse named keys exhausts it after fewer rows; both places the budget is read — `DESCRIBE` and `SHOW BUDGET` — derive it from `next_id`, which the high-water advance keeps truthful.

**`DESCRIBE`**'s summary line carries no `key_order=` since BB-S3b (BB-Q11 (a)): a field that cannot vary reports nothing, and it went with the state it reported. The tuple key column reports `autoincrement=if-omitted` on every relation that declares one, and every other column `no`; a heap's hidden key is not listed (§3.1b). Neither `yes` nor `no` is true of a tuple key — the sequence runs when the `INSERT` omits the key and does not when it names one, and both are legal everywhere — so printing either would be printing something untrue for a field's convenience.

**`ORDER BY <tuple key>` is discarded, with no per-page work.** `exec::CompileStepChain` accepts the driving relation's tuple key as an `ORDER BY` target and discards the clause outright: a walk emits pages in ascending `min_key` and a page's slots consecutively in slot order (`RunWalkStep`, `src/exec/step_vm.cpp`), and every leaf's slot order is its key order by placement (BD-R1, BD-R2). On a heap the elision is off: a walk there is page order, not key order (§3.1b). The Cabin serve's tuple key sort (`cabin.md` §4a) and the index step's (`index.md` IX8a) rest on the same premise. No relation records an exception for a reader to test (BB-R10), and superblock 20 refuses the version-19 volumes whose leaves need not hold it (§4.1).

**Recovery**: the mark's advance is one `OverwriteLogged` of one `sys.tables` row, logged before the row it covers is placed, so it redoes with every other catalog write and a crash between the two burns an id rather than reissuing one (K1, `keystoneid-invariant.md` §2). The retired key-order byte rides in the same row, written 0.

Tests: `tests/supplied_key_test.cpp` and `tests/sorted_leaf_named_keys_test.cpp` end to end (the latter's census pins every tuple-key-caused refusal to the two reasons), the admission cases in `tests/catalog_test.cpp`, the placement and leaf-division cases in `tests/btree_test.cpp`, the waits in `tests/lock_family_test.cpp` (`NamedKeyWaitTest`), and the crash cases in `tests/sorted_leaf_crash_test.cpp` and `tests/recovery_undo_test.cpp`.

### 4.1a Monotonicity when more than one core inserts

**Every core issues from the one mark.** An omitted-tuple key `INSERT` runs on
its session's core and calls `Catalog::AllocateRowId`, the in-place bump of
the relation's `sys.tables.next_id` under that catalog page's latch
(`catalog.md` CT5). Two cores issuing
into one relation are serialised by the latch, so the ids are **one
sequence in issue order however many cores insert**, and §4.1's argument
holds unchanged: the mark stays one ceiling on what has been placed, and
issued ids are unique across cores by construction (K1). **Placement order
need not be issue order on a btree** since BD (BD-R6): the bump runs under
no page hold, so an id issued before a higher one that was placed first
lands below it, at the slot it sorts to, and the leaf stays in key order by
placement (BD-R2).

**No core caches a block, and that is deliberate.** An issued tuple key is an
identity *and a sequence* (invariant 11), and a per-core block would break
issue order across cores - the later of two rows could carry the lower id.
The build departs on that ground from the per-core row-id cache of 4,096
that AT-R4 and D20 name (`instructions/v3.0.0/workorder-at-m3-uniformity.md`).
The transaction-id sequence keeps its per-core block (`txn.md` §4.2),
because no reader decides by a transaction id's order since AN-S2
(`txn.md` §4.1).

**A relation is one structure headed by `desc_page_id`**, and
`range_size_ids` is refused by name (`crosscore.md` CC8).

**What a client may rely on.** An issued tuple key is an identity **and a
sequence**, monotonic in issue order, on every relation and whichever cores
insert, and comparing two issued ids of one relation orders them in issue
order, never across relations or histories. **A named key carries no
order**: it is any id in the space not bound to a committed tuple (§4.1),
so its value says nothing about when it was inserted.

**On a heap, read order is not key order** (§3.1b): its rows lie in no
key order and a walk is page order, so without `ORDER BY` two rows issued
`n` and `n + 1` may read back in either order. A declared Keystone is
named as a btree's tuple key is; a hidden one by the KWP load stream or an
`INSERT` naming `keyidentity`, and never below the heap's issue mark.

### 4.1c `PURGE` frees a deleted key

> **`PURGE FROM [ns.]t WHERE <tuple key comparisons>` retires, keyless, the slot of every committed delete-marked row its window names, once no reader can see the row it deleted. After it the key is free, and an `INSERT` that names it is judged as if the key had never been placed.** BH (`instructions/v3.0.0/workorder-bh-purge-key.md`, PU1-PU12) built it; K1's one named exception (`docs/rules/keystoneid-invariant.md`).

**The statement** (PU1). Each conjunct compares the tuple key with a non-negative integer literal: `=`, `<`, `<=`, `>`, `>=`, or `BETWEEN a AND b`. The conjuncts fold to one window `[lo, hi)` through `CommandDispatcher::FoldTupleKeyWindow` - `DeclaredWriteBorrow`'s fold, the write path's recognizer of a tuple key window (a step chain's - a `SELECT`'s and a write's subquery - is `TupleKeyRangeOf`, `src/exec/step_compiler.cpp`) - clamped to `[1, 2^48 − 1]`. A conjunct the fold cannot read is **refused**, never skipped, because skipping one would widen the window (`id > 0 AND id != 5` would free 5). `PURGE` is a head matched by text, never a reserved word. It runs in **autocommit only**, on a **user relation with a declared tuple key only** that **carries no Transition** (BV-Q4 (a), `docs/spec/transition.md` §5: a freed key could restart a governed row's state history), with the **admin role** (`RequiredRole`'s unclassified default). It records no pattern, trail or access statistics.

**What is freed** (PU2, PU3). A slot is a target when it is keyed in the window, delete-marked, its deleter is not in flight, and `TransactionManager::ResolvedForEveryReader(deleter)` holds - every live and future reader sees the delete. A live key refuses a **window of one key**, however it is spelled (`id = 5`, `id BETWEEN 5 AND 5`), `InvalidArgument`; a wider window passes over live keys. An absent key - never placed, rolled back, already purged - purges nothing and is no refusal, so a `PURGE` can be run again.

**The waits** (PU4, PU5). A delete-marked key whose deleter is in flight, or the one key of a one-key window whose latest writer is in flight, waits for that writer's decide; a key whose deleter some reader cannot see yet waits for the horizon. Both are **polled**, bounded by `exec::kPurgeHorizonWaitNs` (1 s, no configuration key) - not by `lock_wait_fault_net_ms`, which bounds a lost wake and logs its firing as a fault - and refused `TxnConflict retryable=1` naming the key. **Each attempt is a whole statement under a fresh owned transaction**, ended before the wait: so the `PURGE`'s own view is minted after whatever it waited for and never holds its own horizon down, and between attempts it holds no view, no `IS` and no `IX` - a DDL during the wait proceeds and the re-run waits for it. The synchronous path cannot wait and answers with the refusal at once.

**Judged whole, then written key by key** (PU6, BH-R6). The attempt takes the relation's `IX` and **no row or range unit** (BH-R4), walks the window under shared holds and collects its targets, writing nothing; the first pending key ends the attempt. Then, in key order and in drain mode, each target goes through `exec::PurgeKey`: `btree::BtreeHoldTombstone` finds and verifies the slot under the leaf's exclusive hold - **skipping it unless it is still the tombstone the judged deleter stamped** (PU12: a named `INSERT`, another `PURGE`, or a purge and re-insert on another core may have reached it first) - the version's spills are read off the held page, the slot is retired and `SLOT_RETIRE` logged at `kNoTxnId` under that hold (AT-S21), and after the hold each spill is released with `VARHEAP_RELEASE` at `kNoTxnId`. **Retire first, release second**: the reverse could release a value a re-run would release again. The `IX` is held through the last release, so an `X` `CREATE INDEX`'s backfill and an assertion build, safe only under their `X`, never meet one. An online `CREATE INDEX` holds only `IS` (`index.md` §10.3): its drain waits out a `PURGE` granted `IX` before its announce, and a later one runs beside its backfill. A refusal while writing keeps every key purged before it, and its text says how many and that a re-run finishes the window; a refusal between a key's retire and its release purges that key with its spills leaked, and says so.

**A purged leaf takes its keys back** (BH-S5). Retired slots keep their directory entries and bytes, so a leaf a purge emptied, or left with one key, is full with nothing to divide - and a leaf with no key below an incoming id would append a new leaf whose low key equals its own. So **a full leaf with a retired slot is compacted before it is split** (`btree::CompactLeafAndInsert`): rebuilt in place with its `min_key`, sibling link and `grown_over` kept, every keyed version (delete marks included) back in key order and the incoming row where it sorts, its page epoch moved past every renumbered slot, logged as the one image of a `BTREE_SPLIT`; no parent changes. A copy-free scan for a retired slot comes first, so a leaf with none splits as before.

**The race with an `INSERT` of the same key** (PU12). The leaf's exclusive latch orders them: an `INSERT` that reaches the leaf before the retire meets the tombstone and is refused `AlreadyExists` (*"… a row with this key was deleted; PURGE frees its key …"*, BH-Q13); one after it meets a keyless slot and is placed, its record after the retire's.

**Logging, recovery, durability** (PU8, BH-R7). No record kind is added and the superblock version does not move for it: both records are today's, at `kNoTxnId`, so analysis never counts them a loser's and undo never reverses them; redo applies each with the rollback's own applier. A loser `INSERT` of the purged key is undone by key at mount. The attempt's `TXN_COMMIT` follows every purge record, so `PURGED n` carries the session's durability class, and its count reaches KWP as `rows_affected` (PU7).

**What it leaves** (PU11, BH-R8, BH-R9). No assertion departure (`DELETE` wrote it), foreign-key check, Cabin or index hook, undo record or trail entry is written. Secondary-index entries, Cabin entries and Waystone trails stay: every consumer re-checks a stored tuple key against the row now there, so a purged and re-placed key reads as the new row, once (BH-S1's Census B). A row `PURGE` removes no index entry; `PURGE INDEX` (`index.md` §2.2) removes the purged version's, which that statement judges owed nothing once the slot is gone; a key purged and placed again appends its own entry beside it (`index.md` IX4b). The issue cursor never hands a purged key out; only an `INSERT` that names it takes it again.

**The horizon's obligation, for every later view.** The gate is sound because every view that can read a superseded version of a user row is registered with the horizon, or reads only latest state, or is excluded by a relation `X` (BH-S1's Census A, which also closed a resumed READ COMMITTED park that re-minted its registered view above its walk's snapshot). **A new kind of read view must be shown to be one of those, or a `PURGE` may retire a row it is still entitled to read** - a wrong answer with no error.

**Refusals** (PU10), each with its byte: inside `BEGIN`, `NotImplemented` at byte 0, before the transaction is touched; a system relation, `Unsupported` at the name (checked before the qualifier, whose check calls `InitTableAccess`, and before the heap check; BH-Q17); a heap whose Keystone is hidden, `Unsupported` at the name, because it releases its own slots (§3.1b). **A btree whose Keystone is hidden is purged** (DR-Q19, DR-Q20): by `keyidentity` comparisons, folded as a tuple key's are, and - where its key is embedded (§3.1c) - by the key's own: the leading key columns each by one `=`, then one inclusive range (`>=` and `<=`, or `BETWEEN`) on the next, which is one window of ids because the ids ascend as the keys do (`CommandDispatcher::EmbeddedPurgeWindow`). Every conjunct is folded or the statement is refused `NotImplemented`; a value its column cannot hold is refused, never read as an empty window. **A heap whose Keystone is a declared `int64` primary key is purged by Keystone as a btree relation is, its tombstone found through that key's index** (DN-Q6): the walk reads the data pages in page order and judges every key of the window, and a purged slot is released once no index names it; no `WHERE`, `NotImplemented` past the name; a conjunct outside the six forms - another column, `!=`, `IS [NOT] NULL`, `IN`, a function, a subquery, column to column - `NotImplemented` at its function, column or (for a bare subquery) the `WHERE` token; a negative literal, `InvalidArgument` at it; a window of one live key, `InvalidArgument` at the literal; a wait at the bound, `TxnConflict retryable=1`; a refusal while writing, its own code with the count; a session below admin, the role refusal.

## 5. Indexing

- **Every user relation not created `HEAP` is a clustered B+ tree** on the Keystone tuple key; a heap is data pages found by key through its Keystone index (§3.1b), and only the system relations are catalog chains. The tree *is* the storage, and a descent is authoritative: a miss means the row does not exist, and no scan follows. That authority is what lets a leaf place a caller-named key wherever it sorts and refuse it only as a duplicate (§4.1).
- A btree **leaf is a heap page** — same slot directory, same tuple format, same MVCC header, same `min_key` and `next_page_id`. A clustered-btree relation is therefore not a second storage engine; it is heap pages with a directory over them.
- **A leaf grows two ways.** An id above everything the full leaf holds opens a fresh right leaf and moves nothing — the append shape a monotonic sequence produces. An id that sorts *inside* a full leaf makes the leaf **divide**: the keyed versions are cut once - the rightmost leaf at the insertion point, any other at the median key - the upper part moves to a new leaf whose `min_key` is the split key, and the old leaf keeps its own. SQL produces both shapes, the second whenever a named key sorts below a full leaf's highest; §4.1 carries the invariant argument, the epoch consequence and the internal-node case. Below a full leaf a row takes the slot its key sorts to (§4.1), and **a split is logged as one `BTREE_SPLIT` record** (`wal.md` §5.2).
- **A new leaf is published separator first, sibling link last.** A leaf is reachable two ways — a descent routed by its parent's separator, and a scan following the previous leaf's `next_page_id` — and a grow writes them separately, so one of the two half-applied states is always possible when a page allocation or a page read fails part-way through. Only one of them is survivable, and the order is chosen on that: *separator written, link not* leaves a page allocated and unreachable to a scan, which costs an allocation and nothing else, because a failed promotion fails the insert and no caller kept a row in it. *Link written, separator not* is unsurvivable — the leaf sits in the sibling chain routed by nothing, so the **old** leaf goes on taking the ids the new one holds, it is full, and the next such id appends another leaf *in front of* the unrouted one. The chain then descends, and the page-wise ordering the descent's exactness, and so the duplicate check, rests on is false. The ordering, and the fact that the final link write goes through the descent's own pin so it cannot fail, are in `src/storage/btree/btree.cpp`. **A catalog chain has no such question**: nothing routes to a chain page, so the link is its only publication and it is written last (§3.1b).
- **A descent is authoritative across cores too, and what makes it so is a coverage check rather than a lock** (AT-S5c). A leaf covers `[min_key, right sibling's min_key)`; both ends are immutable, so the interval changes only by a page spliced in on the right, which is what both split shapes do. Two cores reach one relation's leaves and a descent has **no latch coupling** (it releases an internal node before asking for its child, `page.md` §6), so in that gap the leaf can give the top of its range away. **A write descent takes its leaf exclusive at once** (DK's D1, `workorder-dk-descent-low-key.md`): the parent's stored `level` says its child is a leaf, so below a level-1 node the leaf is fetched with `Get` and never held shared first, and a child that is not a leaf where `level` named one is `Corruption`; only a root that is itself a leaf is read shared, released and fetched again exclusive, a second gap of the same kind. The descent therefore asks whether the leaf still covers the key, and when it does not it **moves right** along the leaf chain (DK's D2): it reads `next_page_id` under the leaf's hold, releases the leaf, fetches the right one in the same mode and asks again - the failed check proved the key at or above the right leaf's `min_key`, which never moves, so no coupling is needed - up to `storage::kMaxLeafHops` hops; past them it starts over from the root, bounded by `storage::kMaxDescentRestarts`, and a restart makes progress because a splitter holds the old leaf across its own separator promotion. A read lookup's miss moves right the same way. **A write never moves right from the named root itself** (DK-Q10): `SecureParents` reads "no parent" as "this leaf is the root" and a growth goes over `path[0]`, so a stale root that is a leaf is refused as before. A stale internal root reaches, within the hop budget, the leaf that covers the key; when the hop crossed out of the stale root's subtree, a split from that leaf finds no parent below the stale root and is refused with nothing written, and a split from a leaf inside it is answered unless it would grow over the stale root, which its mark refuses. **D1 and D2 hold only while no leaf is removed and no `min_key` is rewritten** (DK-R5): a merge or a rebalance reopens them by name. **The write path pays this unconditionally and a lookup pays it only on a miss**, a hit being authoritative however the chain has moved; a monotonic tuple key lands on the rightmost leaf, which has no sibling to ask. `BtreeSeekLeaf` asks nothing, and the reason is directional: a split moves keys only to the right, so a seek that is outrun lands to the *left* of where the key went, and the scan it feeds walks forward onto that page next.
- **A split finds every parent it will write before it writes anything** (AT-S16, `SecureParents` in `btree.cpp`). The descent recorded its path holding none of it, so since AT-S5 another core can divide a recorded parent first and move the split leaf - or, one level up, the divided node - to the new half, where a separator put into the recorded parent is routed by nothing. This reaches the append path too: two appends serialise on the tail leaf, but a divide under the same parent - which a named key reaches from SQL - waits for neither. So once the leaf is known to split, the insert climbs while the nodes are full, taking each parent **exclusive** and asking whether it still routes the key to the node below - exact, because that node is held and every change to its range is a divide of it - and re-descends from the root it was given on a miss (the operator's Q1 ruling, 2026-09-26: re-validate and re-descend). **Nothing is written until every parent is held, and every page the split will create is claimed** (`PageStore::ClaimNew`, `page.md` §14: its new leaf, one node per full parent, and a root when it grows), so a refusal - `TxnConflict`, retryable, naming a stale path, after `storage::kMaxDescentRestarts`, or the device's own when it cannot grow - leaves the tree as it found it rather than a divided node no parent routes to. **A split that grows a level also pins the relation's anchor first** (`PageStore::PinUnlatched`, `page.md` §3), the page its new root is re-published through: pinned, not latched, so the anchor's later fetch is a hit the bounded pool cannot refuse after the split has written, and the split takes the anchor's latch only where it always did, after its pages - holding the anchor exclusive across the split would order it ahead of index pages another core's index split holds while it waits for the same anchor, and a page latch has no timeout. The pin is given back once the root is staged into the anchor. **Since BA-S14 the clustered tree's refusal is re-run inside the engine** (`workorder-ba-parallelism.md` BA-R11, BA-Q10): a statement that wrote nothing before it waits a turn and runs again from the top under its deadline, re-reading the root, so a client sees it only when the re-runs outlast the fault net or the statement had written rows first. The index tree's keeps reaching the client: it comes after the row is placed, where a re-run would leave earlier indexes' entries behind. The holds cannot deadlock: they are taken bottom-up a level at a time, a re-descent reads only above everything the insert holds, and nothing holds a node and asks for one below it or to its left. A restart makes progress by the descent's argument one level up: a divider holds every node it writes until its insert returns, so a re-descent blocks on it or reads it after its separator is in place.
- **A root is marked when a level grows over it** (AT-S16; the operator's word of 2026-09-28). The old root - a leaf (`kHeaderFlagGrownOver` in the heap header's `flags`) or an internal node (`kInternalFlagGrownOver`) - is marked under the hold the split already has, as the last write of the growth, after every step that can fail: the mark is the only thing on the page that says it now has a parent. A core whose memo still names it - another core grew over it, published or not; a memo drops at the next task boundary - reads the mark before it would grow a level of its own over it and is refused before writing, instead of growing a second root whose publication drops the other one's half. A page written before the mark existed carries 0, which claims nothing, so its arrival is not a format event; the mark is never cleared and a divide's rebuild keeps it.
- **A lookup's answer is held, not only its status** (AT-0 item 12, marked (a); `workorder-at-m3-uniformity.md`). A hit's `(page, slot)` is true only while the leaf is: a division rebuilds the old leaf and moves its upper half, and a placement mid-leaf shifts every slot after it, so a slot read after the leaf is released can be another row. `BtreeLookup` therefore returns the leaf with the location - the descent's own `PageRef`, shared for a reader and exclusive for a writer that asks `kWrite` (a point `UPDATE`/`DELETE`, and rollback's relocation) - and **no caller re-fetches the page by id**. A location carried past its hold - the step runner's probe memo, a Cabin entry between its two serving phases - is a hint, and is read only through `VerifyTupleAt`, whose relayout-epoch and Keystone checks turn a moved row into a miss and a re-descent. Nothing reads under the hold across a suspension.
- **Waystone** (`waystone-concpets.md`) is the engine's other access structure: `(fetch_id, arg_hash)` → the Keystones a previous execution of that pattern instance found, across relations. It is advisory and validated on use, and it may replace a *lookup* but never a *search*. **It records and replays only for the shapes an operator opted in with `WAYSTONE ON` since CF-S1b** (`waystone-concpets.md` §4a): every other `SELECT` pays one atomic load while nothing is opted, and no `SELECT` writes a catalog row.

## 6. Page-Latch Consistency

There is no single canonical in-memory tuple and no hash table enforcing that an identical tuple exists at most once in program memory. Consistency is kept at the **page** level.

- A page frame is **pinned** for the duration of any access and **latched** — shared for reads, exclusive for structural mutation (slot directory changes, a leaf division or compaction). Tuple bytes are read and written directly within the pinned, latched frame; there is no tuple-identity cache to keep coherent with the page.
- Latching is **a cross-core lock**, declared on `rules.md` §3's shared list (the page frame's latch word, AM-S1) over the instance's one pool (AM-S2). A frame's latch word is held by a **core**, re-entrant for that core and never upgraded, and it serializes holders on different cores as readily as tasks on one (`page.md` §6). A write runs where the session is (`crosscore.md` CC11), so the latch's cross-core half is load-bearing, and `btree.cpp`'s descent depends on it (AT-S5c).
- Executors may copy tuple bytes into private working buffers. These are ephemeral projections; they compete with no canonical copy, because there isn't one.
- The Keystone word's atomic-CAS requirement (§4) is independent of latching: even under a latch, the word is read and written as a `std::atomic<uint64_t>` so fields never tear.

Frame reclamation under this model is `docs/spec/eviction.md`'s: every accessor returns a pinned `PageRef`, and a CLOCK sweep reclaims only unpinned frames of evictable classes.

## 7. Access Statistics, and no Relayout

KDS collects access statistics; they are read by `SHOW ACCESS` and by `CREATE CABIN`'s no-filter warning, and the Cabin controller does not read them (`cabin-controller.md` R2).

**Collection is built; no relayout planner or mover is.** `sys.access_stats` records one row per access *shape* — `(kind, rel_id, column_mask)` — with how often it ran and when it last ran, written for every access kind through one call with no per-kind branch (`include/kds/stats/access_stats.hpp`): a `SELECT`'s every step at its successful end, and a foreign key's forward and reverse checks when they run, whatever the statement's end; a failed `SELECT` records nothing. **The store is memory, the instance's, since DA** (`instructions/v3.2.0/workorder-da-access-stats-memory-resident.md`): one part per core, the core a statement ran on its part's only writer, a count in the part before the statement returns, and a reader merging every part (`sys-views.md` §6.2d) - emptied by a restart and a restore, as the catalog relation at page 11 it replaced was emptied at every mount. A part admits 4,096 shapes by default (`access_stats_bytes_per_core`); a new shape past it is dropped and counted (`sys.meta`'s `access_stats_dropped`), and every known one goes on counting. An `ADD COLUMN` that reuses a position removes that position's shapes from every part before it answers (CD-OI-13 (a)); a dropped relation's shapes stay until a restart. `access_statistics = off` records nothing. `SHOW ACCESS` reads it, and `CREATE CABIN` warns when no recorded shape filters the Cabin's column (`exec/cabin_ddl.cpp`); nothing else acts on it.

The shape is keyed by **columns, never values**: `WHERE flag = 1` and `WHERE flag = 2` are one row. That is what bounds the relation by the schema rather than by the data, so it needs no eviction policy and no directory — the unbounded axis, *which arguments repeat*, is Waystone's and stays there (`waystone-concpets.md` §5). The two layers answer different questions and are deliberately not merged.

The kind split is what makes the data worth having: a walk driven by an equality on a non-tuple-key unindexed column is `kFilterScan`, not `kScan` — a statement that asked for a few rows and read all of them, the case an index or a clustering decision would fix. `kIndexProbe` and `kIndexRange` (`docs/spec/index.md` §8) are counted through the same call. Neither scan kind is trail-replayable — invariant 9's line is lookup versus search, and both are searches.

### 7.1 No mover

(Was `physical-optimizer.md` §6, §8's retired key and §10, last at `418670a3`, moved here on 2026-10-22.)

**Nothing moves a tuple for statistics' sake.** No relayout planner or mover exists, and every user relation not created `HEAP` is a btree, so a mover would be a tree restructure: it would have to respect the `min_key` insertion rule (§3.1), keep the tree's descent exact (§5) and bump the page epoch (§3.1a) so every recorded location on a page it moved becomes untrusted at once. `kVarHeap` pages are outside any such move by construction (§3.4). Three facts about the engine stand in front of one:

1. **Reader horizon.** `ReadHorizon()` bounds a purge (`txn.md` §4.1); a delete-marked user row is retired only by `PURGE` (§4.1c), and nothing compacts a relation for space.
2. **Ordered-between compatibility.** Clustering an arbitrary hot id set onto one page would break the between-pages key order that the descent and `kRange` pruning read.
3. **Cross-relation page reuse.** Trail validation checks `rel_oid` and the Keystone id at the recorded `(page_id, slot)`, ids are issued per relation, and `PAGE_INIT` writes epoch 0 — so a page freed from relation A and reallocated to B could validate a stale trail entry. **Answered for a dropped relation's pages** (`drop-table.md` DT1, BF-Q17 (a) of `instructions/v3.0.0/workorder-bf-drop-table-page-reclaim.md`): the reclaim frees only pages its owner walk checked; it frees nothing before no replay can name a page; and the one verifier checks the page's class and `owner_oid` against the location's relation, so a reused page is a miss (BF-R10). Every mountable volume's user pages carry `owner_oid`, so no mountable volume holds a page that reads owner 0.

Not in this engine: a relayout planner or mover, and per-pattern hot-set clustering. The relayout surface is deleted since BZ: the shadow planner, `SHOW RELAYOUT` and `sys.relayout` are gone, `SHOW RELAYOUT` is refused as an unknown `SHOW` target, and `relayout` is an ordinary identifier (nothing is reserved). The `physical_optimizer` config key that switched the planner is **retired**: a file naming it is refused at startup by name (`Expeditor::Config::ApplyFile`'s retired keys; `crosscore.md` CC10).

## 8. Invariants

Never violated, never "temporarily" bypassed.

1. Page size is 8192 bytes; page ids are `uint32_t`; `0xFFFFFFFF` is reserved as invalid.
2. A heap page's - a btree leaf's or a catalog chain page's - `min_key` is immutable after creation, until the page is freed. A page id reused after a dropped relation's reclaim is a new creation, its `min_key` fixed again by that creation (`drop-table.md` DT1).
3. No tuple with `id < min_key(page)` is ever placed in that page, including by a leaf division - for the life of the page, which a free ends.
4. Tuples within a catalog chain page are unordered by contract. **A heap data page is unordered**: a row takes a free slot of a page whose `min_key` admits its Keystone (invariant 3, DN-R10), and its slot says nothing of its key. A btree leaf is sorted by placement: every keyed slot ascends by Keystone id, live and delete-marked alike, whatever order rows arrive in and at every core count, because a row takes the slot its key sorts to (BD-R1, BD-R2); a retired slot carries no key and sits anywhere. Readers rely on a leaf's order through the `ORDER BY <tuple key>` elision, the Cabin serve's tuple key sort and the index step's sort (§4.1), **and on a heap none of them reads slot order: the elision is off and both sorts take the Keystone from the row or the entry.**
5. The Keystone column is exactly `id:48 | flags:8 | reserved:8`.
6. The Keystone word is read and written atomically as a `uint64_t`; on-disk encoding uses explicit shift/mask, never compiler bitfields.
7. Ids stored outside the tuple header are zero-extended `uint64_t` with the upper 16 bits zero.
8. Waystone is advisory: deleting it wholesale may cost performance and must never change a query result.
9. Waystone is never **authoritative**. A reader may consult it for *where to look*, provided it treats a missing or stale entry as a miss, checks the Keystone id of the tuple actually found at the reported location, applies MVCC visibility exactly as the authoritative path would, and falls through to that path - a btree descent on a btree relation, the Keystone index's descent and the rowid's page on a heap (§3.1b) - on any mismatch. It chooses where to look, never what is visible.
10. No single canonical in-memory tuple is enforced; consistency comes from page pin and latch discipline (§6).
11. Every relation's tuple key is a **unique 48-bit `id`, never rebound except by `PURGE` (§4.1c), never updatable, and never carried outside the Keystone word**. A declared tuple key is an integer column, the relation's first; where a primary key is declared it is the single `int64` one, which is declared first (DN-Q13, DR-S3d). A relation that declares any other primary key, and a heap that declares none, carries an engine-added hidden `int64` column 0, which `*` never includes and which one reserved word, `keyidentity`, reads by name on every relation (DN-D3, DN-D6); the declared key is then a key over it and no tuple key (§3.1b, §3.1c). **A rowid is not a tuple key**: it names where a heap row is, `page << 16 | slot`, and a slot is reused for a new row with a new Keystone once no index entry names it (DN-D1, DN-R2) - so K1 is the Keystone's, and a rowid is bound to many rows over a relation's life, one at a time. **On a heap a named key's uniqueness is the Keystone index's, not a leaf's**: a key an entry of it names - live or delete-marked - is `AlreadyExists`. A declared-PK heap keeps a deleted row's Keystone entry until a `PURGE` frees the key; a hidden-Keystone heap refuses a named key below its issue mark, so a deleted key is never named again (DN-Q14). Where the id comes from (§4.1) is a per-**row** fact — the `INSERT` names it or omits it — and there is no key mode, and no relation that declares its tuple key refuses either arity. **One declaration fixes it for a relation's every row** (DR-S3e, §3.1c): on a btree whose primary key is embedded, every row names its id, which is the code of its key columns, so no id is issued there and none is named that is not its row's key; that is the relation's key form, fixed at `CREATE TABLE`, and it changes nothing an id is - 48 bits, unique, in the Keystone word, placed where it sorts. On a btree whose primary key is hashed (§3.1c) an omitted id is the key's home where that is free and an issued one otherwise, the mark starting above every home; that too is a choice of the id's value and of nothing an id is. **A Keystone id is bound to at most one committed tuple in the lifetime of a relation, except across a `PURGE` that freed it** (K1, BD-R4). `sys.tables.next_id` is a **high-water mark on what has been placed**: `AllocateRowId` draws from it for an omitted key, `AdmitExplicitRowId` advances it past a named one at or above it, and it never moves backwards. **Issued keys are a sequence in issue order**, unique among issued ids by the mark; the placement's duplicate check catches one a named key took first, and the issue draws again (§4.1). **Named keys carry no order**: a named key's uniqueness is the descent's - a slot keyed `k`, live, or delete-marked and not purged, is `AlreadyExists` - and it is otherwise refused only as exhausted, `OutOfRange` (BD-R5); a leaf's slot order is its key order by placement (invariant 4). No relation refuses a named key for being below the mark but a hidden-Keystone heap, as above (DN-Q14 (a), DN-Q20). No relation records an exception: `kUnordered` is deleted (BB-R10). What nothing relaxes: the tuple key is not updatable, the cursor never issues an id twice, and a committed key is never bound again except after the `PURGE` that freed it.
12. The tuple MVCC header is exactly `trx_id:48 (zero-extended to 64) | undo_ptr | data_len | flags` = 20 bytes. There is no `xmax`; a version's validity interval is reconstructed from the undo chain, and DELETE is the slot's `DELETED` mark plus the deleter's `trx_id`.
13. **Every tuple is fixed-length.** A relation's row size is a schema constant; variable-width values occupy tagged cells of exactly `kds.inline_cell_width` bytes (§3.3), and that width is instance-pinned in the superblock. No code path produces a tuple whose size differs from its relation's constant.
14. **Var-heap values are immutable per version** and `kVarHeap` pages are never relocated; the class is logged, headered, and checksummed — authoritative data, not advisory (§3.4).
