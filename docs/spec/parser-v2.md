# KDS Query Language v2 — Parser, Step Chains, and Execution

**Official specification** of the query language: the parser, the
AST→`StepChain` compile contract, and the execution contract. Consistent
with `docs/rules/rules.md`, `docs/spec/protocol.md` (KWP §5),
`docs/spec/waystone-concpets.md` (trail model and replay contract),
`docs/spec/heap-and-tuple.md` (invariants 7 and 11), `docs/spec/txn.md`,
`docs/spec/aggregate.md`, `docs/spec/join-inner-build.md` and
`docs/spec/null.md`.

The language runs: the step compiler (`src/exec/step_compiler.cpp`), the
step VM (`src/exec/step_vm.cpp`), joins, predicate-position subqueries, the
tri-state collapse, the row-touch budget (`include/kds/exec/budget.hpp`) and
pagination are in the tree with `tests/exec_chain_test.cpp`,
`tests/exec_subquery_test.cpp`, `tests/exec_budget_test.cpp` and
`tests/pagination_exec_test.cpp` beside them. The parser is recursive
descent over an owning AST; tokens are zero-copy views into the statement
and the fingerprint is accumulated during the parse. The corpus
(`tests/testdata/parser_corpus.txt`) is the enumeration of verdicts, verdict
by verdict.

`IN (value list)` is served since BU-S2 (I10) beside `IN (SELECT …)` and
`BETWEEN`; `CREATE TABLE` takes no `WITH (...)` option table (I7).

## 0. Decision record

| # | Decision | Choice |
|---|---|---|
| J1 | Subquery scope | **Wide**: predicate-position subqueries — scalar (uncorrelated *and* correlated), `IN`/`NOT IN (SELECT …)`, `EXISTS`/`NOT EXISTS` — nesting to a fixed depth cap. Not restricted to flattenable forms |
| J2 | Inexecutable forms | Refused, understood, with an exact position — never a slow generic path. Table-position nesting (derived tables, CTEs), subqueries containing aggregates (**AG8**), and over-depth are truthful errors |
| J3 | Classification | Absorbed into **`kJoinSelect`**; the concept generalizes from "join chain" to **step chain**. No new enum value |
| J4 | Vehicle | The AST→`StepChain` compile contract is the seam: the parser emits an AST, `Compile(AST) → StepChain` resolves names against the catalog, and nothing downstream sees a name |
| J5 | Trail recording policy | **n = 2**: an instance's trail is recorded on its **second** execution (the first only counts) |

**J2's one code is two.** Everywhere this document writes a refusal, read the
*code* off the rule that splits it (`include/kds/base/status.hpp`,
`docs/spec/protocol.md` §11): `Unsupported` is what this engine's
architecture cannot admit and no later release lifts, `NotImplemented` is
what the design admits and nobody built. The position requirement, the
never-a-generic-path requirement and every form's membership in J2 hold for
both. **Most of J2 is `NotImplemented`** — table-position nesting (derived
tables and CTEs), outer joins, `ORDER BY` by ordinal or expression, the
aggregated-output tail, subqueries containing aggregates, and
`ORDER BY`/`LIMIT` inside a subquery; of these, outer joins (BU-S6), the
ordinal and expression keys (BU-S4), the aggregated tail and aggregating
subqueries (BU-S5) are refused by the step chain and answered by the query
layer (I19). **What is `Unsupported`** is the
shorter list: the depth cap (a recursion needs *a* bound structurally, and
the parser, the compiler and the step VM agree on it), one relation named
twice in a FROM list without distinct aliases (distinct aliases are the
answer on every later release too), and a `$name` parameter on the newline
protocol, whose wire has no bind step.

## 1. The step chain

Every SELECT-class statement compiles to a **step chain**: an ordered list of steps, each reading one relation with one access kind. The chain's order is execution order: the written order, or the join planner's for a planned block (I12) - *the chain is the plan*.

| Kind | Authoritative work | Trail-replayable? |
|---|---|---|
| `Lookup` | tuple-key-equality descent (constant or bound param) | **yes** — completeness follows from tuple key uniqueness, **and only under rule 0** (I17) |
| `Probe` | tuple-key-equality descent keyed by a value produced by an earlier step or outer row | **yes** — same argument, per producing row, **and only under rule 0** (I17) |
| `Range` | tuple key range via the leaf chain | no — search; prefetch only |
| `Scan` | full walk with a predicate | no — search; prefetch only |
| `Exists` | semi-join probe: stop at the first qualifying row | **positive result only** (§4) |
| `NotExists` | anti-join: prove absence | **never** — absence has no witness |

**A `Lookup` step that carries a key set** (I10, since CU-S1) descends once per value of a list and is a search over those values: it is not trail-replayable (`IsTrailReplayable(const Step&)`).

A join contributes one `Lookup`/`Probe`/`Scan` step per relation, in the chain's order. This table *is* `docs/spec/waystone-concpets.md` §2's trust model — a waystone may replace a lookup, never a search — extended with the negation rule: **negation steps are search-class by definition**.

Step numbering is global (the outer chain and every sub-chain share one counter), so a trail entry's `step_id` is unambiguous without parent linkage. **A top-level step's `step_id` is its relation's written position, whatever position the planner runs it at** (CB-Q3) - an invariant every trail, every `ExecStats` lookup and CC's statistics key on. A written-order chain is a pure function of the AST without its select list (only the projection mask reads that), hence of `fetch_id`; a planned block's order is also a function of the catalog and of the planner's inputs (I12), and a trail stays replayable across orders because replay is keyed by `(step_id, tuple key)` and re-derives the key (I17) (AP-S2, `waystone-concpets.md` §3).

## 2. Subqueries as steps

- **Uncorrelated subquery** → a **prefix sub-chain**: hoisted, executed exactly once before the outer chain, its result bound as a value (scalar) or a probe set (`IN`).
- **Correlated subquery** → a **nested sub-chain step**: executed once per outer row, correlation columns arriving as `Probe` keys. A correlated tuple-key-equality subquery therefore costs what a join step costs and records the same trail shape.
- **Scalar cardinality:** more than one row is a runtime error, `CardinalityViolation` (retryable = 0). Parse time cannot prove cardinality in general, so the check is per execution. Zero rows is NULL, and therefore a false predicate. A first-row pick is never acceptable — it makes the answer depend on physical order.
- **`IN` (positive)** compiles to `Exists` per outer row over the sub-chain, or a hoisted probe set when uncorrelated. **`NOT IN` / `NOT EXISTS`** compile to `NotExists`. `NOT IN` keeps standard three-valued semantics — any NULL in the subquery result makes the predicate never-true — implemented, tested, and called out in the client manual as the foot-gun it is.
- **Depth cap:** sub-chains nest to depth **4** (`parser::kMaxSubqueryDepth`); deeper is `Unsupported`.
- **Out of scope (J2) for a step chain, each refused with an exact position:** subqueries in FROM (derived tables, the query layer's since BU-S7, I19), CTEs, subqueries containing `GROUP BY`/aggregates (**AG8** — a fold inside a sub-chain puts an aggregation boundary where the execution model has none), and subqueries in `INSERT`/`UPDATE` value position.

**Why table-position nesting stays out of the step chain**, since it is the question every reader asks next (the query layer answers a derived table over rows it holds, I19, and never as a step): a derived table's result must become a relation with a schema, materialized somewhere and probed by something other than a tuple key. That breaks tuple-key-direct probing into the next step, which is the entire shape of the execution model, and it puts a temporary relation in the storage layer. A predicate-position subquery needs none of it — it consumes rows and yields a boolean or a value.

The structural rule that enforces it: **the relation-reference production must never reach the statement production**, and `WITH` must not lex as a statement head (a statement beginning `WITH` is `NotImplemented`).

## 3. Architecture instructions

**I1 — Literals are arguments, never shape (`pattern_id` for free).**
The fingerprint is one pass over the token stream, taken during the parse (`include/kds/parser/fingerprint.hpp`): `pattern_id` hashes the *shape* — every token in order, with each value literal replaced by a single parameter marker — and `arg_hash` hashes the *arguments*, the inline literal values in the order they appeared. Identifiers are shape. Inline-literal and bind-parameter forms converge on one `pattern_id`: `WHERE id = 42` and `WHERE id = ?` are one pattern, and a `?` contributes nothing to `arg_hash` because its value arrives at BIND; `param_count` says how many bound values a BIND stage folds in before the instance key is final. A correlation reference contributes a *shape* marker to `pattern_id` and nothing to `arg_hash`, so a correlated statement keeps one stable `arg_hash` across outer rows — which is what gives it an instance key at all.

No `kFingerprintVersion` bump follows from any grammar addition: new keywords, `.`, and sub-select parens are additive shape, and every previously-accepted statement hashes identically. That invariance is pinned by the corpus, not assumed.

**I2 — One class per statement; the chain is the shape. (J3)**
The parser classifies execution shape at parse time and the executor dispatches on it with a `switch`; the one plan enumeration is the join planner's choice of a block's order (I12). **Every step-chain statement classifies as `kJoinSelect`**, read as "step-chain select"; single-relation point and range forms keep their own classes. The enum is `StatementClass { kPointSelect, kRangeSelect, kJoinSelect, kUnclassified }` (`include/kds/exec/step_chain.hpp`) and does not grow: root classes for every outer shape × inner shape × correlation state would be an unbounded cross product, and `sys.patterns.stmt_class` is one byte on disk. The `StepChain` carries the shape; the tag carries the dispatch. `kUnclassified` is the safety valve and is metered.

**I3 — Per-session arena and flat AST.** Not built: AST nodes are owned by the tree the parser returns. Nothing here is a contract.

**I4 — Zero-copy tokenizing.**
Tokens reference the statement text in place (`include/kds/parser/token.hpp`); nothing is copied during lexing, and a token must not outlive its statement — the rule is structural (tokens never leave a parse), not enforced by a debug check. The one boundary where things outlive the parse (names entering the catalog, cached text) is the only place copies happen. The lexer tracks byte offsets so every error position — and every refusal position J2 requires — is exact. `.` is a token, so `a.x` lexes as a qualified name.

**I5 — Name resolution happens once, before execution.**
Relations resolve to oids and columns to ordinals; the executor never sees a name. A bound column reference is

```
ColumnRef { uint8 up; uint8 rel_slot; uint16 col_pos; }   // 4 bytes, no arena reference
```

`up` is a de Bruijn level — 0 is this chain, 1 its parent — so a predicate is independent of which chain it landed in, and it maps one-to-one onto the execute-time frame stack. Resolution rules: `a.x` names a relation or alias in this chain's FROM list or an enclosing one; an unqualified `x` resolves iff exactly one visible relation has that column, searching innermost-first and stopping at the first level that matches, so adding a column to an outer relation can never silently change an inner chain's meaning; anything else is `InvalidArgument` with the exact position. **Within one relation a name matches a column ignoring ASCII case, for reads and writes alike** (`Schema::FindColumn`, the one resolver; `instructions/v3.2.0/raft-marks-2026-10-15.md` §1): a read, a `SET` value's column read, a `SET` target, an `INSERT` column list, `DROP COLUMN` and `RENAME COLUMN`'s old name, the column `CREATE INDEX`, `CABIN`, `ASSERTION` or `TRANSITION` names, and a stored assertion canon re-parsed at mount. Column names are unique under that rule (`catalog.md` CT7), so a match is one column - and where a relation created before the rule holds two (`id` beside `ID`, or two exact `aa`), any statement naming them is `InvalidArgument` as ambiguous, naming every match, at the name's byte, never resolved to the first column; no statement can name either column of such a pair. A dropped column never matches. K2 is asked of the resolved column, not the written bytes, so `SET ID` on a tuple key `id` is refused `Unsupported`. The write paths' tuple-key fast paths (`NamesTupleKey`) decline an ambiguous name, so the compiler refuses it there too, and PURGE, which has no compiler, refuses it in its own conjunct check. Relation names are not covered by this rule. **Aliases (`FROM t AS a`) are in scope**, which is what makes a self-join expressible; a FROM list naming one relation twice without distinct aliases is `Unsupported`, not a silent ambiguity.

This lives in the **step compiler**, not the parser — `Compile(AST) → StepChain` resolves names against the catalog and emits `ColumnRef`s. A compiled `StepChain` contains no identifier on any execute path; execution performs zero catalog name lookups.

**I6 — The tuple key's id space is enforced where a key is named (invariant 11).**
A named `INSERT` key is checked against `[1, 2^48 − 1]` on its raw digit text rather than a signed decode, before anything is placed, and refused `OutOfRange` at the token's byte (BD-R5's "exhausted", `heap-and-tuple.md` §4.1); a bound parameter is the literal `C_BIND` substituted for it, judged the same way at execution. A `PURGE` window is clamped to the id space instead, and a tuple key literal in it that is negative or wraps past int64 is refused `InvalidArgument` (`heap-and-tuple.md` §4.1c). A probe key taken from a producing row needs no check — it came out of a Keystone word and is in range by construction.

**I18 — The error codes this language requires.**
`StatusCode::kUnsupported`, `kNotImplemented` and `kCardinalityViolation` exist (`include/kds/base/status.hpp`), each mapped to its own `wire::ErrorCategory` with `retryable = 0`; `kTxnConflict` remains the only retryable code. Every J2 form and every over-cardinality scalar returns its own code, never a generic `InvalidArgument`: a client cannot fix a cardinality violation by fixing its arguments.

## 4. Grammar surface

**I7 — `CREATE TABLE` options.** There is no `WITH (key = value, …)` option table; the storage form (`HEAP`/`BTREE`) is a trailing clause, `HEAP` asking for data pages found by key through a Keystone index, its Keystone a single `int64` `PRIMARY KEY` declared first or else a hidden column (`heap-and-tuple.md` §3.1b). **Waystone is not a table option**: it is keyed on `(fetch_id, arg_hash)`, not on a relation.

**I8 — Session and admin statements.** `SET DURABILITY {STRICT|GROUP|RELAXED}`, `SET ISOLATION LEVEL …`, `SHOW META`, `SHOW TABLES` and the other `SHOW` forms are *dispatcher* commands, not parser statements: ordinary statements returning ordinary result sets — one surface, one auth story. SET is excluded from fingerprinting.

**I9 — Join and nesting scope.**
§2's four subquery forms are in scope for predicate position, correlated included. Table-position nesting is out and answers `NotImplemented`.

The join surface: inner equi-join chains over 2+ relations (`JOIN … ON a.col = b.col`, chained and flat) with `AS` aliases; `ON` requires a qualified column (`rel.col`). `LEFT`/`RIGHT`/`FULL`/`OUTER` are lexed and reserved but rejected `NotImplemented` by the native grammar with the keyword's own position, so the grammar does not shift; since BU-S6 the query layer answers them (I19).

**I10 — Filter scope.** Conjunctions of `col op {value}`, `BETWEEN`, `IS [NOT] NULL`, the §2 subquery predicates, and — since AP-S4 — a comparison with a **scalar function call** on either side (`DATE(ts) = '2026-10-02'`, `ts < NOW()`, `IS [NOT] NULL` included). A call's arguments are column references; a literal argument, a nested call, `IN`/`BETWEEN` with a call on the left, and a call anywhere but a WHERE comparison - the select list, `ORDER BY`, `GROUP BY`, `HAVING`, a catalog view, and a `BETWEEN` bound - are refused `NotImplemented` at their byte by the native grammar (the query layer reads them, I19; an `INSERT` value is a SET value since BU-S8, I20). **A `SET` value is the one value position that is an expression since BJ** (`docs/spec/types.md` §3.2b): operators, `CASE`, `COALESCE`, `NULLIF`, `GREATEST`, `LEAST`, `CAST` and `::`, the comparisons and `AND`/`OR`/`NOT`/`IS [NOT] NULL` as bool values, the scalar functions of that section and a scalar subquery; `SET (a, b) = (x, y)` is two assignments. Its own refusals name their byte: `IN`, `BETWEEN`, `LIKE`, `EXISTS`, `IS TRUE`, a correlated subquery, a subquery over a catalog view. An unknown function's name is refused `InvalidArgument` at compile, as an unknown column is; an aggregate's name keeps the refusal it has always had in a predicate. A function conjunct is `PredicateKind::kCompareFunction` and lowers to a residual kind of its own, never a key (`include/kds/exec/step_chain.hpp`'s `FunctionPredicate`; the catalog and purity are `include/kds/exec/functions.hpp`, AR1 §2-§3). **`OR`, `NOT` and parentheses since BU-S1** (`instructions/v3.0.0/workorder-bu-basic-query-surface.md`): a WHERE is a boolean tree - `OR` loosest, then `AND`, then `NOT` - of which the top-level AND-list, parenthesized or not, is flattened into ordinary conjuncts, so a WHERE without `OR` or `NOT` lowers exactly as before. A group holding `OR` or `NOT` is one conjunct of kind `PredicateKind::kBoolTree` and lowers to a residual kind of its own, never a key (BU-R5; `step_chain.hpp`'s `BoolPredicate`): no tuple key bound, index range, Cabin probe, join key, build key, write lock window, point-write target or PURGE window is read off it, and equality propagation (I12) draws only from top-level conjuncts. Its leaves are the comparisons, column pairs, `IS [NOT] NULL`, `BETWEEN`, function comparisons and - **since BU-S3** - the §2 subquery predicates: each such leaf is a sub-chain of the step the conjunct is placed at, marked `in_tree` (`step_chain.hpp`'s `SubChain`) so every walk of the step tree sees it while no conjunct loop runs it alone; it is placed by §2's rule, never hoisted (a false uncorrelated `EXISTS` under `OR` must not empty the statement), its answer is a leaf of the tree in I16's three values, and a conjunct reading one is evaluated after the step's other conjuncts and sub-chains. `OR` over a catalog view is refused `NotImplemented` at its byte, and a tree deeper than 64 levels or larger than 4,096 conditions `Unsupported` (BU-Q2). Arbitrary expression operands - and a value function the native catalog does not hold, which the compile declines `NotImplemented` - are the query layer's (I19). **Since BU-S2** `IN (v, …)` is the disjunction of equalities and `NOT IN (v, …)` the conjunction of inequalities (one item: the plain comparison), `col NOT BETWEEN` is `NOT (col BETWEEN …)`, `col [NOT] LIKE 'p'` is a `CompareOp::kLike` comparison over `char`/`varchar` that travels only inside a boolean conjunct (bytes, `%` and `_`, case-sensitive, no `ESCAPE`; BU-Q6), and a literal on the left of a comparison is its mirror. A multi-item `IN`, `NOT BETWEEN` and `LIKE` are `kBoolTree` conjuncts and never a key, but for the one shape below; a `NOT IN` list is an AND of `!=` and, at the top of a WHERE, flattens into that many ordinary conjuncts, none of which keys anything. `IN (SELECT …)` is §2's. **One shape of boolean conjunct is a key since CU-S1** (`instructions/v3.2.0/workorder-cu-key-set-access.md`; BU-R5 amended for it alone): a conjunct whose root is an `OR` and whose every leaf is `<the step's tuple key> = <literal>` - what `id IN (v, …)` and a flat `id = a OR id = b` both lower to - gives its step a **key set** (`step_chain.hpp`'s `KeySet`), the leaves' values that the single-value descent would key on, ascending and distinct, served by that descent once per value. A leaf whose literal is NULL or negative names no key: it is left out of the set and stays a leaf, and a list with no key at all keeps its walk. The set is an annotation on `kLookup`, with no `Step::key`, and not a kind (CU-Q1), so `sys.access_stats` names the structure that served and no persisted number moves. Its step ranks directly below a single-value tuple key equality, which always wins, and above every other arm - a tuple key range, an index, a Cabin, a filter scan, a build - as a function of the shape alone; of two such conjuncts the first written is the set. It records and replays no trail (CU-Q4), a one-step statement on it is `kJoinSelect` (CU-Q6), the join cost model prices it as its values' descents, and `ANALYZE` prints `key_set=<n>` on its step line. **The conjunct stays in the step's residual** (CU-R1): every row a descent finds is tested against it, the leaf that named the row's value first and the rest of the tree in written order only where that leaf is not true (CU-Q9) - an `OR` with a true leaf is true, so this changes what is evaluated first and never an answer - and a set step therefore returns the rows the walk of the same list returns. **The same shape on another column is a key set since CU-S2**, on the structure's own single-value kind: on a column of a secondary index's equality prefix the step is `kIndexProbe` or `kIndexRange` and walks the index once per distinct value into one seen set (`index.md` IX8b, IX9); on a column that carries a column Cabin it is `kCabinProbe`, served from the union of its values' sets when every one is observed and walked otherwise (`cabin.md` §4e). A tuple key set outranks both. An index set is chosen with the literal index probe, under IX9's order, and only on a step no join key could enter (`index.md` §9); a Cabin set is the last of the Cabin arms and takes only a step that would otherwise walk its relation whole (`cabin.md` §4e) - so no statement leaves the structure that served it before lists were read except for an index a list reaches further into. Each keeps the list in the residual with the finding value's leaf asked first. Not the shape, and a residual only: an `OR` across columns or against another relation's column, one holding a leaf that is not `=`, one under `NOT` or under another `AND` or `OR` node (`id IN (1, 2) OR id = 3` is an `OR` holding an `OR`), and a list on a column that no index's usable prefix reaches and no column Cabin holds. **A write is by key set since CU-S3**: an `UPDATE` or a `DELETE` whose `WHERE` holds that conjunct on the tuple key writes by the point write's descent once per distinct value, ascending (`exec::WriteKeySetOf`, `CommandDispatcher::WriteWalk::WriteKeySet`). **Any conjunct may stand beside it since CU-S3b, as beside a single `<tuple key> = <literal>`** (`exec::WriteKeyOf`): `id = 1 AND v = 3` and `id IN (1, 2) AND v = 3` descend, a single equality ahead of a list, and the conjuncts beside the key are asked of the row each descent finds. Both targets are read off the compiled `WHERE` by the rule a read's step is keyed by. **A unique key named whole is a target too** (DR-S3a, DR-Q16): where neither stands and the `WHERE` pins every key column of a unique index - a primary key's `$pkey_<oid>` or any `CREATE UNIQUE INDEX`, the lowest `index_oid`, never one still building - by an equality with a literal, the statement descends once per tuple key that key's run names, ascending (`exec::WriteIndexKeyOf`, `exec::IndexRunTupleKeys`, `WriteWalk::WriteKeys`). The run is the superset every index run is (IX1), a prefix for a string key (IX6), and each row is asked the whole `WHERE`, so `a = 1 AND b = 2 AND v = 3` writes what its walk writes; a value the key encoder refuses passes the index over and the walk answers. **A bound on the tuple key, and an index the `WHERE` enters, are how a write finds its rows too** (DU, `instructions/v3.2.0/workorder-du-keyed-write.md`; `index.md` §9a). Below the three targets above, in the read ladder's own rank: **a tuple key window** - the one the statement's lock window is folded from (`txn.md` §5), a one-sided bound included, met with the ids an embedded primary key's conjuncts name - **bounds a btree's walk**, which seeks to the low key and ends at the first key at or past the high one (`WriteWalk::BoundBy`, `Visit`; `WalkBound`), and on a heap, whose pages are in no key order, is a range of the Keystone index; **an index entered by its equality prefix, by one value list standing as a prefix column, or by an inclusive range on the column after the prefix**, is the read ladder's own choice for the same conjuncts (`exec::WriteIndexArmOf`, over `IndexProbeOf`) - the tuple keys its entries name are collected before a row is written, made distinct and sorted, and each is written by the point arm, ascending (`CommandDispatcher::CollectWriteKeys`, `WriteWalk::WriteKeys`). A btree's tuple key range with both ends, neither strict, and an embedded key's window are taken before an index, as a read takes them; a one-sided or strict bound, and any bound on a heap, rank below one, and then drop the collected keys outside them. **A collection is a superset and decides no row** (IX1): every row is found at its slot, qualified on the whole `WHERE` and claimed by the walk's own row function, a row two entries name is written once, and a statement that moves the column it is found by never meets an entry it appended, the collection ending before its first write. **A statement's first collection is read to one entry past `max_locks_per_txn` and no further** (DU-Q2): past that nothing is written from it and the statement's walk answers. `indexes = off` takes the index arm and a heap's Keystone range away. **On a heap these arms write in key order, where the walk writes in page order** (DU-Q7, `known-gaps.md`): a statement whose rows are judged against each other as they stand - a unique key it shifts - can be answered by one order and refused by the other. A locking read takes every one of these arms (`txn.md` §5). **A descent that declines** - a damaged descent or an unreadable page, never a key's absence - hands a btree's statement to the walk from that key and a heap's to the walk from the head where no row was offered yet; after one was, a heap's statement is refused `TxnConflict`, its walk resuming by place and not by key - and a heap's walk that parked after taking a statement over resumes as the walk, never through a key arm, which would offer the rows it wrote again. **An embedded primary key is the tuple key's arms** (DR-S3e, `heap-and-tuple.md` §3.1c): on a btree whose key is its Keystone id, every key column pinned by an equality with a literal is a `Lookup` at the id the values encode to - a read's and a write's point arm alike (`exec::WriteKeyOf`) - and the leading columns pinned, with or without an inclusive range on the next, are a `Range` over the ids of every key that begins so (`EmbeddedKeyWindowOnStep`, below the Keystone's own arms and above every index and Cabin arm, under the tuple key's pin). The conjuncts stay in the residual; a value that does not encode, a one-sided bound and a join key leave the step to the ladder's other arms. **A `WHERE` holding a subquery, in a conjunct or under a boolean one, names no target**: a write evaluates no subquery under the leaf it holds exclusive, so that statement collects its rows in a read walk and writes them in a write walk, key or no key (`docs/pending/keyed-write-beside-a-subquery.md`). Each row a descent finds is qualified, claimed and written by the row function the walk runs, the whole `WHERE` asked of it with the finding value's leaf asked first (CU-R1, CU-Q9), so visibility, first-updater-wins, the foreign-key, unique-key, assertion and Transition checks and `RETURNING` are the walk's and the statement leaves what the walk of the same `WHERE` leaves. **The lock window does not move** (`txn.md` §5): a list declares no window and each row written takes its row unit - `U`, or `X` for a `DELETE` - in key order, the order the walk asks them in; a bound on the tuple key beside the list declares its window as it always did, and the descents then write under it with no row unit. A held row parks the statement at its value: the walk's resume position is a key and the values ascend, so the resume starts at the first value at or above it and no row is offered twice. A descent that declines hands the rest of the list to the walk, from that key on a btree and by the rule a unique key's descent follows on a heap (below). A value with no row is the tree's `NotFound`, and a list none of whose values is a key walks and writes nothing. The rest of BU-R5 stands for the shape: no join key, build key, write lock window or PURGE window is read off it - `PURGE` by list is refused `NotImplemented` - and a write finds its rows through no Cabin, for a list as for a single value (DU-Q0). A list on a relation a write only reads (`UPDATE ... FROM`, `DELETE ... USING`, a subquery, `INSERT ... SELECT`) is a read step and is keyed. A statement driven by a set is run inline, as one driven by a single descent is, and a set never yields (CU-Q8, `sched.md` §3): the cap on a conjunct bounds its descents, not what the rest of the chain does under each (`known-gaps.md`, "Key sets (CU)").

**I11 — `ORDER BY <col> [ASC|DESC] [, ...] LIMIT n [OFFSET m]`.** Limit and offset are values, so `LIMIT 10` and `LIMIT 20` share a `pattern_id` — corpus-pinned. A sort *column*, being an identifier, is part of the shape instead: `ORDER BY a` and `ORDER BY b` are different patterns. **Each clause is independently optional**: `LIMIT` without `ORDER BY` takes a prefix of the order the chain emits, which is no contract since CB-S2 (I12): it is some n rows of the reply, as in general SQL. Any column may be a sort key, tuple key or not, each with its own direction, up to **8 keys** (`parser::kMaxSortKeys`); tuple key order is the free order and the compiler **elides** the sort for `<driving tuple key> ASC` alone (over a key set too, I10, which descends for its values in ascending order), and **under a `LIMIT`, for `<driving tuple key> DESC` alone over a walk, a filter scan or a tuple key range of the driving relation**, which is then read from its high end down - a leaf a step, each step left a descent from the last leaf's `min_key`, so the LIMIT stops the read (CV O2, `instructions/v3.2.0/workorder-cv-ordered-index-walk.md`; `ANALYZE` prints `order=tuple_key_desc` on the step; a key set, a build or a Cabin arm keeps the sort, and so does every statement without a LIMIT, CV-Q2 (a)) - and, **under a `LIMIT`, for keys an index of the driving relation holds after the equality prefix the access ladder chose** (or over a step with no conjunct, from its first column), none a string, all ascending or all descending: the step walks that index in entry order, or from its high end down, and resolves as it goes (CV O1 and O3, `index.md` IX8c and IX9; `ANALYZE`'s `order=index_asc` or `order=index_desc`), ties by ascending tuple key as the sort's - by descending tuple key under `DESC` (I12) - every other order costing an output sort (`exec::OutputSort`, a sink decorator) bounded by `sort_max_rows` (default 1,048,576, `exec::kDefaultSortMaxRows`) — a sort that would exceed it fails the statement, and under `LIMIT` a top-N heap holds only what the reply needs. NULLs sort largest (`null.md` §4). `ORDER BY` by ordinal, alias or expression is the query layer's (I19). **The tail is the outermost non-aggregated block's**: over aggregated output `ORDER BY` is parsed and refused at the native compile, `LIMIT`/`OFFSET` refused at the native parse, each `NotImplemented` (fold order is not a contract — `aggregate.md` §2), and each the query layer's since BU-S5 (I19), and inside a subquery the whole tail is `NotImplemented` with the byte. Which relation a sort column belongs to is the compile half's check, not the parser's. `LIMIT`'s execution is a sink-decorator quota over `RowSink`'s `kStop` — `exec::EmissionQuota`. The defining contract: the reply to `LIMIT n OFFSET m` is rows [m, m+n) of the unlimited reply. That contract binds the *reply*, not the chain, so it holds over the one row source that is not a chain: a `sys.*` statement is answered by the catalog's typed readers before the compiler is asked for a chain, and the quota runs over its materialized rows after the `WHERE` and before the formatting — the same `EmissionQuota`, constructed from the clause rather than from a `StepChain`. `ORDER BY` over a `sys.*` view is refused with the byte: `exec::OutputSort` normalizes its keys out of a `ChainFrame` against `SortKey`s resolved to indices in a Schema, and a view has neither. A clause the engine cannot serve is refused, never parsed and silently dropped.

**I11a — `FOR UPDATE`, the locking clause** (DC, `instructions/v3.2.0/workorder-dc-select-for-update.md`). `SELECT <* or plain columns> FROM <one relation> [WHERE ...] FOR UPDATE`: the clause stands after the pagination tail of the outermost block and ends the statement, and the statement claims the rows it returns (`txn.md` §5, "A locking read"). `FOR` and every word after it are ordinary identifiers matched by text at clause position, so nothing is reserved, `for` and `update` stay column names, and no statement that parsed before the clause existed parses differently: the positions the production is entered at admitted only `)`, `;`, the end of the text and an `INSERT`'s `ON` or `RETURNING` (`Parser::ParseLockClause`, one production for both grammars). A locking statement's words are hashed as shape, so it is a `pattern_id` and a `fetch_id` of its own, and `kFingerprintVersion` did not move (the golden corpus pins both). **Every other spelling is refused by name** (`NotImplemented`): `FOR SHARE`, `FOR KEY SHARE` and `FOR NO KEY UPDATE` at the byte of `FOR` - `FOR SHARE` is never served by the lock table's `S`, which admits another writer's claim - and `OF <relation>`, `NOWAIT` and `SKIP LOCKED` at their own byte; a word that spells no strength is `InvalidArgument`. **The shapes refused at the byte of `FOR`** (`NotImplemented`, DC-Q5 (a)): a join, an aggregate or `GROUP BY`, `ORDER BY`, `LIMIT`, `OFFSET`, a clause inside a subquery, a derived table or an `INSERT`'s source, and every form only the query layer answers (I19), whose grammar reads no locking clause and refuses one by name rather than answer with it dropped; a `sys` view is `Unsupported`, having no row to claim. **No path that does not claim answers a locking statement**: `HandleSelect` hands a parsed one to the locking read before a catalog view, a chain or the query layer is asked, and `exec::Compile` refuses a statement carrying the clause, so `ANALYZE`, `WAYSTONE ON`, `CREATE PLAN` and `ADVISE PLAN` refuse it and no trail, plan or Cabin serves it. It is a write for authorization and for access mode: it needs `readwrite`, is refused `READ_ONLY_TRANSACTION` inside a `READ ONLY` transaction, and is refused `NotImplemented` in autocommit, where its claim would end with the statement. None of these refusals fails a transaction.

**I13 — Dialect compatibility is a non-goal.** No PG/MySQL emulation, no quoting mimicry, no shims. Compatibility requests are product decisions, not parser patches.

## 5. Execution contract

**I12 — The chain is the plan.**
**Since CX-S0 `join_order` says who may change the order of an inner-join block, and the default fixes it** (`instructions/v3.2.0/workorder-cx-managed-plans.md` CX-R1, CX-R7, CX-R10, on the operator's words of 2026-11-18). The key takes three values, set at boot and changed for the run by an admin's `SET JOIN_ORDER planned | fixed | written`, one value for the instance that every core's next compile reads; a restart reads the boot key again. **`fixed`, the default**: a block the search below would search is asked for its shape's **captured order** first - the key is the statement's fetch id, its relation count and every relation's oid in written order, compared whole, so it holds no literal and one capture serves every binding of the shape, and a relation dropped and created again under its name misses. A captured order is compiled through the full ladder after the written one, as a memo hit's is, so every refusal stays the written order's, each step's access arm is `f(shape, catalog)` again at every compile (a `CREATE INDEX` moves a captured shape's arm; nothing but an operator's act moves its order), and the compile pins no statistic. A shape with no captured order is searched as under `planned`, without the memo, and **its answer is captured once every relation of the block has a published prior** (`plan-stats.md` PS1); until then the search's answer runs uncaptured and the block is searched again at its next compile - the one change `fixed` admits, from an order priced blind to the first one priced whole. The table is the instance's (`exec::CapturedPlans`): the first install wins and every core runs it. **A capture outlives the run since CX-S1a** (superblock 37, `exec/plan_catalog.hpp`): the compile installs it in memory and queues it, and core 0's `system` task writes the queue to **`sys.plans`** once a second - one logged row a shape, holding the fetch id and the fingerprint version it was taken under, every relation oid, the order, when it was written and the capturing statement's text with each literal written `?` - so the statement itself writes nothing, a `READ ONLY` transaction's first compile included; a clean shutdown writes what is still queued, and a mount installs every row before a statement compiles, after a crash and after a restore too, so a captured shape is not searched again; it keeps one row a shape, removing a second row for a key it has loaded, a row of another fingerprint version and a row naming a relation that is gone. A capture a crash finds still queued - or written and not yet synced with the log, which the step does not sync on its own - is lost and made again at the shape's next compile. No row moves the schema version word. **`DROP PLAN <name>`** (admin, autocommit only) removes a row and forgets its shape, whose next compile captures again from the statistics of that moment - the one way a captured order is re-armed; a committed `DROP TABLE` forgets every shape naming the relation, and the task - or the next mount - removes their rows. The table holds at most 65,536 shapes, evicts none, and a new shape past that runs its written order. A block no key fits - no fetch id, or more than 16 relations - runs its written order. **A captured order is declined for a statement, which then runs its written order, in two cases**: it does not compile for it, or it adds a sort the written order does not have and the statement's `LIMIT` does not bound to a top-N heap `sort_max_rows` covers (CC-Q10's rule, asked of every binding because `LIMIT` is a literal and outside the key) - so a captured order never refuses a statement its written order answers. **Under a minted view (a DDL open anywhere in the instance) no capture is made and a held one is still run**: an order priced against a catalog state that may roll back is not fixed, and a captured one was fixed outside any view for these exact oids, so one open DDL does not let every captured shape follow the statistics. A tuple key chain leaves the compile before the table is asked, as before the statistics. Leaving `fixed` keeps the captured orders, unread; coming back reads them again. **`planned`** is the search at every compile, as the rest of this paragraph describes it. **`written`** keeps the written order. `ANALYZE` prints `order=captured` for a captured order (no estimate: none was read), `capture=first` on the search whose answer was captured, `capture=deferred` on one whose answer was not (a relation without a prior, or a DDL open), and `order=written capture=unkeyed|over_ceiling|declined` for a block that ran as written without a search; `SHOW META`'s `join_order` block carries the value in force and the table's counts, and `sys.plans` (`SHOW PLANS`) the rows. A dispatcher built with no instance behind it - every suite's rig - runs `planned`.
**Since CX-S1b an administrator's plan is the first source of a block's order, under every value of `join_order`** (CX-R1, CX-R9; `exec/admin_plans.hpp`, `exec/plan_ddl.hpp`, `exec/plan_rule.hpp`). `CREATE PLAN <name> FOR <select> VARIANT <v> WHEN <rule> ORDER (<relation>, ...) ... VARIANT <w> ELSE ORDER (<relation>, ...)` (admin, autocommit only, answered once durable) attaches a plan to the statement's shape - the captured plans' exact key - as a logged `sys.plans` row of origin `admin`, and from then on every compile of the shape asks the instance's one table of them first: an enabled plan outranks the shape's captured order, the search and the written order, and nothing but `ALTER PLAN` or `DROP PLAN` changes it. **A plan is variants**: each a join order, named by the statement's bindings (the alias where one was written, the table's name otherwise), and all but the last a rule over the statement's **arguments** - `ARG(k)`, its k-th value position in token order, however the value arrived (written, or substituted at `C_BIND`). The first variant whose rule holds is the statement's, chosen at every compile and never remembered; the last is `ELSE`, which is mandatory, so every statement of the shape has one. **A rule is total and reads arguments alone**: comparisons (`=`, `!=`, `<`, `<=`, `>`, `>=`) joined by `AND`, over sums (`+`, `-`) of `ARG(k)` and integers in 64-bit arithmetic checked for overflow, and `=`/`!=` between an argument and a string by its bytes; a comparison that cannot be decided - an argument of the other type, an integer past 64 bits, an overflow - is false, never an error, and each comparison must read an argument. `OR` and ordering strings are `NotImplemented`; **`IS NULL` is `Unsupported`**, because NULL is shape to the fingerprint, so a statement with a NULL in a value position is another shape with a plan of its own and no argument of a matching statement is NULL. **What a variant holds is an order and, since CX-S3a, at most one pin a relation** (the next paragraph): each step's arm is the ladder's again at every compile, so a variant cannot force an arm (CX-R2), and one whose order does not compile for a statement or adds a sort its `LIMIT` does not bound (CC-Q10) is **declined for that statement**, which runs its written order, counted (`plan_declined`) and named by `ANALYZE`; the plan stays as it is. **`CREATE PLAN` is by example, with literals** - a `?` is refused `NotImplemented`, as `WAYSTONE ON` refuses one - and every variant's order is compiled for the statement as written before the row is made; the row keeps the shape text and no literal. It is refused for a join the join planner does not order (a joined `SELECT *`, a subquery predicate: `NotImplemented`), for a one-relation statement with a subquery predicate (`NotImplemented`) or written `AS SEARCHED` (`Unsupported`: it has no order to search), for a name beginning `captured_`, for a shape that already has an administrator's plan and for a name that is taken (`AlreadyExists`). **`CREATE PLAN <name> FOR <select> AS SEARCHED`** (CX-Q28 (a), CX-R11) runs the search once with the statistics of that moment, whatever `join_order` is and with no memo or captured order between, and stores its order as a plan of one variant, so a shape that is not captured - deferred, unkeyed, over the ceiling, or under `planned` or `written` - can always be fixed by hand. **Unlike the captured table, a block of tuple key descents is asked too** while any plan is enabled (one relaxed load answers "none is"): a plan made and then not applied would enforce nothing of what was written. A statement over one relation reaches the table only while a one-relation plan is enabled (a second relaxed load, `any_single()`), and then every top-level one-relation `SELECT` with a fetch id does, a point read included. **`ALTER PLAN <name> DISABLE`** keeps the row and serves it to no statement - the shape goes to its captured order, the search or the written order - and **`ENABLE`** serves it again; **`ALTER PLAN <name> REPLACE VARIANT <v> (WHEN <rule> | ELSE) ORDER (...)`** replaces one variant's rule or order, an `ELSE` by an `ELSE` and a `WHEN` by a `WHEN`, checked against the plan's bindings and argument count and **not compiled** (the row holds no literal to compile with), so an order that does not fit a statement is declined at that statement's compile. Each change is the plan's row written again under a new id and the old row removed; a mount keeps the newest row of a name. `DROP PLAN` of an administrator's plan leaves the shape to the captured order beneath it, never to a fresh search where one is held (CX-Q17). The three statements take one claim for the instance and never wait for it: a second plan DDL meanwhile is refused `TxnConflict`. **An enabled plan RESTRICTs `DROP TABLE` of every relation it names** (CX-Q24 (a), `drop-table.md` DT3); a disabled one does not, and a plan whose relation is gone - or whose fetch id was taken under another fingerprint version - reads `invalid`, serves nothing, refuses `ALTER PLAN` (`Unsupported`) and stays until its `DROP PLAN`: the engine does not delete an administrator's object. **A plan a rename put out of reach reads `invalid` too, and restricts no drop** (DI-S4, `exec::PlanRowCanMatch`): a plan's key is its statement's fetch id - a hash of the text - and its relations' oids, a rename keeps the oids and changes the spelling that reaches them, so the old text no longer resolves and the new one is another fetch id. Established from the row alone - the name each reference of the stored statement spells against the current name of the oid recorded at its position, and each column written `binding.column` against that relation's columns - and for a captured order as for an administrator's. Nothing is written at the rename and nothing is removed: a rename back puts the plan in force again, RESTRICT included. What is not established - a column written unqualified - reads as it did. **A rename orphans a plan without marking it**: a fetch id hashes the statement's names, so after `ALTER TABLE ... RENAME` no statement written with the new names matches the plan, which still reads `enabled`, still serves a statement written with the old names were one to resolve, and still RESTRICTs the renamed relation's drop until its `DROP PLAN` or `DISABLE` (CX-Q24 (a)'s rule for a captured row, here with the RESTRICT kept). A plan-served block names its relations and its key to the statistics as a searched one does, so its runs' counts are folded under every value but `written`. `ANALYZE` prints `planned order=plan plan=<name>/<variant>`, or `order=written plan=<name>/<variant> plan_declined=1`; `sys.statement_stats` carries `plan_source`, `plan_name` and `variant` for the shape's latest compile; `SHOW META`'s `join_order` block counts the plans, the enabled ones, the compiles that found one and the declines.
**Since CX-S3a a variant may pin one access arm a relation** (CX-R2, CX-Q4 (a); `exec/admin_plans.hpp` `ArmPin`): after its `ORDER`, `ACCESS <binding> <pin> {, <binding> <pin>}` with a pin `TUPLE_KEY`, `INDEX [<index name>]`, `CABIN [(<column>)]` or `SCAN`, or `NOT` before one of the first three. **A pin restricts the ladder and never replaces it**: the classes are the ladder's own ranks - the tuple key (a lookup, a probe, a key set, a range), a secondary index (the named one, or any), a Cabin (every Cabin arm), the walk (a filter scan or a bare scan, with or without the statement-local build) - and each rank is tried, by its own rule, only where the pin admits its class, so a pinned step runs an arm the ladder could legally take for it and every located row still meets the whole residual. A pin naming a class is met only by an arm of it (and a named index only by that index); `NOT` leaves the ladder whatever else it has, and the walk is always left, which is why `NOT SCAN` is refused. Under a pin naming a keyed class the walk's own ranks - the filter scan and the build annotation - stand aside, so a strict tuple key range, which the ladder ranks below them, is still the tuple key class's to take. A rank a pin rules out is ruled out with its consequences: where `NOT TUPLE_KEY` or `CABIN` takes a strict range away, a value list on a cabined column is served as a Cabin set, which the unpinned ladder would have left to the range (CU-Q12) - the same rows, by the arm the administrator asked for. **A pin no arm meets is never forced**: at `CREATE PLAN` it refuses the statement (`InvalidArgument`, naming the relation and the pin), and at a later compile - an index dropped while the plan was disabled, a binding whose literal names no key - the variant is declined for that statement, which runs its written order with the ladder unrestricted. `ALTER PLAN ... REPLACE VARIANT` takes the clause too, compiles nothing, and checks one thing of a pin it can ask with no statement: that a named index exists on its relation (`NotFound`). **An enabled plan RESTRICTs `DROP INDEX` of an index one of its variants pins by name** (`index.md` §10), asked under the relation `X`; `REINDEX` keeps the name and is not restricted, and a Cabin's drop is not restricted either - a `CABIN` pin names no Cabin, so a dropped one leaves the pin unmet and the variant declined. `ANALYZE` marks a pinned step `arm=plan`; a step with no mark took the ladder's own choice. `sys.plans`' `variants` shows the clause.

**Since CX-S3b a controller-made Cabin reaches the ladder only through a plan that names it, and a statement over one relation takes a plan** (CX-Q6 (a), CX-Q4 (a); `step_compiler.cpp` `CabinGate`). A Cabin of `auto` origin - one the cabin optimizer made (`cabin-controller.md`) - is tried by no Cabin rank of a step with no pin, and by none under `CABIN` unnamed or `NOT` another class, under every `join_order` and in a subquery of a write as in a read (a write's own `WHERE` takes no Cabin arm): the ladder reads the relation as though that Cabin were not there, so switching the controller on moves no step's arm. **`ACCESS <binding> CABIN (<column>)` names the column Cabin on that column** and admits it whoever made it - and nothing else, so the pin is met only by that Cabin's arm: its literal probe, its correlated probe or its value set. `NOT CABIN` takes no name (`InvalidArgument`), an expression or predicate Cabin cannot be named (`NotImplemented`: the controller makes column Cabins alone), and a name the relation does not carry a Cabin on is the unmet pin above - refused at `CREATE PLAN`, declined at a compile, `NotFound` at `REPLACE VARIANT`. The name is the column's as written: after a `RENAME COLUMN` the pin names nothing and the RESTRICT below no longer finds the Cabin, while the plan, whose statement names the old column, matches no statement (a fetch id hashes names). **An enabled plan RESTRICTs the drop of a Cabin one of its variants names**: `DROP CABIN ON t(<column>)` is refused naming the plan, and the cabin optimizer's own DROP of it is skipped and counted (`sys.meta` `cabin_optimizer_drops_restricted`), a budget swap that chose it as its victim building nothing; a column Cabin's drop holds no relation lock, so a plan made while one runs has its variant declined instead (CX-Q4 (b)). **A statement over one relation has no order and an arm**: `CREATE PLAN <name> FOR <select over one relation> VARIANT ... ORDER (<the relation>) [ACCESS ...]`, its variants chosen by the same rules; the compile compiles the statement unpinned, then under the variant's pin, and declines the pin where no arm meets it or the pinned arm adds a sort the `LIMIT` does not bound. A one-relation block with a subquery predicate takes no plan, as a join with one takes no order.
**Since DU-S3 an `UPDATE` or a `DELETE` takes a plan for its arm** (DU-Q4 (a); `CommandDispatcher::WritePlanFor`, `WritePlanRow`, `WriteWalk::BoundBy`). `CREATE PLAN <name> FOR <update | delete> VARIANT ... ORDER (<the relation>) [ACCESS <the relation> <pin>]` is a one-relation statement's plan, keyed by the write's own fetch id and its relation's oid: its variants' rules read the write's arguments (`ARG(k)` counts the `SET` list's literals too, in written order), one plan holds a shape, `ALTER PLAN` and `DROP PLAN` are a `SELECT`'s, an enabled plan RESTRICTs the relation's `DROP TABLE` and a pinned index's `DROP INDEX`, and a rename of the relation or of a column the statement writes by its binding makes the plan `invalid` (DI). A run asks for the plan where a one-relation plan is enabled (`AdminPlans::any_single`) and settles the variant's pin before a row is read. **The classes are the read ladder's, by the kinds a read's steps are** (`ArmClassOf`): `TUPLE_KEY` admits a key, a list and a btree's bounded walk; `INDEX [<name>]` a unique key named whole, an index the `WHERE` enters and a heap's Keystone range; `SCAN` holds the write to its walk, whole; `NOT <class>` leaves the others. A pin restricts the arms by their own rules and never forces one: a variant whose class no arm of the statement is of is declined for that statement, counted (`plan_declined`), and the statement runs unpinned. Refused at `CREATE PLAN`, each at its byte: a variant the example cannot run, an index the relation does not have, `BUILD` (a write has no join) and `CABIN` (a write reads through none) - which `REPLACE VARIANT` refuses too - `AS SEARCHED`, a `WHERE` holding a subquery (it walks whatever a plan says), and the example's own refusals, its `SET` list's among them; a subquery in a `SET` value is `NotImplemented` there, nothing running it. `ADVISE PLAN` takes a `SELECT` alone, a locking read takes no plan (I11a), and a write through a view is refused as every write through one is. **`ANALYZE UPDATE` and `ANALYZE DELETE` run the write and answer with how it found its rows** (DU-S3): the prefix comes off above everything that reads a statement's first word, so the statement is authorized, refused in a `READ ONLY` transaction, parked and resumed as the write it is, and its reply is `analyze rows=<n> class=Update|Delete`, then `write <kind> <relation>` under the name a read's step of that kind prints - `Lookup` (`key_set=<n>` for a list), `Range range=[lo, hi]` (`range=empty` for a window no key is in), `IndexProbe` or `IndexRange` with `index=<name>`, `key_set=<n>` and `keys=<n>`, the rows it then descended for, `Scan` - with ` past_cap=<index>` for a collection DU-Q2's bound declined and ` arm=plan` under a pin, then `planned plan=<name>/<variant>` and ` plan_declined=1` where its plan was asked. **A write has no compiled chain, so the line names the arm that ran**: under `indexes = off` it prints `Scan` where a read's step would still print `IndexProbe`. `RETURNING` under the prefix is refused `NotImplemented` before a row is written, a byte a refusal names is counted from the write's first word - as an analyzed `SELECT`'s is from its `SELECT` - and `ANALYZE DELETE STATISTICS` keeps its own refusal.

**Since CX-S5 a variant may pin a relation's join method** (`exec/admin_plans.hpp` `ArmPin::Build`; `join-inner-build.md`): after `ORDER` and any `ACCESS`, `BUILD <binding> ON | OFF {, <binding> ON | OFF}`, one a relation. **`OFF` takes the statement-local build's rank from the step's ladder**, so a walked join walks the inner relation per outer row, or takes the strict tuple key range ranked below the build. **`ON` holds the step to the build**: every keyed class stands aside, as under `ACCESS ... SCAN`, and the pin is met only where the step then carries the build annotation - the build's own rule (`BuildKeyOf`: one non-tuple-key correlated equality of one descriptor, nothing else read from another relation, no function or boolean conjunct) and the filter scan's rank above it are unchanged, so a join entered by the inner relation's tuple key, the first step and a step with an unindexed literal equality cannot meet it. Unmet, it is the unmet pin of CX-S3a: refused at `CREATE PLAN`, declined at a compile. `ON` beside an `ACCESS` pin naming a keyed class is refused at `CREATE PLAN` and `REPLACE VARIANT` (`InvalidArgument`); beside `NOT` a class or `SCAN` it is consistent. **A met `ON` builds subject to `join_build_max_rows` at run time**, as every build does: a cap of `0`, or a map that outgrows it, walks per outer row (CX-Q8 (a), a resource limit and not a plan change), and `ANALYZE`'s `inner_built=0` says so. A captured order still carries no build pin (CX-Q12 (a)): its build side is the compile's given its order. A step pinned only by `BUILD` is marked `arm=plan` too. `sys.plans`' `variants` shows the clause after `ACCESS`; the row carries it as ` build=<w>:ON|OFF;...`, so a row written before CX-S5 reads as it did.
**Since CX-S7 the search is an advisor too** (CX-R5, CX-Q29..Q33; `exec/plan_advice.hpp`): `ADVISE PLAN FOR <select>` - admin's, by example with literals as `CREATE PLAN` is (a `?` refused `NotImplemented`) - runs the join order search once for the statement, with the statistics of that moment, whatever `join_order` is and with no memo, captured order or administrator's plan between it and its answer, and **applies nothing**: it captures nothing, memoises nothing, moves no plan counter and writes no log. It prices the answer against **the plan in force**: the order and pins this statement's next compile would run - an enabled administrator's plan's variant chosen for its literals, else under `fixed` the shape's captured order, else under `written` the written order - compiled through the ladder under the search's own cost inputs; a plan in force that would be declined for the statement is priced as the written order it would fall back to. Under `planned`, and under `fixed` for a shape not yet captured while the captured table has room, the next compile runs the search's answer, so the ratio is 1 (`in_force` `searched` and `uncaptured`); past the table's ceiling a new shape runs as written (CX-Q21), and that is its plan in force. The reply is `ADVISED PLAN fetch_id=... in_force=<written | captured | uncaptured | searched | admin:<plan>/<variant>> searched=<0|1> cost_ratio=<proposal over plan in force, 3 decimals> generation=<the statistics generation read> order=(...) [why=<reason>] [plan=CREATE PLAN advised_<fetch id> FOR <the statement as written> VARIANT advised ELSE ORDER (...)]`, the plan text issuable as it stands where no administrator's plan, enabled or not, holds the shape (one plan a shape: `CREATE PLAN` refuses a second `AlreadyExists`). A statement over one relation is refused `Unsupported` (no order); a join the search never orders - tuple key descents alone, a subquery predicate - is advised its written order, `searched=0`, at a ratio of 1 that prices nothing (an administrator's plan in force for a descent chain included), with `why=` saying so; a subquery predicate's block, which `CREATE PLAN` refuses `NotImplemented`, gets the reason and no plan text, and its `sys.plan_advice` proposal is NULL, so the engine never proposes a plan it refuses; a joined `SELECT *` is refused by the parser before either. The proposal is an order alone: it carries no `ACCESS` or `BUILD` pin, the search deciding neither. **`sys.plan_advice`** holds the latest advice a shape, memory only and emptied by a restart, bounded at 1,024 shapes `[provisional]` with the oldest dropped past it (CX-Q30 (a)), its proposal over the shape text with literals `?` (CX-Q31 (a)); no compile reads it.
**Since CB-S2 the order of an inner-join block's relations is the join planner's** (`instructions/v3.2.0/workorder-cb-join-planner.md` §3.2, on the operator's word of 2026-10-18): a top-level block of two or more relations with no subquery predicate and not `SELECT *` is compiled in every order of its relations up to four (greedily above), and the chain `exec::EstimateChain` (`include/kds/exec/join_order.hpp`) prices cheapest runs if it beats the written order by the margin (CC-Q8; the first cheapest in permutation order among equals). Since CC-S1 the cost reads the compiled chain - kinds, literals with a range's span as its half-octave band, build annotations, its sort and its LIMIT - the catalog's identifier bounds (a unique index whose every key column is bound holds one row; a Transition's state count raises an equality's selectivity, never lowers it) and the statement's `join_build_max_rows` and `sort_max_rows`; an order that adds a sort the written order elides is never taken unless LIMIT bounds it to a top-N heap (CC-Q10). **Since CC-S3 it also reads the join planner's statistics** (`docs/spec/plan-stats.md`): a relation's prior rows replace the constant, a block's observed join-subset cardinalities `card(T)` replace the product of selectivities for the prefixes a run measured, a decline fact prices that build as the walk, a build is priced only under a quarter of `join_build_max_rows`, and an order must beat the written one by 10 % once any fact enters. The plan is `f(shape, catalog, statistics generation, span bands, statement limits)` under `planned`, and `f(shape, catalog, captured order)` for a captured shape under `fixed`; the access ladder stays `f(shape, catalog)` given each step's predecessors. The literals are inputs too: a range's span, a LIMIT, a tuple key literal's validity. **Since CC-S4 each core remembers a searched block's order** under `planned`, under exactly those inputs, its literals included (`plan-stats.md` PS6), so a statement repeated with the same literals compiles two orders, not up to 24. A step's `step_id` is its relation's **written** position (CB-Q3), and `ANALYZE` prints `reordered=1` when the order moved. `join_order = written` keeps the written order. **Without `ORDER BY`, emission order is not a contract** (CB-Q1): the paragraphs below that speak of written order describe the chain as compiled, whichever order that is. Everything else in this section stands. Execution order is the chain's order: the chain runs front to back, nested-looping into each subsequent step. A *documented client contract* — deterministic, predictable, appliance-appropriate — not a limitation to apologize for. An uncorrelated sub-chain is hoisted and runs once before the outer chain; a correlated one runs per outer row, where it is written.

**Decorrelation rewrites are forbidden**, not merely unimplemented: turning a correlated subquery into a semi-join, or hoisting its inner side into a read the written order never scheduled, is exactly the silent reordering this contract rules out, and it is not validatable against the trail model. What it forbids is the *hoist* — reading the inner relation before written order reaches it. The statement-local inner build (sanctioned below) hashes inside the very walk written order schedules, which is why it is not this rewrite. The one permitted plan-level shortcut, because it changes no result and no order: a false uncorrelated top-level `EXISTS` short-circuits the statement without opening the outer relation.

**`ORDER BY` is the one sanctioned reordering, and it refines this contract rather than replacing it.** A sort is a sink decorator: the chain still runs front to back and still emits in the chain's order, and the reordering happens strictly downstream of every step, every trail entry and every access count. Arrival order is the sort's last key and always ascending, so **rows the clause does not distinguish come back in the order this contract gives them** — a client that orders by a column with ties sees the chain's order within each tie - the planner's, for a planned block. **Under an elided descending order the chain's order is the walk's** (CV-Q4 (a), adopted on the operator's standing go-ahead of 2026-11-20): an `ORDER BY <index keys> DESC` the reverse ordered index walk serves (I11, `index.md` IX8c) returns its ties by **descending** tuple key, where a sort over the same rows returns them ascending; write the tuple key last (`ORDER BY created_at DESC, id DESC`) for an order that is total either way. What a sort does *not* do is license the engine to reorder anything the statement did not ask to reorder; the prohibition above is unchanged. The contract is stated in the client manual, and execution order provably matches written order for both orderings of one query.

**Equality propagation is the one sanctioned predicate rewrite, and it adds conjuncts, never removes, rewrites or reorders one.** From `A = B` — two columns of one chain — and `B = <literal>`, the compiler appends the implied `A = <literal>` to the flat conjunct list before attachment, so the step owning `A` can be *keyed* on it: a join whose restriction is written against the other relation stops compiling the keyed side to a full walk per outer row. Its constraints, each load-bearing:

- **Results are unchanged by transitivity.** Joins are inner-only (I9), and a NULL in `A` or `B` makes a written conjunct unknown, which drops the row whatever the derived one says; the derived conjunct is *appended*, so the residual still carries every written conjunct and any step downgraded to a scan filters to identical rows.
- **Plans may only be strengthened.** Derived conjuncts sit after every written one, and the tuple-key-equality choice takes the first usable equality in residual order — so a written key is never displaced by a derived one. A derived conjunct *can* do more than fill a scan: it may promote a written `kRange` to a `kLookup` (a strictly stronger trust class under invariant 9), change which secondary index a step enters, reach a `CabinProbe`, or flip a statement's class to `kPointSelect` when it proves the driving step a point. Every one of those is a stronger access to the same rows; none weakens one.
- **At most one conjunct is derived per column**, and only for a column carrying no written equality-to-literal of its own — the first descriptor-matching literal in its class, in written order. A second literal on one column is plan-inert (a keyed candidate already exists) and result-inert (the written conjuncts fully express the predicate, contradiction included); without the bound, a class of *M* columns carrying *L* literals appends `L·(M−1)` conjuncts, which is a compile-time and per-row blowup an adversarial statement can drive to seconds.
- **Still `f(shape, catalog)`.** First-seen order everywhere, no data consulted; `docs/spec/index.md` §9's purity claim is unchanged.
- **The literal crosses only an identical type descriptor** (`type_val` and `len` both equal): it was coerced against the column it was written on and is copied bytes-for-bytes — re-coercing a coerced decimal would rescale it twice. A mixed-descriptor join key keeps its unpropagated plan.
- **`$param` propagates**, for the reason the lookup path treats one as tuple-key-eligible.
- **Derived conjuncts are marked** (`StepPredicate::derived`): `ANALYZE` prints `derived` on their filter lines — a diagnostic must name a predicate the client can find in their text, and the derived occurrence's verdict is never different, since the descriptor guard makes both columns the same type.

**Range bounds cross the same classes since CB-S1** (`instructions/v3.2.0/workorder-cb-join-planner.md` §3.1, on the operator's word of 2026-10-18): from `A = B` and `B > <literal>` (`>=`, `<`, `<=` alike, `BETWEEN` as its two ends) the compiler appends `A > <literal>`, at most one lower and one upper bound per column, the first written in each direction, under the same descriptor guard, the same `derived` mark and the same appended-never-replacing rule - so results are unchanged for the reason they are above. A column holding an equality-to-literal, written or derived, derives no bound (the equality is the stronger conjunct), and a column with a written bound in a direction derives none in it. A derived bound can make a step a `kRange` or a `kIndexRange`, and narrows what a walked join's build buckets; on a column its step already keys per outer row (the own side of a correlated equality) it filters only, and never picks the index range, predicate Cabin or cover arm over the correlated probe, whose descent to the matches the range could only widen. Out of scope by decision: deriving column-column conjuncts (placement already keys on the earliest available side). What this rewrite deliberately does not touch is order: the chain still runs front to back in written order, and the written order still decides which relation drives — propagation makes both writings of a restricted join fast, it does not choose between them.

**The rewrite inventory (CX-S2)** (`instructions/v3.2.0/workorder-cx-managed-plans.md` CX-S2, CX-Q9 (a)): everything the compile and the executor do to a native `SELECT`'s chain beyond choosing each step's arm (the ladder) and the block's order (CX-R1's three sources), classed by what decides it - with the ladder's two locate structures that are more than a descent, the key set and the inner build, listed beside the rest. A statement the query layer answers (I19) compiles no join block and is outside it. **Every compile-time item below is decided by the statement's text, the catalog's DDL state and the order the block runs in, and every run-time item by those, the run's own rows, a boot limit or (Waystone alone) the trails earlier runs recorded - none reads a statistic, the memo, a captured or administrator's plan, `join_order` or load, and the clock reaches only `NOW()`'s value, never a step** - and structurally so: the compile-time items are in `CompileBound` (a literal on the left is mirrored before it, by the parser, and `NOW()` is read into the statement's context before it), which every path of `CompileBlock` calls and which is handed no `PlanOptions`, and the run-time items read the chain it produced, never the options. So for one order the chain is the same under `written`, `fixed` and `planned` and whoever chose the order, and no item here moves a plan on its own.

**Class (b) - a rewrite that reschedules reads by the engine's choice - has no member and is never automatic**: no subquery is unnested or turned into a semi-join, no inner side is hoisted into a read the order did not schedule (the prohibition below), no conjunct a statement wrote is dropped, no contradiction skips a relation (a negative tuple key literal, an inverted range and a key set with no valid key each keep their walk), and no `DISTINCT` or `LIMIT` is pushed below a join. Such a rewrite may exist only as an option of an administrator's plan, once a scenario statement is named as its consumer (CX-Q9 (a)); none is built. A block with a subquery predicate is never reordered, and a subquery's own block is compiled with no plan, so the hoist and the sub-chain placement only ever run in written order.

**The statement-local inner build is the one sanctioned execution-time structure, and it adds a way to *locate* an inner match set, never a reorder of a row or a read** (`docs/spec/join-inner-build.md`). When a join's inner step would walk per outer row — no index, no Cabin, no literal to propagate — the executor lets the first outer row's inner walk double as the build of a statement-lifetime map from join-column values to matching rows, and every later outer row probes the map instead of walking. Three facts keep it inside I12, each load-bearing:

- **The outer relation still drives.** The build changes how a match set is located, never which relation iterates or what joins what — the claim IX17 and CB12 already ratified for correlated probes, applied to a structure whose lifetime is one statement.
- **Read scheduling is unchanged.** The inner relation is first read exactly when written order reads it: the build is that walk's side effect, the Recording pattern `docs/spec/cabin.md` §4 ratified.
- **Emission order is captured, not reconstructed.** Buckets append in walk order, so a probe replays each key's matches in the order the walk would have emitted them — for a named key and an issued one alike, since build order *is* the walk's order.

Hard rules ratified with it: never the outer side, never an emission reorder, never survives the statement, never feeds Waystone. **Which relation is the inner side is the join planner's since CB-S2**: the build still hashes the inner step of the chain, and the planner puts the relation whose build the model prices cheapest there (W0's "choose the smaller side"). What the prohibition above still forbids is the hoist — building before written order first reads the inner side — which is the semi-join/hash-join rewrite and is not what this paragraph licenses.

**I15 — Nested access rules.**
A nested sub-chain step and a join probe both perform storage access *inside* an outer walk's callback, and the buffer pool evicts (`docs/spec/eviction.md`), so a span into a page frame does not survive a nested fetch.

- **R1 — decode before descending.** At every step, the row is decoded into that step's owning frame buffer before any nested access. No span into a page frame — a tuple payload, or a descent's carried-out leaf — may be live across a call that can fetch another page.
- **R2 — nested steps are read-only.** Every nested walk uses read access, enforced structurally: the nested driver has no parameter for it, which stops a read-only statement from dirtying frames. Read access alone does not keep a write's subquery off the write's own rows: a sub-chain re-runs per row (uncorrelated ones included, on the write path) and would read the rows the statement has already written. So **an `UPDATE` or `DELETE` whose `WHERE` holds a subquery collects its targets first**, whatever relation the subquery reads: a read walk evaluates the `WHERE` over every row and writes nothing, then the write walk writes exactly the collected tuple keys without evaluating the `WHERE` again. The second reason is the page latch's: a subquery evaluated in the write walk reads pages under the walk's exclusive leaf, and two such statements on two cores close a cycle of latch waits that nothing breaks (`docs/rules/rules.md` §3's page latch row). The targets ride `WalkCursor`, so a statement resumed after a park writes the same set; one re-run whole collects afresh under its new snapshot. The set is one key per matched row and is not capped, as the transaction's trail, which the same rows grow, is not. A point write by tuple key has no other conjunct, so it carries no subquery; a statement that collects nothing writes nothing and takes no leaf exclusive.
- **R3 — recursion is bounded**, at compile *and* at execute: the §2 depth cap is `parser::kMaxSubqueryDepth`, refused at each end. The chain-hop budget is a corruption guard, not a plan guard; the plan guard is §7's row-touch budget.
- **R4 — a walk must be stoppable.** `ChainVisit`/`BtreeVisit` callbacks return an outcome, and "stop" ends the walk successfully — `Exists` ("stop at the first qualifying row"), `LIMIT` and every cost guard depend on it. **"Stop" is never encoded as a `Status`**: control flow through the error channel makes "did it fail or did it finish?" unanswerable at the call site. A client's `C_CANCEL` is not a stop — it is `kCancelled`, a failure, taken only at a walking `SELECT`'s slice boundary (`protocol.md` §10, BA-S15).

A stopping visitor touches no page beyond the one it stopped on.

**I16 — NULL and cardinality.**
NULL is storable (`docs/spec/null.md`), and comparison is three-valued. The evaluator computes a tri-state and **collapses it to a boolean in exactly one place** — UNKNOWN becomes false at the root of each conjunct (`null.md` §4: `WHERE` keeps only true). For a flat conjunct the root is the comparison; for a boolean conjunct (I10, BU-S1) it is the tree's root, which evaluates in Kleene logic - `NOT unknown` is unknown, `false AND unknown` false, `true OR unknown` true - so `NOT (a = 1)` keeps no row whose `a` is NULL (BU-R4, `chain_frame.cpp`'s `EvaluateBoolConjuncts`). `NOT IN`'s standard semantics are three-valued and the dangerous half is exactly that: if the subquery result contains a NULL and the probe matches nothing, `x NOT IN (S)` is UNKNOWN, not TRUE, so it is never implemented as `!IN`.

## 6. Trail integration

- **Recording (J5, n = 2), for opted patterns only since CF-S1b:** a shape records and replays only once an operator opted it in with `WAYSTONE ON` (`docs/spec/waystone-concpets.md` §4a); a shape nobody opted is never sighted. For an opted pattern, the first execution of an instance `(fetch_id, arg_hash)` only counts and the second records (`TrailRecorder::kRecordThreshold`). Sightings live in a bounded, core-local in-memory table; eviction merely restarts the count, which is a performance event. A recording writes the trail and nothing to the pattern's `sys.patterns` row (`docs/spec/waystone-concpets.md` §4).
- **Per-step recording:** `Lookup`/`Probe` steps append entries in execution order with their `step_id` and per-entry `rel_oid` — the existing 32-byte format, unchanged. `Exists` steps record the witnessing row only. `Range`/`Scan`/`NotExists` record nothing.
- **Replay** consults the instance's trail for entries with the step's `step_id` and applies `docs/spec/waystone-concpets.md` §2 per entry; any miss falls through to the authoritative path *for that step alone*. Search-class steps use the trail only as a prefetch batch.
- **`Exists` replay is positive-only**, and the asymmetry is the whole point: a validated witness *proves* non-emptiness, because presence has a witness. A missing or invalid witness proves nothing and the probe runs. A trail can never conclude absence.

**I17 — Rule 0: the key must be re-derived, at every replayed step.**
Before a trail entry for a `Probe` step may be trusted, the executor derives the probe key from the **current** producing row it has in hand and requires it to equal the entry's `tuple_key`. A mismatch is a miss for that step alone. **The driving step is under the same rule** (AR1's rule 0′): a `Lookup`'s key is derived from the statement's own values, and an entry filed under another key is turned away whatever instance key led to it.

Without it, replay is a wrong-answer generator, and no other rule catches it. Suppose the producing row's join column was updated from 77 to 91 between recording and replay. The entry for tuple key 77 passes every other check in `waystone-concpets.md` §2 — `rel_oid` matches, the Keystone id at the recorded slot is 77, the epoch matches, MVCC says visible — because **every other rule validates the trail against storage and none of them looks at the query**. `UPDATE` overwrites in place and keeps `(page_id, slot)`, so nothing about the producing row looks stale. The join would emit row 77; the correct answer is row 91.

The check is free at runtime: the producing row is already decoded by R1 and the probe key is already a resolved `ColumnRef`. How it is held - the replay index's key and rule 1's check against the derived key - is `waystone-concpets.md` §2 rule 0's.

## 7. Executor

A small step VM in `src/exec/`: compile once (AST → `StepChain`, alongside class tagging), then iterate — a linear loop over steps, a nested loop for sub-chain steps, on the core its session is on; only a `SELECT`'s outermost walk yields, every 64 pages (BA-S15, `sched.md` §3), and nested walks and write walks run to completion. Cursor and row state live in the chain frame: no allocation per row, bounded by depth cap × per-step state. The VM is the compile contract J4 preserves.

Two things the VM inherits from I15 rather than choosing: frames own their decoded rows (R1), and nested steps are read-only (R2). One thing it must not do: hold a `TableAccess` pointer across anything that can bump the catalog version.

**The walk and the scan kernel** (BM, `instructions/v3.0.0/workorder-bm-scan-row-kernel.md`).
- **A btree walk owns its slot loop.** Every walk step on a btree relation - the outermost and a nested one alike - fetches each leaf (`btree::BtreeFetchLeaf`) and calls its slot visitor directly: no `std::function` and no `StatusOr` per slot, the page's slot count read once per leaf (`PageView::ReadTupleIn`). The row loops `UPDATE` and `DELETE` run still go through their primitives.
- **What cannot change within a statement is checked once per step.** The decode's schema-and-layout checks and the residual's malformed-chain checks run at a step's first visible row, by whichever access kind reaches it, with their messages; every later row pays the payload's length check and the comparisons. A malformed later conjunct is therefore refused even where an earlier one false on every row would have masked it. `UPDATE`'s and `DELETE`'s own row walks check their `WHERE` conjuncts the same way, once at their first row, and compare per row (BT, `instructions/v3.0.0/workorder-bt-accept-tuple-row.md`, BT-R5).
- **The scan kernel is a pre-filter, never the answer.** A conjunct `column <op> literal` on the step's own relation is compiled, when its type allows, to the comparison `CompareValues` would make on the decoded column, made on the cell's bytes: the int widths, date, timestamp and narrow decimal sign-extended, bool zero-extended, `uint64` unsigned, the 128-bit decimal pair, column 0 as its 48-bit Keystone id (never its 8-byte cell), `char(N)` after its NUL trim, and a `varchar` cell only inline, read by `storage::InlineCellBytes` - `DecodeCell`'s checks with no `Status`, which the column decode takes first too (CA C4). It may only reject a row the residual would reject; every row it passes is filtered by the residual unchanged. A NULL operand, a literal of another kind or scale, a `uint64` tuple key, the `IS` pair, a spilled or refused cell and a correlated conjunct are the residual's.
- **It reads only what the walk holds** (R1): a visible version on the page under the walk's read hold, after the length check and before the copy; a version reconstructed through undo from the reader's own buffer, never the page; no fetch. It is armed once the step's check has run, so a step's first visible row takes the full path, and never while that step's Cabin recording is live.
- **Same rows, order and counts.** A rejected row is examined, not matched, and charged to the row-touch budget in the order the residual's rejection is, so `examined=`, `sel=` and `ResourceExhausted` read the same; what falls is work - copies, decodes, spill fetches. `scan_kernel = on|off` (`kds.conf.sample`) is a read-path switch, on by default, and the contract suites compare replies across it.

**Cost.** Outside the outermost `SELECT` walk's yield nothing suspends mid-statement on a cooperative core, so an unbounded correlated scan is a denial of service on a shared engine. A per-statement row-touch budget (`max_rows_touched`, default `exec::kDefaultRowTouchBudget` = 100,000,000) stops the walk through R4 and fails the statement with a clear status; failing is the kinder answer. The rows a join touches depend on its order, so since CC-S3 whether a statement meets the budget can move with the join planner's statistics as well as with the catalog.

## 7a. The query layer

**I19 — What a step chain cannot carry, the query layer answers (BU-S4, `instructions/v3.0.0/workorder-bu-basic-query-surface.md` BU-Q8..Q13).** A SELECT the native grammar (§4) refuses, or whose native compile declines it `NotImplemented`, is parsed again by the query grammar (`Parser::ParseQuery`, `parser::Query`) and, if that reads it, run by `exec::RunQuery` (`include/kds/exec/query_layer.hpp`); if the query grammar refuses it too, the native refusal is the reply (BU-Q9) - but for a statement either grammar read as far as a locking clause, which is answered by the grammar that read it: the query grammar reads no `FOR UPDATE` and refuses one by name (I11a). So every statement the native path answers keeps its parse, chain, plan, trail and reply, and `ANALYZE` never reaches the layer.

- **Forms (BU-S4).** The select list holds value expressions - the BJ grammar of `docs/spec/types.md` §3.2b over any column of the `FROM` list, qualified or bare - each with an optional `AS alias`, plus `*` and `rel.*`; `SELECT DISTINCT`; a select list with no `FROM` (one row); a value expression anywhere a `WHERE` condition stands, with `[NOT] IN (list)`, `[NOT] BETWEEN`, `[NOT] LIKE`, `EXISTS` and `IN (SELECT ...)` among them; `ORDER BY` a position, an output column's name or alias, or an expression (under `DISTINCT`, one of the select list's), up to `kMaxSortKeys`.
- **Grouped blocks (BU-S5).** `GROUP BY` over value expressions, `HAVING` over the keys and aggregates (I16 at its root), `ORDER BY`, `LIMIT` and `OFFSET` over groups, an aggregate under an alias, over an expression or inside an expression, and an aggregate inside a subquery. The fold is `aggregate.md`'s: §3.1's NULLs, AG3's accumulator checked at every row, §3.4's AVG, AG11's `aggregate_max_groups` and `aggregate_max_distinct`; a key named twice is refused as natively. A column of the block outside an aggregate must be a `GROUP BY` expression as written; a subquery may not read a column of a grouped block (`NotImplemented`).
- **Joins (BU-S6).** `INNER`, `LEFT`, `RIGHT` and `FULL [OUTER] JOIN`, `CROSS JOIN` and comma joins, `ON` over any typed bool condition, `USING (col, ...)` (refused under `FULL`, and `*` over a `USING` join refused, each `NotImplemented`). Written order; a comma binds looser than `JOIN`, so a `RIGHT` or `FULL` join after a comma - `x, a RIGHT JOIN b`, which is `x` crossed with `a RIGHT JOIN b`, not left-deep - is refused `NotImplemented`; a USING pair's other column is reached only qualified, so a bare name over a USING join and a third relation's column of that name is ambiguous; a join hashes on the column equalities of one type among its `ON`'s top-level `AND` terms and tests the whole `ON` per candidate pair; an outer join null-extends the side with no match; its output counts against `sort_max_rows`. A `WHERE` term is evaluated after the joins, and carried by a relation's walk only when that relation is on no join's nullable side (BU-Q7) - a `RIGHT` join's every relation left of it, a `LEFT` join's right relation, both sides of a `FULL` one.
- **Set operations, derived tables, subqueries as values (BU-S7).** `UNION`, `INTERSECT` and `EXCEPT`, each `[ALL | DISTINCT]`, `INTERSECT` binding tighter than the other two and each left-associative; NULLs one value; `ALL` by multiplicity (`EXCEPT ALL` removes one left row per right row); the sides' columns paired by position, of one type each (two text types meet as `varchar`, anything else refused, BJ-R3), named by the left side; `ORDER BY` a position or an output name and `LIMIT`/`OFFSET` over the whole, a parenthesized side keeping its own. A derived table `(SELECT ...) AS name` - a set operation or a grouped block included - is a relation of the block whose columns are its output's, never correlated with its siblings or its enclosing query (`LATERAL` is not read), never carrying a `WHERE` term into itself. A subquery as a value - in the select list, `ORDER BY`, `GROUP BY` or an expression anywhere - returns one column and at most one row (none is NULL; more is `CardinalityViolation`, as line 77's rule), and may be correlated. A column is read by its SQL name - a relation's column name, an output column's alias, column name (`o.id` is `id`) or aggregate (`sum`) - and headed by the rule above; a derived table that reads a column of an enclosing query is refused `NotImplemented`.
- **Native walks below, rows in hand above.** Each relation a block names is walked as a single-relation step chain (`LayerHost::WalkRelation`, the dispatcher's `WalkForLayer`), at the statement's one snapshot, carrying every top-level `WHERE` term that reads that relation alone, holds no subquery, and that the native `WHERE` grammar reads (`Parser::ParseConditions` over the term's text) - so a pk or index term keeps its access path. A term is never carried by a relation on an outer join's nullable side (BU-Q7). Everything else is evaluated over the rows the walks returned: joins (hashing on `ON`'s top-level column equalities), the remaining terms, grouping, the select list, `DISTINCT`, the order and the count. A layer walk has no text of its own, so no fingerprint and no trail; a layer statement records and replays none (BU-Q12, invariant 8).
- **Typed at compile** (BU-Q11 `[quiet-wrong]`): every expression is typed by BJ's typer (`TypeQueryExpression`) before a row is read, with no implicit conversion; an untyped literal takes its context's type, or with none its natural one (an integer `int64`, a string `varchar`, a bare decimal its own `decimal(p,s)`, a lone `NULL` `varchar`). A comparison is a `bool` value, three-valued; `WHERE`, `ON` and `HAVING` keep a row only when true (I16 at the condition's root, BU-R4). `CAST(x AS varchar(N))` stays refused, `N` being a cell width and not a length (BU-Q13).
- **Headings.** An alias; else a column as written (`o.id`); else an aggregate over a column or `*` in the fold's canonical form (`count(*)`); else the expression's text as written.
- **Bounded** (BU-Q10): every row set held - a walk's rows, a join's output, a sort, a set operation - by `sort_max_rows`, a group table by `aggregate_max_groups`, the DISTINCT sets by `aggregate_max_distinct`, each refused `ResourceExhausted` naming the setting; nothing is truncated.
- **Not reached**: a catalog view (`sys.*`) in a layer statement is refused `NotImplemented`; `OVER`, `FILTER`, `WINDOW`, `QUALIFY`, `DISTINCT ON`, `NATURAL JOIN`, `LIKE ... ESCAPE`, `NULLS FIRST/LAST` and `WITH` are refused by the query grammar by name - and, the query grammar refusing, the reply is the native path's refusal (BU-Q9): `WITH`'s `NotImplemented` at its byte, `OVER` the native parse's "expected 'FROM'".

## 7b. The DML forms (BU-S8)

**I20 — What an INSERT, UPDATE or DELETE reads beyond its own rows**
(`instructions/v3.0.0/workorder-bu-basic-query-surface.md` BU-Q16..Q18).

- **A VALUES value** takes the SET value's grammar (`Parser::ParseSetValue`): a bare literal keeps the shape it always had, anything longer is an `InsertStmt::ValueExpr`, typed by `TypeSetExpression` for the column its position reaches and folded once before any row is placed; one reading a column is refused.
- **`INSERT ... SELECT`** parses its source in the query grammar (`InsertStmt::select`) and the dispatcher runs it through the query layer (`RunLayerQuery`) at a snapshot taken after `BeginWrite`, whole, before the first row.
- **`ON CONFLICT [(col)] DO NOTHING`** (BU-Q18): on the tuple key (`col` the tuple key, or none written), each row naming a key is asked `TupleKeyPlaced` - the key's row unit taken as a named-key placement takes it, BD-Q9's wait included - before any row is admitted, and a placed key (live, delete-marked, or named by an earlier row) drops the row. **Since CG-S1 `col` may be the one column of a unique index** (`ResolveConflictArbiter`): each row's key is checked at latest state under its `kIndexKey` unit (BX-R1, BX-R3) and a held key drops the row, row by row, so no key's unit is held across two rows. Its forward fk check is hoisted over every row before the first write, so a dropped row has taken its parents' `S`. Any other target is refused `NotImplemented` at its byte.
- **`ON CONFLICT [(col)] DO UPDATE SET ...`** (CG-S1, `instructions/v3.2.0/workorder-cg-on-conflict-do-update.md`): the arbiter is as `DO NOTHING`'s - none written means the tuple key, refused on a heap whose Keystone is hidden (`heap-and-tuple.md` §3.1b). Row by row (`InsertOnConflict`): an absent key takes the insert arm, `InsertOneRow`; a held key updates its holder through `UPDATE`'s per-row path (`UpdateParsed` with the holder as its target, under the holder's row `X`), the SET list typed and evaluated as an UPDATE's against the holder's before-image, with `EXCLUDED.<col>` bound to the proposed row's value and the target's own name qualifying its columns. On a unique index the holder is read again under its `X`, and one moved off the key takes the insert arm. **Refused**, each at its byte: a key held by a delete-marked row - committed, with `PURGE`'s hint (CG-Q2 (a)), or this transaction's own (CG-Q3 (a)) - `AlreadyExists`; two rows naming one key `CardinalityViolation` (CG-Q4 (a)); `DO UPDATE ... WHERE` `NotImplemented` (CG-Q5 (a)); a SET of the tuple key (K2). **A held row the statement's view does not see** - written by a transaction that committed after it - is refused `TxnConflict`, retryably, rather than left unwritten. The reply is `INSERTED oid=<o> rows=<inserted + updated>` (CG-Q7 (a)), and `RETURNING` answers both arms' rows.
- **`UPDATE ... FROM u` / `DELETE ... USING u`** is the statement's WHERE made one `EXISTS (SELECT * FROM u WHERE ...)` (`ExistsOver`), whose block shares the statement's name space (`SelectStmt::shares_parent_names`: a bare column both relations hold is ambiguous, one name bound twice refused). `UPDATE`'s EXISTS is `at_most_one` (BU-Q16 `[quiet-wrong]`): never hoisted, it reads a second row and refuses `CardinalityViolation`. One relation after `FROM`/`USING`.
- **An `UPDATE`'s or `DELETE`'s `WHERE`** is the native grammar's alone (I10): no query layer stands behind it as one does behind a `SELECT` (I19), so an expression operand (`n + 1 = 3`), a comparison with a literal on both sides (`1 = 0`) and any other form only the query grammar reads are refused `NotImplemented`, the message carrying the native refusal and its byte (`Parser::DeclineDmlWhereExpression`, asked of a second parse from `WHERE` on the refusal path only). A `WHERE` neither grammar reads keeps its native `InvalidArgument`, and so does one holding an aggregate outside a subquery, which is wrong in any `WHERE` (a `SELECT`'s query layer refuses it `InvalidArgument`). The second parse reads syntax and no types, so a `WHERE` a `SELECT` would refuse mistyped (`WHERE n LIKE 5`) is declined here `NotImplemented` before any typing.
- **`RETURNING <items>`** (BU-Q17): the query grammar's select list (`Parser::ParseOutputItems`) after the statement's clauses; the dispatcher (`WithReturning`) finds the rows on the transaction's trail since the statement's mark, reads each back by tuple key, types the items over the relation's live columns with the query layer's typer, and emits them before the write scope ends.

## 9. Testing requirements

1. **Oracle equivalence:** every step-chain statement checked against a naive reference evaluator over small fixtures — joins, each subquery form, NULL-in-`NOT IN`, cardinality violations.
2. **Advisory family:** results byte-identical with Waystone off, trails dropped mid-run, and recording disabled — across nested chains too.
3. **Replay rules:** §1's per-kind table enforced by instrumentation — a `NotExists` step provably never reads a trail; an `Exists` step never concludes absence from one; rule 0's stale-probe-key case returns the new row.
4. **n = 2:** first execution records nothing (instrumented); second records; sighting-table eviction restarts the count with no correctness change.
5. **Refusal surfaces:** every J2 form errors with its own code and an exact position, and nothing falls through to a generic path.
6. **Depth and numbering:** chains at the cap; global `step_id` stability across executions of one instance.
7. **Fingerprint invariance:** every pre-existing corpus statement's `pattern_id` is unchanged by every grammar addition; convergence of inline and bound forms; a correlated statement's `arg_hash` stable across outer rows.
8. **Execution equivalence:** `Probe` and `Scan` strategies agree row-for-row; execution order matches the chain's order, and both writings of one join return the same multiset.
9. **Nested access:** a stopping visitor touches no page past the stop; a false uncorrelated `EXISTS` opens zero pages of the outer relation; a correlated `EXISTS` short-circuits, proven by page-touch count.
10. **Grammar:** golden parse trees for every production; byte- and token-level fuzzing — never crashes, always returns `Status`; a corpus of nesting attempts outside predicate position contains no accepted parse.
11. **Zero-copy:** token text is a view into the statement and lexing allocates nothing (`include/kds/parser/token.hpp`); the fingerprint is accumulated during the parse rather than by a second lex.

## Addendum — `DELETE`

`DELETE FROM <t> [WHERE <predicate>]` is a statement head.

- **The WHERE is the same production `UPDATE` uses** (`ParseOptionalWhere`
  at depth 0), compiled through the same `exec::CompileWhere`, so a
  `DELETE`'s predicate means exactly what the `SELECT` that found the rows
  meant. Predicate-position subqueries nest exactly as a `SELECT`'s do.
- **No fingerprint bump.** `fingerprint.hpp`'s rule names this exact case:
  making a statement fingerprintable that previously was not does not move
  any hash already stored. `DELETE` is not fingerprinted, and the
  golden corpus records it as `ok  -  -`.
- **`DELETE` is not a reserved word.** Like `SELECT`, `INSERT` and
  `UPDATE`, it is matched by text where the grammar expects it, so a column
  may still be named `delete`.
- It does not compile to a step chain. `HandleDelete` walks the relation
  itself, exactly as `HandleUpdate` does, and applies the same visibility
  predicate through `txn::Classify`.
