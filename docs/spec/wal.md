# KDS Write-Ahead Log (WAL)

How KDS makes a mutation durable, and how it replays one. `[PROPOSED]` marks a default to confirm or amend before the affected part is built; `[OPEN]` must not be assumed. Companion specs: `docs/spec/page.md` (page header, flush gate, file layout), `docs/spec/txn.md` (transactions and MVCC), `docs/spec/heap-and-tuple.md`, `docs/rules/rules.md`, `docs/spec/sched.md`.

**Status: every data mutation is logged, and recovery runs at mount.** The boundary lives in `include/kds/wal/recovery.hpp`:

- **Analysis, redo and the high-water repair run once per log** — on core 0, there being one log (§3) — followed by a completion checkpoint; `SHOW META` prints the recovery block. The catalog recovers too, and a torn catalog page refuses the mount rather than being served corrupt.
- **The undo phase is injected.** `RecoverStream` takes an `UndoPhase`; mount installs `txn::RecoveryUndo` (`src/server/mount_recovery.cpp`), so losers are rolled back. A stream that analysis found losers in, recovered **without** one, fails the mount — deliberately, because redo without undo is worse than no recovery at all: redo restores uncommitted writes, and a surviving uncommitted row reads as *committed* on the next boot (`txn.md` §4.1). A recovery that replays and stops has published every loser's writes.

§11a states exactly which mutations are logged; §12 specifies the replay.

---

## 1. Purpose & Guarantee Model

WAL provides the engine's **atomicity and durability**. Target domain is financial OLTP, so the guarantees are stated as business commitments:

- **No acknowledged loss:** a commit acknowledged under the synchronous classes below survives any single crash with no data loss and no partial transaction.
- **Bounded recovery:** restart time is bounded by checkpoint cadence (RTO is a tunable, not an accident).
- **Auditability:** the log is a complete, ordered, checksummed record of every change — the substrate for point-in-time recovery and, later, replication.

### Durability classes

| Class | Commit acknowledgment | Loss window | Intended use |
|---|---|---|---|
| `D1 strict` | after the commit record is durable (flushed + device-synced) | zero | default for financial writes |
| `D2 group` | same durability point; flush batched (group commit); ack waits on the batch | zero (latency traded for throughput) | default operating mode |
| `D3 relaxed` | after the record enters the WAL ring | ≤ configured flush interval | bulk load, reconstructible data |

Class is a per-transaction property (`C_TXN_BEGIN.durability`) with a session default; `S_TXN_OK` for D3 carries the `RELAXED` flag so audit logs distinguish ack semantics. `D1/D2` differ only in batching, never in the durability point.

## 2. Architectural Position

- **Redo log + undo pages.** WAL is a **physiological redo log** (page-oriented records: page_id + slot + bytes). MVCC history lives in undo chains reached via each tuple's `undo_ptr`; undo-page writes are themselves WAL-logged, so both roll-forward and roll-back state survive a crash. (InnoDB-shaped, deliberately not Postgres-shaped and not Oracle block/ITL-shaped — settled with the MVCC header decision, §5.1.)
- **WAL-before-data:** no modified page reaches disk before the log records describing the modification are durable. Enforced in code, not by caller discipline: the `BufferPool` holds a `WalDurability` seam and **refuses to flush a frame until `durable_lsn() ≥ page_lsn`** (`docs/spec/page.md` §8). This spec defines the rule; the pool implements it.
- **Who runs it:** foreground tasks *append* records as part of their page mutations; flushing, group-commit completion and checkpointing run in the **`system` scheduling group**. WAL housekeeping never runs inside foreground tasks. **Segment recycling** (§11-4) detaches segments on the thread whose checkpoint published the anchor, under the stream latch and with no I/O, and removes their files on core 0's WAL writer thread, after that pass's sync.
- **I/O:** all WAL I/O goes through the injected `IoBackend` seam — never direct syscalls, never mmap (rejected engine-wide, `docs/spec/page.md` §15) — so every guarantee here is testable under deterministic simulation with fault injection (rules.md §4). The concrete backend remains `[OPEN]` and must not leak into WAL logic.
- **Not via `PageStore`.** WAL segments are append-only streams; `PageStore`'s random-access `PageRef` semantics are the wrong shape. WAL owns its segment files directly through `IoBackend`. `PageStore` remains the seam for data/undo/catalog/Waystone pages only.
- **Waystone: unlogged** — Waystone pages are the headerless page class (`docs/spec/page.md` §1): no `page_lsn`, no checksum, never replayed. On crash, an enabled relation's Waystone rebuilds via backfill; its advisory contract makes an empty structure correct.
- **Backpressure is legitimate here.** Unlike Waystone (advisory, drop-on-overflow), WAL is correctness: a full WAL ring suspends the appending foreground task until space frees — the one sanctioned way durability slows the foreground, visible in metrics (§13).

## 3. Log Topology — One Stream Per Instance

**A volume records its own topology and only one is admitted.** `SuperBlockFields::log_topology` holds `kSingleStream` (1); any other value is refused **by name** by `SuperBlock::Decode`, naming the absent migration rather than reporting unspecified damage, so a pre-M0 volume does not mount. There is no runtime switch, no way to convert a volume, and no branch below the door: the mount does not ask the field, it is refused at the door if the field is wrong. `CreateFresh` takes no topology parameter, so this build cannot write a volume it would then refuse.

**One stream** (AR0 M0): the instance has one log. Core 0 opens it and owns it; every peer **attaches** to that stream and to core 0's writer thread and opens no log of its own. A peer appends through the stream's latch and asks core 0's writer for a sync instead of issuing one — so every `fdatasync` this instance pays is issued once, over one file — on core 0's writer thread for D3's loss-window tick, for every sync a peer asked for and, **above one core, for core 0's own `group` commits too** (BA-S7 part 1, `instructions/v3.0.0/workorder-ba-parallelism.md` BA-R4): the writer kicks each core whose committer parked on a durability point when the watermark passes, and no drain reports a staged commit as work, so a reactor with nothing else to do blocks rather than polls. **Above one core a `strict` commit is staged and parked too** (BA-S7 part 2, BA-Q3 (b)): it appends its record, holds its snapshot marker, and publishes only once the writer's sync covers the record, so concurrent `strict` commits share a sync and D1 stays "visible only once durable". A sync that fails under it aborts it (§6-5). `EnsureDurable` and `SyncAll` still sync on core 0's reactor, and at one core so do `group` and `strict` commits, as before. The append path therefore carries a lock; AR0-2 accepts that cost deliberately and it is what §6's ring bookkeeping is written around.

- **LSN** is instance-wide: one monotonic `uint64_t` byte offset over the one log, comparable everywhere. Records from different cores interleave in it freely.
- **The superblock anchor is a fold.** Slot 0 holds the record of whichever core published the lowest `redo_start_lsn`; slots 1..N−1 are unused, and `SetWalAnchor` refuses any core but 0 so no caller can bypass the fold. Until **every** core has published at least once, the fold holds at the mount anchor rather than at the minimum over the cores that have — a warm-up, because a core that has published nothing has not yet said its redo start is high. `superblock_checkpoint_anchor.hpp` owns it.
- **Recovery runs once**, on core 0, before any peer exists (§12). A peer performs no recovery pass; its `SHOW META` recovery block says so rather than reporting an empty one.
- **`TXN_PREPARE` (27) and `PAGE_HANDOFF` (25) are retired kinds** (BP-R4). No build that writes superblock 22 appends either, so analysis refuses a log carrying one `Corruption`, never skips it; the numbers stay assigned so no later kind reuses them (`wal/record.hpp`, `wal/analysis.cpp`).
- **Counters are per manager, so a peer's are honestly zero; the roll's are the stream's** (BQ-S1): `wal_append_lsn`, `wal_rolls` and every `wal_roll_*` read the same on every core and are never summed across cores. A peer asks the writer for every commit and durability sync, so its `wal_syncs` and `wal_interval_syncs` are structurally 0 and its durability cost is read on core 0. **A peer's append that rolls does sync**, inline under the stream latch (§4.1): the roll's device sync and the new segment's header sync and directory fsync run on whichever core rolled, and are counted in the stream's roll totals, not in `wal_syncs`. `wal_sync_failures` is the exception: a peer's flush of the shared ring and its wait on the writer can both fail and are counted where they happen.

- **The core count is not pinned.** The superblock records `core_count`, and a mount at a different `cores` records the new count and logs the change rather than refusing (`src/bootstrap/bootstrap.cpp`, `SuperBlock::SetCoreCount`). Nothing on the volume names a core (`sys.tables.owner_core` is a reserved word, written 0 and never read). What is sized by the count - the anchor fold's warm-up over every core's published checkpoint, the lock table's partitions, the page latch's owner bits - is sized from the running one, and the fold's slot 0 holds the lowest redo start whatever count wrote it, so recovery replays from it correctly across the change. Online core-count change - adding a core to a running instance - is not supported.

## 4. Segment & Record Format

### 4.1 Segments `[PROPOSED]`

- A stream is a sequence of fixed-size **segment files** (64 MiB), named by `(core_id, segment_no)`. **The size is a constant and a property of the volume, not a setting** (`kDefaultSegmentSize`, `wal/log_device.hpp`): a segment file of another size is `Corruption` at open, and an LSN's segment is `lsn / segment_size`, which the anchor's redo start relies on, so a change of size is a format event - the superblock bumped and every older volume refused (`instructions/v3.0.0/workorder-bq-wal-segment-roll.md` §1.3, BQ-Q4). **A larger segment does not make a roll cheaper** (BQ-S2, `bench/v3.0.0/results-bq-s2-rung1-v2.7.0-909-g4cf30270.md`): rolls get rarer and each holds longer - about 5 ms more per MiB at `relaxed` under a bulk writer, the total held time flat - and BQ's mount probe at 1,024 MiB saw the restart take 1.1-1.4 s longer and a single `INSERT` stall up to 12.8 s while a roll waited on the preparer's build (the probe writes 2.5 segments of log at every size, so it does not separate the size from the volume). **Segment numbers never restart**: recycling (§11-4) removes segments from the front, so the device's live segments are a contiguous run `[first, end)` with `first` above 0 once anything is recycled. A mount opens the run from the segment holding the anchor's redo start; segments below it are leftovers of an interrupted removal, neither read nor deleted by the open, and removed by the first anchor publish after it - the mount's completion checkpoint's, when its sync lands. A gap at or above the anchor's segment is `Corruption`, as is no segment there at all.
- Segment header (one 4 KiB block): magic, format version, `core_id`, `segment_no`, `start_lsn`, header CRC32C.
- **`core_id` names the stream's owner, not the record's author.** It is 0 on every segment, because core 0 owns the one log and the peers attach to it (§3); no record names the core that appended it (BP-H5: the envelope's `flags` byte is written 0 on `PAGE_INIT` and the checkpoint records).
- **Format version is 2, and this build reads version 2 only** (`kSegmentFormatVersion`, `kMinReadableSegmentFormatVersion`). The minimum is a **floor and not just a version**: `DecodeSegmentHeader` refuses what is *newer* than this build, and the floor is what refuses what is older rather than accepting and mis-decoding it. The floor tracks the current version while no compatibility promise exists (pre-1.0); the day one does, a decoder per supported version replaces it, with a migration story.
- **Any change to a record payload is a format-version event**, because recovery reads the log back. "Nothing reads this format back" is not an argument that may be reused without re-checking that it is still true.
- **A roll's order is durable**: the segment it leaves is synced - its records and its seal - before the next segment is created, and the next segment's header is written as part of its creation, under the same fsync that makes the segment exist. **A segment's body is usually built ahead** (BA-S12): once the current segment is half full, `WalStream::Append` asks the device for the next one, and a thread of the device's own reserves, zeroes and fsyncs it under the temporary name; the roll then writes the header over its first block, `fdatasync`s it, renames and syncs the directory - the header durable before the name, as when the creation builds the body itself, which it still does when nothing was built ahead. A body built ahead and never adopted is a temporary file and nothing more: a clean shutdown can leave one, and the next creation of that number removes it. **A segment is built under a temporary name** (`wal-<core>-<n>.log.tmp`), which `Open` never adopts, and renamed to its own name - never over a file already there - only after that fsync; the directory is synced after the rename. So after any crash the last segment has a durable header and every earlier one is sealed on the device, a scan never stops at an unsealed segment with the stream resuming beyond it, and a creation a crash interrupted leaves at most a temporary file, which the next creation of that number removes.
- Records are 8-byte aligned and **never span segments**: a non-fitting record pads the tail with `PAD` and seals the segment. Oversized payloads are a design error, not a spanning case. **A record must also fit the ring whole**, so the largest payload is the smaller of the two less the header - `WalManager::usable_payload_bytes()`, which a caller that chunks its own data cuts against (AZ-S3; the ring is the smaller at the defaults, 1 MiB against a 64 MiB segment). **A stream opens on neither a ring nor a segment below 512 KiB** (`kMinRingCapacity`, `kMinSegmentSize`, `stream.hpp`): both floors hold the largest `BTREE_SPLIT` (§5.2), so the record a split appends after its pages changed is never refused for its size.
- A sealed segment is immutable — the unit of archiving (§13) and recycling (§11).

### 4.2 Record header `[PROPOSED]`

Fixed 32-byte header + payload; little-endian; field-wise memcpy codec with `static_assert`ed offsets (rules.md §2/§5):

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 4 | `total_len` | header + payload + padding to 8 B |
| 4 | 4 | `crc32c` | over bytes 8..total_len |
| 8 | 8 | `lsn` | this record's stream offset |
| 16 | 8 | `txn_id` | zero-extended **48-bit** transaction id (§5.1); upper 16 bits 0; 0 = non-transactional (checkpoint, pad) |
| 24 | 1 | `type` | §5 |
| 25 | 1 | `flags` | per-type |
| 26 | 2 | `reserved` | 0 |
| 28 | 4 | `page_id` | target page; `kInvalidPageId` where N/A |

Torn-tail detection needs no commit marker: recovery walks forward; the first record with a bad CRC or impossible `total_len` is the durable end of the stream.

## 5. Record Catalog

### 5.1 MVCC model the records serve

The tuple header carries exactly **`trx_id` (writer, 48-bit) + `undo_ptr`** — there is **no `xmax` field**. A version's death is the next version's birth: walking the undo chain, the reader already knows the overwriting transaction when it arrives at an older version, so the chain itself encodes validity intervals; storing the boundary twice is redundant. DELETE is a **delete-mark** (slot/Keystone flag) plus the deleter's `trx_id` in the writer field — no separate field. Row locking has **no field of its own**, in the header or on the page: AO-R3 decided no persisted lock bit at all, so the byte stays zero and a row's tuple `X` is the writer stamp the header already carries, with the lock table holding the rest in memory (`txn.md` §5). The Postgres-style secondary role of `xmax` as a lock slot is covered by that stamp. Consequences for WAL: every heap mutation record carries the writer `trx_id` it stamps; undo records carry the *prior* writer id, which is what makes the no-`xmax` reconstruction work. The 48-bit width bounds `txn_id` in §4.2; exhaustion is `OutOfRange`, never wrapped (`docs/spec/txn.md` §4.2).

### 5.2 Types `[PROPOSED]`

Physiological redo: each record targets one page and is idempotently replayable (§9).

- **Transaction:** `TXN_BEGIN`, `TXN_COMMIT`, `TXN_ABORT`. `TXN_PREPARE` is a retired kind analysis refuses (§3).
- **Heap:** `HEAP_INSERT` (slot, tuple bytes incl. Keystone word, writer `trx_id`, `undo_ptr`), `HEAP_OVERWRITE` (in-place new version; payload includes new writer id + new `undo_ptr`), `HEAP_DELETE_MARK` (sets the delete flag + writer id — the DELETE of §5.1), `SLOT_RETIRE` (physical retirement after purge — distinct from delete-mark), `PAGE_INIT` (new heap page: common header + `min_key` + `owner_oid`, the owning relation's oid stamped into the common header at initialization, `docs/spec/page.md` §2a; `min_key` is immutable thereafter, so it appears only here). The `PAGE_INIT` payload is 24 bytes, `owner_oid` at offset 16 with four reserved bytes at 12 that keep the codec's mirror struct naturally aligned; a 12-byte legacy payload decodes as owner 0 (unattributed), mirroring §2a's on-page zero-default. **The length discriminator is a floor, not an equality**: `DecodeRecord` returns the record's 8-byte-aligned tail rather than the exact payload — a 12-byte payload comes back as 16 bytes, a 24-byte one as 24 — so `>=` is the only test that reads a legacy record correctly, and it is the rule every payload codec in `wal/payload.cpp` uses.
- **B+ tree** (BD-R3 E2, BD-R12, `instructions/v3.0.0/workorder-bd-sorted-leaf-named-keys.md`):
  - `BTREE_INSERT` (29): one row placed in a leaf where its key sorts. `HEAP_INSERT`'s payload — `{trx_id, undo_ptr, slot, tuple_len}` plus the tuple — with a strict redo: the directory entries at and after `slot` move up one, as the live placement moved them, and only when `slot` is the slot `btree::SearchLeaf` answers for the key on that page; anything else is `Corruption`. There is no re-application arm, because an insert whose split imaged the leaf logs no `BTREE_INSERT`. A `HEAP_INSERT` naming a B+ tree leaf is refused at redo; `HEAP_INSERT` is a heap page's record alone.
  - `BTREE_SPLIT` (30): **every page one split writes, in one record** — the new leaf, the old leaf, every internal node created or amended and a new root, each as a full image (`[nr_pages | reserved]` then `nr_pages × [page_id | reserved | 8192 bytes]`). Analysis dirties each page and redo applies each through its own `page_lsn` gate. The record's CRC makes the split atomic: a torn one ends the log before it, so a split replays whole or not at all, where a run of separate records could be cut between a parent and a link. It carries the inserted row, so no insert record follows it. **A secondary index's split is the same record** (its pages, no `INDEX_INSERT`). **A split that grew a root carries the relation's anchor page too**, its root slot already moved (`Catalog::StageAnchorRoot`, staged last under the split's holds), so the root a mount reads is replayed with the split or not at all; before, a later `ANCHOR_UPDATE` could be cut away from the split and leave the anchor naming the grown-over root, losing every row the split moved to keyed access. `ANCHOR_UPDATE` remains for an anchor's seeding at `CREATE TABLE`/`CREATE INDEX` and for a root no split record carries (`Catalog::PublishRoot`: an index root grown where nothing logs index writes as they are made). It fits every stream whole: a split carries at most `kMaxBtreeSplitPages` = 34 pages (the deepest split, 33, and the anchor), each tree asserts its bound against that (`log_page_image.hpp`, `command_dispatcher.cpp`), more is refused at encode and is Corruption at decode, and the stream's ring and segment floors hold the 278,840-byte record (§4.1).
- **Undo:** `UNDO_WRITE` (undo-page append; payload = the record's tail + prior writer `trx_id` + prior `undo_ptr` — the chain link; `docs/spec/txn.md` §3.5).
- **Var-heap:** `VARHEAP_APPEND` (a spilled value landing in a `kVarHeap` page; payload = slot + value bytes, target page in the envelope — `docs/rules/rule-fixed-length-tuple.md` §5) and `VARHEAP_RELEASE` (its rollback compensation, `docs/spec/txn.md` §6). The slot is recorded rather than re-derived because replay must reproduce the *exact* pointer the tuple's cell already carries; a pointer resolving to a different slot after recovery would be a value silently swapped for another. **Write ordering:** `VARHEAP_APPEND` precedes the `HEAP_INSERT`/`HEAP_OVERWRITE` whose cell points at it, in the same transaction, replayed by ordinary winner/loser machinery. **There is deliberately no var-heap-specific recovery logic, and none may be added.** Logged at all because a var-heap value is *authoritative data*: losing one loses a committed value, not a hint, which is what separates this class from the advisory waystone family.
- **Allocation:** `ALLOC`, `FREE` - **reserved and emitted by nothing**; redo refuses either. The free map is not logged: its pages are the store's regions, written with no record and repaired at recovery by the allocation floor (`docs/spec/page.md` §5). A dropped relation's page is freed without a record, once the durable redo start has passed the drop's commit so that no replay can name it (`instructions/v3.0.0/workorder-bf-drop-table-page-reclaim.md` BF-R4, BF-Q2 (a)). No record precedes a file extension either (`docs/spec/page.md` §14).
- **Catalog:** catalog-page mutations (DDL, Waystone flag changes) as ordinary page records.
- **Control:** `CHECKPOINT_BEGIN` (payload: active-txn table + dirty-page table with recovery LSNs), `CHECKPOINT_END`, `FULL_PAGE_IMAGE` (§10), `PAD`.

Adding a type is a format-version event; unknown types on replay are a hard recovery error, never skipped. `record.hpp`'s enum is frozen and append-only.

## 6. Write Path `[PROPOSED]`

Shaped for the reactor:

1. A foreground task mutating a page first appends its record(s) into the **WAL ring** — the instance's (§3); preallocated, so an append whose record fits its segment is a memcpy and a cursor bump, no allocation and no I/O. The **whole** append runs under the stream's latch — the size checks, any segment roll, the encode into the ring and the cursor bump; the reserve/copy/publish split that would have left the copy outside it was tried and abandoned (AL-R1; `docs/spec/page.md` §2b records what became of the document that argued the other way). The frame's `page_lsn` mirror is set to the record's LSN (the on-page header field is stamped by the same mutation).
   - **An append whose record does not fit rolls the segment, and the roll is device I/O under the latch** (since `a1679272`; `wal/stream.hpp`'s protocol header is the authority as built): it seals and flushes the segment, waiting out an unlatched flush in flight; syncs the segment it leaves through `WalStream::SyncDevice`, which first waits out any device sync in flight, the writer thread's included; and creates the next (§4.1) - all before the latch is released, so every core's append, flush and drain waits the roll out. Its cost is step 5's. **The latched roll stands** (BQ, 2026-10-12, `instructions/v3.0.0/workorder-bq-wal-segment-roll.md`): no rung below the latch's release met BQ's bar (two measured, two bounded out), and releasing the latch for the roll's I/O is not built.
   - **What is outside the latch**: a flush's device write since BA-S12, which swaps the staged ring for a second buffer under the latch and writes it unlatched, one at a time, with a roll and a detach waiting it out; and `WalStream::Sync`'s device sync, which runs after an unlatched flush. A roll's sync is the one device sync taken under the latch.
2. Reactor **phase 5** drains the ring into segment writes through `IoBackend`, batched.
3. `TXN_COMMIT` under `D1/D2` suspends the committing task on a flush future; the `system`-group flush completion resumes every task whose commit LSN ≤ durable LSN (**group commit**). `D3` resumes immediately.
4. Ring full ⇒ the appending task suspends until drain (§2 backpressure); stall time is metered.
5. **Fail-stop.** A device write the stream issues that fails - a flush of the staged bytes (an unlatched one stops the stream before it releases its claim, so no flush claimed after it publishes past the hole), or a roll's segment creation or header - stops the stream for good, and so does a ring-full refusal once its bounded drains are spent. Every later append, flush, seal and sync, on every core, is refused `IoError`, so every write is refused, and only a restart brings writes back; its recovery replays the durable prefix. The reason is step 1's order: a page is mutated under its hold and its record appended after, so a refused append leaves a mutation no record describes, and a compensation logged after it - a rollback's `SLOT_RETIRE` - would describe to redo a change redo never saw, refusing the next mount. Stopping refuses that compensation with every other record, and the next mount's undo retires the placement from its durable undo record. **No page is written back after the stop** (`DevicePageStore`'s writeback asks `WalDurability::stopped()` and refuses): the page_lsn gate cannot catch a mutation whose record was refused, because its page_lsn did not move, so without the refusal a split's shrunk leaf, or a row with no undo record, could reach the disk. A crash then leaves the disk at a point an arbitrary log prefix describes, which is what recovery is built for. A group commit parked on its durability is answered with the refusal rather than left waiting. `SYNC`, eviction's writeback and a transaction-id carve are refused with it. **A failed device sync stops the stream too** (operator, 2026-10-07), on the reactor's inline sync and on the writer thread alike: no sync that starts after the failure publishes a durable point (one that returned OK before it may still publish its true watermark), the writer never syncs again, and every waiter is answered with the failure. **Both threads sync the log's data through one gate** (`WalStream::SyncDevice`): one device sync at a time, refused once stopped, the stop raised before the next can start. **The log directory's fsync**, which a roll and a reclaim both issue, is serialized inside the device and a failure of it is sticky, so the next roll fails and stops the log. Without it a sync on the other thread, started after the failure, could report OK over the pages the failure dropped, and two overlapping fsyncs on one descriptor can hand the error to one caller and OK to the other. A sync can therefore wait out one already in flight, and a roll does so holding the stream latch (step 1). **Measured** (BQ-S1, `bench/v3.0.0/results-bq-s1-segment-roll-v2.7.0-909-g4cf30270.md`, at `v2.7.0-909-g4cf30270`): at `relaxed` under a bulk writer (about 75 MiB/s of log) a roll holds the latch p50 about 330 ms, p99 about 790 ms, max 1.2 s, and 95 % of that is this wait - the writer's tail `fdatasync`, slow on a device also taking the log, the checkpoint's writeback and the next body's zero fill. Rolls come every ~0.85 s there, so 35-46 % of a window is under a hold; cores without the bulk writer see a schedule p99 of 288-659 ms against 0.23-0.47 ms alone (medians), and core 0's drain carries about all of its core's stream-latch wait. At `group` the hold is about 6 ms p50 and 20 ms p99. A retry is not an answer, because on Linux a failed `fsync` can drop the dirty pages and clear the error, so the next one reports success over bytes that are gone; publishing that would claim durability for a hole in the log.

## 8. Flush-Ordering Rules — normative

The whole correctness contract between WAL, `BufferPool`, and the checkpointer:

1. **WAL-before-data:** a dirty page may be written to the data file only when the log is durable up to that page's `page_lsn` — the instance's, there being one (§3). **That is what makes one buffer pool admissible**: the gate is a property of the log, so any core's manager answers for every core's pages, which would be untrue were there two logs. **Each core asks its own since BA-S1** (`DevicePageStore::SetCoreWalGate`). Core 0 asks the store's default, its owning manager, which syncs inline on its reactor. A peer asks its attached manager, which flushes through the stream latch and waits on the writer. **A cadence checkpoint asks neither and waits for neither since BI-S3**: its writeback takes a `defer`, and where either gate - the batch's or a run's - needs the log past an LSN not yet durable, `WriteBack` stops before that run, gives back its claims with the frames dirty, and returns the LSN; the run task asks the writer (`RequestSyncNow`) and parks, counted into the writer's kick, then writes again, so on core 0 too the checkpoint's log syncs are the writer's. After 16 parks for one step the step waits inline (`Checkpointer::kGateParks`), the counted remainder. Nothing is written ahead of its record either way. Answering is syncing, and a manager's sync writes that manager's own state, so one gate for the instance would run core 0's inline sync on a peer's thread, against §3's *"a peer performs no device sync"*. **Enforced inside `BufferPool::Flush` via the `WalDurability` seam** (`docs/spec/page.md` §8); `MarkClean` is reachable only as flush completion. `DevicePageStore` — the store the server runs on — holds the same seam (`SetWalGate()`) and applies it in `Flush`, `Sync` and `FlushPages`, gating on the highest `page_lsn` in the batch. An ungated store flushing a logged page is exactly the violation this rule names.
2. **Commit-before-ack:** a `D1/D2` commit is acknowledged (`S_TXN_OK`) only after its commit record is durable.
3. **Checkpoint honesty:** `CHECKPOINT_END` is written only after every page in the checkpoint's dirty-page table has been flushed under rule 1, or remains listed with its recovery LSN.

## 9. Page LSN & Idempotent Redo

`page_lsn` lives at offset 8 of the **common 32-byte page header** on every headered page (`docs/spec/page.md` §2) — heap, B+ tree, undo, catalog, superblock, free-map. Redo replays a record iff `record.lsn > page_lsn`, making replay idempotent and restartable. A headerless page has no `page_lsn` and is never a replay target (§2).

## 10. Torn-Page Protection

Adopted with the checksum decision (`docs/spec/page.md`): **full-page images.** The cadence - the first modification of a headered page after each checkpoint logging a `FULL_PAGE_IMAGE` - is **not built**; images are logged by the paths that log one today: an index build's tree, a bulk fill's pages, a Bound Cabin chain's old tail (`docs/inflight/known-gaps.md`). Recovery restores an image before replaying deltas. The doublewrite-buffer alternative is rejected (extra file, second write path; FPI composes cleanly with either topology). Division of labor: the header **CRC32C detects** a torn/corrupt page at load; the **FPI heals** it during recovery. Cost is log volume proportional to checkpoint cadence — an explicit RTO/volume trade on the same knob (§11).

## 11. Checkpointing `[PROPOSED]`

Fuzzy checkpoints, run as a `system`-group task per core - **a task since BI-S2**: the cadence's timer callback only submits it (`Checkpointer::SubmitRun`), and it takes `Start`, each step and each publish batch in a poll of its own with a yield between, so a run no longer holds its core's reactor for its length (BI, `instructions/v3.0.0/workorder-bi-checkpoint-off-the-reactor.md`). The gate's hold lives in the checkpointer, never in the task's frame, and shutdown abandons every core's run before the first shutdown checkpoint, which then starts from its own `CHECKPOINT_BEGIN`. **The gate rotates cadence attempts** (BI-Q7 (a)): among the cores that asked within one period it admits the one whose last entry is oldest, where a first-come gate let a run longer than `period / cores` starve some cores for good; shutdown's and mount's attempts are first-come — **each core checkpoints its own active transactions, and one checkpoint runs in the instance at a time** (AT-S8). The pool every checkpoint walks is the instance's (`page.md` §6), so the dirty set is the instance's; the active-transaction table is not. Each core's `TransactionManager` holds its own live set, unlatched, and recovery's analysis needs every live transaction's undo head in some `CHECKPOINT_BEGIN` inside the replay range — so a single gathered checkpoint would need an instance-wide table, which the operator declined at AT-S8 in favour of this: every core keeps its checkpointer, `wal::CheckpointGate` admits one run at a time and a cadence tick that finds another core's running skips, and each core's cadence starts `core_id / cores` of a period late so the ticks do not meet every period. A skip costs that core's contribution to the fold a later redo start, never an answer. Every core publishes into the one `SuperBlockCheckpointAnchor` **itself**, under the superblock latch `rules.md` §3 declares. Step 3 publishes into the fold of §3:

1. Emit `CHECKPOINT_BEGIN` carrying the active-transaction table (each entry with the transaction's `last_undo_ptr`, `docs/spec/txn.md` §3.3) and the dirty-page table (`BufferPool::DirtyTable()` — `{page_id → recLSN}`, `docs/spec/page.md` §8).
2. Flush dirty pages under §8-1, paced across the checkpoint window - one step of `pages_per_step` (64) pages per poll of the run task - and not SLO-throttled: no controller exists. **Every wait is a park**: the log's, once for the whole snapshot after `Start` and then for a page re-dirtied since, as §8-1 says; a step asks for no data-file `fsync` (BI-Q13) - the publish's parked sync of its collection, on the instance's one data-sync thread (`storage/data_syncer.hpp`, BI-S4), covers every step's writes before the anchor's page. A step's `pwrite`s stay on the reactor; BI-S1 measured them at 0.2-4 ms at p90 for a step, with stalls in the kernel's writeback throttle the outliers. **A step writes no free-map region** (BI-Q12): the maps it would write carry the bit of every page allocated so far, and a crash between steps left an unlogged page allocated and never written. **Each page is copied under its page latch, shared, and cleaned only if nothing re-dirtied it after the copy** (AT-S8 step 1b, `page.md` §6): otherwise writeback on one core could copy another core's half-written page and clear its dirty mark and recLSN, so a committed change could drop out of the next checkpoint's dirty table and the redo start pass it. **And a page another writeback has claimed is waited for and looked at again** (AT-S10e, `page.md` §8), so an older copy never lands after a newer one: without it the disk could sit one write behind a frame that read clean, a loss this checkpoint's anchor would then persist past.
3. Emit `CHECKPOINT_END`; **after it is durable**, persist the redo start (`min(recLSN)`) into the superblock anchor (§14-3). **The cadence's publish is paced** (BI-Q5 (a)): every page dirty at that point is written in steps' batches, deferring on the log as a step does, then the maps, then one parked data-file sync; only then is page 0 encoded (`SuperBlockCheckpointAnchor::Encode`), written and synced, parked, and committed - the count, `D` and the recycler. The anchor therefore reaches the device after a sync of every page it stands for, including a snapshot page another core's writeback carried and no step of the run synced. A synchronous publish (mount, shutdown) is the whole-store `Sync` it was. **A failed data-file sync stops the instance** (BI-Q3 (a), `storage/data_syncer.hpp`): every data-file sync goes through one gate, one at a time and sticky, the store writes nothing back after a failure, and the server fail-stops the log and aborts, because frames the pool calls clean may hold bytes the device dropped and only a restart replays the log over them. recLSN 0 — a page dirtied but described by no record — is skipped, not `min()`ed in; with no logged page in the snapshot the redo start is the `CHECKPOINT_BEGIN` LSN itself.
4. **Segments wholly below the durable redo start are recycled** (BC, `instructions/v3.0.0/workorder-bc-wal-recycling.md`). Archiving does not gate it (BC-Q1 (a)); **since BR the archive's floor and an open backup's pin join the bound** at the one place it is computed - the recycler `Expeditor` hands the anchor runs `min(D, pin, archive floor)` under the backup control's hold (`docs/spec/backup.md` B3, B11), and the log device keeps a detached segment the archiver has not reached.
   - **The bound is `D`**, the redo start of an anchor a publish's store sync returned OK for - never the in-memory fold, which a failed sync leaves ahead of the platter. A segment `s` is removed when `(s + 1) × segment_size ≤ D`; the segment holding the append point never is.
   - **The fold never decreases**: every publish encodes the maximum of the fold and the highest anchor already encoded. A page dirty at recLSN 0 in one core's snapshot can show an older recLSN in the next core's, so the fold alone can step back, and a lower anchor written after segments were removed would send the next mount to a segment that is gone. A valid redo start stays valid - every later record has a higher LSN and the data file only gains - so the higher of two valid starts is one.
   - **When the bound does not move**: with `checkpoint_interval_ms = 0` no cadence tick runs, and the anchor moves only when another path completes a checkpoint; the warm-up holds it at the mount's until every core has published (§3); an anchor of 0 has never been published and recycles nothing.
   - **What removal costs**: the unlinks and one directory sync run on core 0's writer thread right after a pass's sync, so a peer's commit that asks during them waits them out, and a stream of commits cannot starve them. The filesystem frees a removed file's blocks at its last close, which can be a syncing thread's.

Cadence is the RTO knob: more frequent ⇒ shorter recovery + more FPI volume.

## 11a. What logs today

**Every data mutation and every catalog mutation**, as the ordinary record types: `kHeapInsert` (a heap page) or `kBtreeInsert` (a B+ tree leaf)/`kHeapOverwrite`/`kHeapDeleteMark`/`kSlotRetire` per row, one `kBtreeSplit` per B+ tree split, `PAGE_INIT` for a catalog overflow page, a relation's root and its var-heap root, a `FULL_PAGE_IMAGE` for a chain-link edit and for each page of a backfilled index tree. There is no catalog-specific record type.

Verified against the emission sites:

| Path | Records |
|---|---|
| `INSERT` | `TXN_BEGIN` → `HEAP_OVERWRITE` of the `sys.tables` id bump (the record that makes the id ceiling durable, `docs/rules/keystoneid-k0-findings.md`) and **`UNDO_WRITE{kVarHeapAppend}` → `VARHEAP_APPEND` per spilled cell**, in the pipeline's order for the row's arity and storage (`docs/spec/heap-and-tuple.md` §4.1) → `INDEX_INSERT` per index → `ASSERT_RESERVE` where an assertion covers the row → `UNDO_WRITE{kInsert}` → the row: on a heap `HEAP_INSERT` (with `FULL_PAGE_IMAGE` + `PAGE_INIT` when the chain grows), on a btree `BTREE_INSERT`, or one `BTREE_SPLIT` carrying the row when the insert split the leaf → `TXN_COMMIT` |
| `UPDATE` | `UNDO_WRITE` (before-image) → **`UNDO_WRITE{kVarHeapAppend}` per spilled cell** → `VARHEAP_APPEND` per spilled cell → `INDEX_INSERT` per touched index → `HEAP_OVERWRITE` |
| `DELETE` | `UNDO_WRITE` → `HEAP_DELETE_MARK` |
| rollback | the compensations of `docs/spec/txn.md` §6 — `SLOT_RETIRE` / `HEAP_OVERWRITE` / `HEAP_DELETE_UNMARK` / `VARHEAP_RELEASE` — then `TXN_ABORT` |
| assertions | `ASSERT_BUILD` at CREATE, `ASSERT_RESERVE` / `ASSERT_COMMIT` / `ASSERT_ROLLBACK` on the write paths, `ASSERT_DROP` at teardown |
| checkpointer | `CHECKPOINT_BEGIN` / `CHECKPOINT_END` |

**Ordering rules**, each load-bearing and enforced:

1. `VARHEAP_APPEND` and `INDEX_INSERT` both precede the row record whose cell or entry points at them - `HEAP_INSERT`/`HEAP_OVERWRITE` on a heap page, `BTREE_INSERT`, the `BTREE_SPLIT` carrying the row, or `HEAP_OVERWRITE` on a btree leaf (§5.2, `docs/spec/index.md` §12.1) - for opposite pointer directions and the same reason — the surviving direction is the harmless one.
2. An `UNDO_WRITE{kVarHeapAppend}` precedes the `VARHEAP_APPEND` it can undo, so redo alone can never resurrect an append the undo phase has no record to release; a crash between a spill and its tuple write rolls back like any other loser write. **Gap:** a spill logged with `kNoTxnId` (`LogChainInsert`'s path, taken by the assertion catalog) has no transaction to chain to and no record, so a rolled-back one leaks; nothing sweeps it.
3. A catalog write's `UNDO_WRITE` precedes its row record — redo alone must never resurrect a row the undo phase has no record to retire.
4. A catalog record's **envelope names the acting transaction or `kNoTxnId`, never the header's writer**: analysis notes every named envelope as a loser until a commit in range says otherwise, so a `next_id` bump logged under the relation's long-committed creator would invent phantom crash losers.

One safety note the relation-root `PAGE_INIT`s rest on: they are deliberately unstamped (the first row record stamps the page), and a root that never receives a row is protected by the **checkpointer flushing every page in its snapshot** before `CHECKPOINT_END` — the safety lives in that flush, not in a stamp.

**DDL logs.** DDL runs under a real transaction (autocommit included), its catalog writes log the ordinary types with undo records a crash loser's mount rolls back through, and `SHOW META` prints `ddl_durable=1 catalog_recovered=1` (`docs/spec/txn.md` §7, `docs/spec/ddl-transactional.md`). The **row-codec definition relations** (`sys.assertions`' source rows) log through `exec/wal_row_log.hpp` — the same order rules, `kNoTxnId` envelopes — so an acknowledged `CREATE ASSERTION` survives and **enforces** after a crash. Two rules ride with that: every transactionless DDL statement — assertion, cabin, ALTER — has no commit record for the durability class to ride, so `kStrict` **and `kGroup`, whose durability point is D1's**, sync at the acknowledgement (`AwaitDdlDurability`); and redo has a `kCabinBound` arm, because `BoundCabinPage::Format` writes a body whose `next_page_id` a zeroed page misreads as page 0. There is no genesis arm for assertion recovery: the publish-time `ASSERT_SNAPSHOT` (`assertion_catalog.cpp`) covers a declaration born after the last checkpoint, and an arm ordering itself before it could adopt an under-counted base over that better one.

**Outside the log, precisely:** `ALLOC`/`FREE`, reserved in the record enum and emitted by nothing, and the **advisory Waystone classes** — trail pages (`stats/trail_store.cpp`) and directory pages (`stats/waystone_dir.cpp`) — which invariant 8 exempts by construction: deleting them wholesale must never change a result, so they owe the log nothing. Nothing *authoritative* is outside.

Three properties of the INSERT path are the shape the other paths copy or deliberately do not copy:

- **The `FULL_PAGE_IMAGE` on chain growth stands in for a missing record type.** Growth mutates two pages: the new page, and the *old* tail whose `next_page_id` now reaches it. §5.2 has no record for a link edit, so the old tail is logged whole. It costs one page of log per page of heap — about +50% log volume on small rows, paid once per 8 KB of tuples, never per tuple. A link-edit record type would be a format-version event.
- **An insert's records are appended under the holds that placed it** (AT-S21) - §8-1, made true of the insert. With a write on every core, a record appended after its page is released would be wrong three ways - another core dividing the leaf a `HEAP_INSERT` names, writing back a split's parent before the split's pages are logged, and shifting the index entry an `INDEX_INSERT` was re-read from - each reproduced across a crash by `insert_log_crash_rig_test.cpp`. The storage call hands back the pages it changed, still held (the leaf and a split's secured parents; a heap chain's tail); a page it created is reachable only through them. Index maintenance logs each entry under the index tree's hold, from the bytes the tree placed, and a root it grew inside its split's record; a spill keeps its var-heap page held until its `VARHEAP_APPEND` (which still follows the spill's undo record, RV3). `LogInsert` releases every hold after the row's stamp and before an own transaction's commit. **A split logs every page it writes in one `BTREE_SPLIT`** (BD-R12), its new leaf as an image rather than a `PAGE_INIT`, which formats a page with no right link. **On a btree, a placement whose record is never written is taken back** under the still-held leaf at every failure exit before the record (index maintenance, the assertion reservation, the undo append, the spills' noting): its slot is removed and its bytes returned, so no later record's slot assumes a row redo never sees; a split's row is retired and the split logged under `kNoTxnId`. The paths that still log after release are named in `docs/inflight/bugs/records-appended-after-their-page-is-released.md`. **A cost, narrowed at BA-S13**: a transaction-id carve persists page 0 alone (`DevicePageStore::PersistPage`): it waits for page 0's latch and claim and no other frame, and its unconditional `fsync` covers whatever else is unsynced in the data file. The pool's other dirty frames, which a carve used to write back and sync, are now the checkpoint's to write, which lengthens its stall (`bench/v3.0.0/results-ba-carve-diag-v2.7.0-736-ge5a7e1b7.md`). The next block is carved ahead, on the `system`-group tick, once three-quarters of a core's window is issued, so a `BEGIN` carves on its own path only when the tick has not got there first.
- **A failed append aborts the write scope.** The statement runs inside one, and a failed append aborts it, which retires the slot through the ordinary rollback compensation — so the row does not survive unlogged. It holds only where a `TransactionManager` is wired in; a dispatcher built without one leaves the row.

Transaction ids come from `docs/spec/txn.md` §4.2's block-reserved allocator over a superblock field, and the abort path lives there too (`docs/spec/txn.md` §6).

## 12. Recovery `[PROPOSED]`

Restartable, and once per log — which is once per instance (§3). Core 0 runs the three phases over the whole log before any peer is constructed. A peer runs no pass.

1. **Analysis:** from the superblock's redo start — the fold's, slot 0 — scan to the durable end (§4.2 torn-tail rule); rebuild dirty-page and transaction tables; classify winners (commit record seen) and losers. A retired kind - `TXN_PREPARE`, `PAGE_HANDOFF` - refuses the mount `Corruption` (§3). **A page's entry is the oldest LSN it must be replayed from, and an entry of 0 gives way to the first LSN that reaches it**: a `CHECKPOINT_BEGIN` lists a page an unlogged path dirtied - mount's own redo among them - at recLSN 0, and kept at 0 the page pulled nothing into the redo start, so its next record could lie below it and never be replayed.
2. **Redo:** replay idempotently (§9), restoring `FULL_PAGE_IMAGE`s first per page. A redo start at or past the scan's end has nothing to replay and scans nothing (BR): with no page dirtied, analysis puts the start at the end it reached, which for a log whose last segment is sealed is the first LSN of a segment that does not exist. **Redo never starts below the scan start** (BC-R2): analysis seeds its dirty-page table from every `CHECKPOINT_BEGIN` in range, and a page an older one lists - written back since and clean - can sit below the anchor, so the recomputed start can fall below where the scan began; those records change no page while the anchor is valid, and once recycled they are not there to read. `SHOW META` prints `recovery_redo_start` and `recovery_redo_start_recomputed` when the floor raised the start. A scan from the head floors at nothing; a checksum-failed page (`docs/spec/page.md` §10) with an available FPI is restored from it. Redo reconstructs crash-time state including uncommitted changes and undo pages. A `BTREE_INSERT` is replayed only at the slot its key sorts to, and a `BTREE_SPLIT` whole (§5.2). It writes no stamp; the header's `flags` word is the format's 0 (`docs/spec/page.md` §2b).
3. **Undo:** roll back losers through their undo chains (`undo_ptr`), emitting compensation as ordinary logged page mutations so undo itself is crash-restartable. Delete-marks by loser transactions are cleared the same way. A loser's row on a B+ tree leaf is re-found by its key, in the recorded leaf and then rightward, and only a version the loser wrote is compensated (`docs/spec/txn.md` §3.3).
4. Recovery completion writes a checkpoint, bounding the next crash's work.

A crash during recovery at any point resumes correctly — enforced by the test matrix (§16).

## 13. Business & Operational Features

- **Configuration:** global durability class + per-transaction override (wire-protocol §9); `D3` flush interval; checkpoint cadence. **The segment size is not a setting**: it is 64 MiB on every volume, a constant of the format (§4.1). **There is no retention setting** (BC-Q4): every segment wholly below the durable redo start is removed, so what the log keeps is set by the checkpoint cadence, the RTO trade it already is.
- **Archiving, backup and PITR - built since BR** (`docs/spec/backup.md`): every sealed segment is archived in order under the volume's lineage (`archive_dir` or `archive_command`), read by an archiver thread off the durable LSN rather than hooked into the roll, so BR adds nothing to the stream latch's hold but one `AppendAndSeal` per backup. A base backup or a snapshot backup plus the archive gives point-in-time recovery to an LSN. `BACKUP_BEGIN` (31) and `BACKUP_END` (32) bound a backup's window in the log; redo passes them.
- **Replication readiness:** the sealed-segment/stream tap is the future log-shipping source. No format concession needed now; the constraint is only "never break §4 self-description".
- **Observability (ship with the first flush path):** durable-vs-appended LSN per log, flush latency percentiles, group-commit batch sizes, ring-full stall time, checkpoint duration, FPI volume share, undo retention headroom, recovery phase timings. Financial operators tune RPO/RTO with these; they are product features, not debug aids. **Recycling's**, on core 0 since BC: `wal_first_segment`, `wal_segments_removed` and `wal_remove_failures`; and `wal_stopped=1` once the stream has fail-stopped (§6-5). **The segment roll's**, since BQ-S1 (BQ-Q3 (a)), the stream's totals printed on every core and never summed (§3): `wal_append_lsn` (its delta over a window is the log written in it), `wal_rolls`, `wal_roll_hold_us` and `wal_roll_hold_max_us`, the steps' times (`wal_roll_seal_us`, `wal_roll_flush_us`, `wal_roll_sync_gate_us`, `wal_roll_sync_us`, `wal_roll_sync_tail_us`, `wal_roll_sync_rest_us`, `wal_roll_create_us`, `wal_roll_body_wait_us`, `wal_roll_body_us`, `wal_roll_header_us`, `wal_roll_rename_us`, `wal_roll_dirsync_us`), the segments a roll's sync covered (`wal_roll_sync_segments`, `wal_roll_sync_segments_max`) and the body's outcome (`wal_roll_body_hit`, `wal_roll_body_waited`, `wal_roll_body_inline`); per core as `load_c<k>_*` and summed as `contention_*`, the drains' stream-latch wait (`wal_drain_latch_wait_us`) and the waits a roll's hold covered (`wal_roll_blocked_waits`, `wal_roll_blocked_wait_us`). Every roll also logs one Info line, `[wal] roll seg=...`, with its steady-clock start, end and steps.

## 16. Testing Requirements

All deterministic (injected clock + `IoBackend` fault injection; rules.md §4). Crash-consistency tests are the shipping condition for every WAL-touching change:

1. **Format:** record/segment codec round-trips; alignment; torn-tail detection (truncate at every byte boundary of the last record); 48-bit txn_id upper-bits-zero assertion.
2. **Ordering:** instrumented backend proves §8-1..3 under randomized scheduling — no data write ever precedes its log durability; `MarkClean` unreachable outside flush completion (shared test with `docs/spec/page.md` §18-4).
3. **Crash matrix:** crashes injected at every phase boundary (append / partial segment write / between commit-durable and ack / mid-checkpoint / each recovery phase); recovery yields exactly the acknowledged-commit state; replaying recovery twice is a no-op.
4. **Torn writes:** partial-page and partial-record corruption injected; checksum detects at load, FPI restores in recovery (composition test with `docs/spec/page.md` §18-5).
5. **MVCC records:** delete-mark by a winner survives; delete-mark by a loser is cleared by undo; `UNDO_WRITE` chain links (prior writer id + prior undo_ptr) reconstruct validity intervals with no `xmax` anywhere — a reader fixture verifies visibility across a rebuilt chain.
6. **Durability classes:** `D1/D2` never lose an acked commit under any injected crash; `D3` loss bounded by the configured window — bound asserted; `RELAXED` flag present on D3 acks.
7. **Group commit:** N concurrent committers, one flush; all resume with durable LSN ≥ their commit LSN.
8. **Backpressure:** ring saturation suspends producers without deadlock; stall metrics visible.
9. **Topology:** a peer's writes are recovered by core 0's single pass and a peer runs none — plus the shared-stream cells: concurrent appenders each landing at the LSN they were handed, no LSN twice, the durable watermark never retreating, and a peer's `strict` commit made durable by core 0's writer with the peer's own sync count at zero.
