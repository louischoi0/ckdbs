## 2. What ran, and what did not

- **The tree.** A new worktree, `audit-core12-slices`, at `0b98bc4f` - the
  head of `origin/main` then, F1-F25's fixes included. It was made apart
  from `audit-lean-and-correct` because two other sessions were editing that
  one (F15 and F26-F32 in one, F4 in the other); what they changed after
  `0b98bc4f` is not in the tree read here, and touches the dispatcher and the
  expeditor only.
- **The method.** The first run's workflow, cut to these twelve slices:
  one finder per slice, the slice files and its rules as the first run gave
  them (at most six findings, bugs first, each with a failure scenario traced
  through lines, a behaviour-preserving fix for anything not a bug, and
  nothing `known-gaps.md`, `docs/inflight/bugs/` or the first run's entry
  already records). Then, per finding, verifiers told to refute it and to
  answer "refuted" when in doubt: a logic defect by two, one tracing the
  code path and one asking whether the behaviour is intended or known (spec,
  `known-gaps.md`, a test that pins it, the work order behind the lines);
  dead code by one asking whether it is really dead; duplication and
  complexity by one asking whether the change is behaviour-preserving and
  worth it. A finding survives only if every verifier assigned to it
  answered and none refuted it.
- **Finders: 12 of 12 returned**, 66 findings between them. What each says
  it read, did not reach, and checked and found sound is section 3, in its
  own words.
- **Verifiers: 25 of 99 returned.** The first pass, on 2026-11-13, lost 78
  to the five-hour usage limit; a resume on the same day reran those 78 from
  the cached finders and lost 74 to the model's weekly limit. The 25 that
  returned are behind G1-G15, G21, G24, G65 and G66.

  the four sweeps (`sweep-dead-upper`, `sweep-dead-lower`, `sweep-vestigial`,
  `sweep-config-hygiene`). The absence of a finding for any of them says

#### G1. WalStream::Open publishes the scanned tail as durable without syncing it, so a mount writes data pages ahead of an unsynced log

`src/wal/stream.cpp:84` - finder's severity **high**, finder's confidence **medium**, slice `wal-write`

Symbols: `WalStream::Open`, `WalStream::ScanTail`, `WalDurability::IsDurable`, `DevicePageStore::AwaitWalGate`, `CheckpointAfterRecovery`

**Claim.** Open sets durable_lsn_ = append_lsn() after ScanTail, on the comment "whatever is already on the device is durable by definition". After a process crash (SIGKILL, abort, OOM) the tail it scanned sits in the OS page cache, pwritten but never fdatasync'ed. FileLogDevice::Open syncs nothing. The store's WAL gate then reads IsDurable(page_lsn) as true for every replayed page, and the mount's completion checkpoint writes and syncs those pages before the first log sync.
