# CLAUDE.md — KDS Storage Engine

Working guide for AI development agents. `docs/heap-and-tuple.md` is the authoritative design spec; this file summarizes it and adds working rules. When the two conflict, the spec wins — flag the conflict instead of guessing.

## What This Project Is

KDS is a **userspace OLTP-specialized database storage engine written in C++**. Its purpose is fast and *correct* OLTP performance through two engine-native mechanisms:

1. **Engine-driven physical page optimization** — runtime statistics reorganize where tuples physically live, not just how the optimizer plans.
2. **Waystone** — a record of where a previous execution of a query pattern found its rows, so a repeated pattern can look directly instead of searching.

Target domain: financial systems. Feature scope is deliberately narrow; do not add general-purpose DBMS features unasked.

**KDS is userspace software.** Do not introduce kernel-module code, kernel headers, or kernel-only APIs.

## Core Architecture

See `docs/heap-and-tuple.md` for the full detail; this is the map.

- **Pages:** 8 KB. Page ids are `uint32_t`; 16 TB capacity = 2^31 pages; `0xFFFFFFFF` is invalid. Never signed.
- **Fixed-length tuples and the tagged cell** (`docs/heap-and-tuple.md` §§3.3-3.4, invariants 13-14): a relation's row size is a **schema constant**, cell offsets are computed from the schema, and every variable-width value occupies one **tagged cell** of `kds.inline_cell_width` bytes — tag `kNull` / `kInline` / `kSpilled`, the tag byte distinguishing NULL, empty and spilled without touching the var-heap. The rule exists for **tuple mobility**: an UPDATE can never migrate a tuple, so with the immutable `min_key` a tuple's address is stable for life until relayout moves it on purpose — which is what stops an UPDATE from burning Waystone entries through epoch churn, and makes relayout a cell-`memcpy` with exact fill-factor math. The width is a **global instance-pinned** constant, not a per-column declared width: one number instead of a schema decision users get wrong, one codec path, and no `VARCHAR(n)`/`ALTER WIDEN` surface at all — paid for in uniform padding on short values. Default 64 bytes, `[OPEN: value]`, configured by the `inline_cell_width` config key. Values too long to inline spill to the **var-heap**, whose whole design goal is to be boring: values are **immutable per version**, appended and never rewritten or moved, so an old-version reader follows an old pointer to bytes that cannot have changed — MVCC correctness for free, no epoch on the pointer, relayout-exempt by construction, and reclamation rides on purge. **Status: the whole rule is in code, var-heap included** (`docs/rule-fixed-length-tuple.md` §§8a-8b). The cell format is `include/kds/storage/tagged_cell.hpp`; the row-size constant is `catalog::RowLayout` (`include/kds/catalog/schema.hpp`), built once per relation at `Catalog::InitTableAccess()` and carried on `TableAccess`; the codec reads static offsets and answers `Corruption` on a payload-size mismatch (`src/exec/row_codec.cpp`); the width is pinned in the superblock at body offset 36 with a mount-time check naming both values (format version 3 → 4, and 4 → 5 when the var-heap grew `SysTableRow` — so **every pre-existing data file stops mounting** — V5 working as intended; note that a *catalog row* format change needs the same bump, since without one the file mounts and then fails opaquely on its first catalog read). The var-heap is `include/kds/storage/varheap.hpp`: `PageType::kVarHeap = 10`, a **per-relation chain** rooted at `sys.tables.varheap_page_id` and allocated at `CREATE TABLE` for any schema that can spill, `RecordType::kVarHeapAppend = 16` logged *before* the `HEAP_INSERT` that points at it. Three things to know before touching it. **Decode does not resolve a spill** — `DecodeRowInto` reports a pending spill and the caller fetches through `ResolveSpills` after releasing its page span, because resolving inline would put a page fetch under the very span `parser-v2.md` I15's R1 and the step VM's `PageSpanGuard` exist to forbid. **The var-heap root is DDL-immutable** — allocated eagerly, never moved by chain growth, which is the only reason it may live on a cached `TableAccess` at all (`catalog_cache.hpp`'s rule). And **nothing reclaims**: reclamation rides on purge, which does not exist, so a shortened or superseded value's bytes stay. Two consequences a caller sees: an UPDATE can no longer fail with `OutOfSpace` on a grown `varchar`, and **`float` columns are refused at `CREATE TABLE`**, because a fixed row size must reserve a width for every column and reserving one for an undecided encoding would be half of settling it. `decimal` was refused for the same reason and **no longer is**: the types work settled its encoding (`docs/spec-types.md`, workplan `TY01`-`TY09`), so `DECIMAL(p, s)` declares, stores and reads back as of TY04, alongside `DATE` and `TIMESTAMP`. `float` stays refused — nothing settled *its* encoding. A value larger than one var-heap page (8144 bytes) is `Unsupported` — the §9 spilled-value cap is still open and a multi-page representation is what would decide it.
- **Semi-sorted heap:** every heap page header holds an **immutable `min_key`** plus a mutable **epoch counter** (bumped when tuples on the page move; storage location `[OPEN]`). A tuple with `id < min_key` can never be placed in that page. Tuples *within* a page are unordered. `min_key` immutability is what lets readers prune by key range without locks. **A relation is a chain of heap pages** linked through `next_page_id` and rooted at `sys.tables.desc_page_id` (`include/kds/storage/heap/heap_chain.hpp`): inserts go to the tail, a full tail grows the chain by one page whose `min_key` is the id that caused the growth, and nothing is split or moved — so each page's ids sit entirely below the next page's `min_key`. The **heap page split policy is open**, and there is no free-space reuse on earlier pages until page compaction exists.
- **Clustered B+ tree:** the alternative storage form, chosen per relation at `CREATE TABLE` (`clustered_type`). A **leaf is a heap page**, so the row codec, `PageView` reads and overwrites, and `HEAP_INSERT` redo all work on either. On a btree relation a pk point lookup descends and the descent is **authoritative** — a miss means the row does not exist. A heap relation has no pk index and scans the chain.
- **Keystone column:** every tuple's mandatory first column is one 64-bit word: `id:40 | flags:8 | reserved:16`. The flags byte is the transaction byte (Oracle lock-byte style); tuple liveness lives in the slot directory. The reserved 16 bits are written 0 and ignored; repurposing is `[OPEN]`.
- **Waystone:** `(pattern_id, arg_hash)` — `patternX(a, b)` — maps to the Keystones a previous execution of that pattern instance found, **across relations, in one page** (`docs/waystone-concpets.md`). Patterns are catalog objects in `sys.patterns`. The trust model is forced by invariant 9, not chosen: **a waystone may replace a *lookup*, never a *search*.** A stored set trusted as complete would be authoritative, and a set missing a row inserted since it was recorded is wrong in a way no per-tuple validation can detect, because absence has no witness. So a pk-equality step or a nested-loop pk probe may be served from a trail; a non-pk predicate, range, or scan still searches, and the trail may only prefetch for it. Every replayed entry is validated — `rel_oid` plus the Keystone id at the recorded `(page_id, slot)`, then the page epoch, then MVCC visibility exactly as the authoritative path would apply it — and any miss falls through for that step alone. **Status: recording and replay both work (P01-P13); retention, decay and epoch bump sites do not (P15-P17).** A repeated pattern instance is served from a validated recorded location instead of a descent or a chain scan. **The recorder** is `include/kds/stats/trail_recorder.hpp` (policy, sightings, auto-registration) over `trail_store.hpp` (one page per trail); **replay** is `include/kds/exec/trail_replay.hpp` consulted from `ChainRunner::TryReplay()` in the step VM. The executor's only knowledge of either is `exec::TouchedTuple` - five integers, no page format - which is what keeps spec §1's "Waystone lives outside the executor" structural, and is forced anyway since `stats/` already depends on `exec/`. **Replay replaces a descent, never a decode**: a trail supplies a `(page_id, slot)` to the same `AcceptTupleAt()` a descent feeds, so a hit and a miss run identical code from the tuple onward - the same argument the probe memo rests on, and the whole reason turning replay on cannot change a reply. Five things to know. **Only lookup-class steps are recorded or replayed** - invariant 9 forbids a trail replacing a search. **Rule 0 is the lookup key**: the replay index is keyed on `(step_id, pk)`, so an entry is only found by matching the freshly re-derived probe key, which is I17's mandatory join check made structural rather than remembered. **A trail is one page and is never truncated** (>253 entries means no trail). **Recording is n=2 observed / n=1 declared**, nothing is recorded on the failure path, and an execution that collects nothing is not even counted. And **two validation gaps that replay now depends on**: there is no page epoch, so rule 2 is unenforceable - safe only while a tuple's address is stable for life, which means ***the epoch must land with relayout, whichever comes first*** - and nothing verifies a page still belongs to the relation it was recorded from, which holds only until pages can be reallocated between relations. `tests/waystone_contract_test.cpp` is the suite that keeps all of this honest: five configurations compared byte for byte, including a deliberately corrupted trail. **Measured (`bench/results-waystone-v2.md`): 22-31x faster on a heap relation, 13-15% slower on a btree one** - the btree loss was `FingerprintOf`'s second lex, and **folding the fingerprint into the parse (2026-08-03) cut it to 3-6%**: the lexer feeds a `FingerprintAccumulator` as it produces tokens, so a parse yields `pattern_id`/`arg_hash` free and `FingerprintOf()` is now only for callers holding a string and no parse. `kFingerprintVersion` did not move and the golden corpus pins that, with a differential test comparing both paths over every statement in it. **Zero-copy tokens followed** (2026-08-03): `Token::text` is a `std::string_view` into the statement, so lexing allocates nothing and a `Token` is trivially copyable - the AST still copies every name it keeps (I4's copy-at-the-boundary rule), which is what lets a `Statement` outlive the SQL. **A token must not outlive the SQL it was lexed from**; nothing catches that for you. Together the two changes cut Waystone's btree overhead from +13-15% to +3-7% and made the parse itself 3-8% faster for every statement. `waystone_recording` and `waystone_replay` are the switches, both default on. The directory is a hash directory, so deepening it preserves only the mappings whose new top digit is zero — growth is a cache flush, safe by invariant 8 and self-healing on the next execution (`docs/waystone-concpets.md` §5).
- **Page-latch consistency:** there is no enforced single canonical in-memory tuple. Consistency is kept per-page: a frame is pinned and latched (shared for reads, exclusive for structural mutation) for the duration of an access, and tuple bytes are read and written directly within it. Latching is core-local (thread-per-core/shared-nothing, `docs/rules.md` §3) — it serializes cooperative tasks on the owning core, it is not a cross-core lock. Executors may hold private working copies; these are ephemeral projections, not competing canonical copies.
- **WAL:** physiological redo log, one stream per core, LSN = stream-local byte offset (`docs/wal.md`). Durability classes D1 strict / D2 group / D3 relaxed are a per-transaction property. WAL-before-data is store-enforced: a frame is not flushed until `durable_lsn ≥ page_lsn` (`DevicePageStore::SetWalGate()`, applied in `Flush`/`Sync`/`FlushPages`). Superblock anchors hold a `kMaxWalCores`-slot table indexed by `core_id` carrying `{checkpoint_lsn, redo_start_lsn, durable_lsn, segment_no}`; the checkpointer publishes into it only after `CHECKPOINT_END` is durable, and an all-zero entry means "replay from the start of the stream". **INSERT is the one logged statement**: `TXN_BEGIN` → (`FULL_PAGE_IMAGE` of the old tail + `PAGE_INIT` of the new one, only on chain growth) → `HEAP_INSERT` → `TXN_COMMIT`, with the class set by the `durability` config key (default `group`). The FPI is there because growth mutates the *predecessor's* `next_page_id` and no record type describes a link edit; it costs about +50% log volume on small rows, and a `HEAP_CHAIN_LINK` record type would retire it. Measured on an EBS gp3 volume, single connection: 802 inserts/s strict, 798 group (a batch of one is a batch), 6,332 relaxed, against 7,673 unlogged. **`CREATE TABLE` and all catalog rows are unlogged, and recovery is not implemented** (`UPDATE` and `DELETE` are logged as of the transaction work — `HEAP_OVERWRITE` / `HEAP_DELETE_MARK`, each preceded by its `UNDO_WRITE`) — nothing reads the log back, so a restart is protected only by `PageStore::Sync()` at `SYNC` or clean shutdown.
- **MVCC:** tuple headers carry `trx_id` (48-bit writer) / `undo_ptr` / `data_len` / flags — 20 bytes, **no `xmax`**: the undo chain encodes validity intervals, so the boundary is never stored twice. DELETE is a delete-mark — slot flag `DELETED` plus the deleter's `trx_id` — distinct from physical slot retirement (`DEAD`).
- **Transactions and MVCC (`docs/txn.md`, workplan `docs/txn-workplan.md` `T01`-`T14`) — built.** Exactly two isolation levels: `READ COMMITTED` (default; read view per statement) and `REPEATABLE READ` (read view per transaction), settable by the `isolation` config key, `SET ISOLATION LEVEL` per session and `BEGIN ISOLATION LEVEL` per transaction — the same three-rung chain `durability` uses. `SERIALIZABLE` is out of scope, not open, and `ParseIsolationLevel` refuses it saying why. **A `Session` per connection** (`include/kds/server/session.hpp`) carries the level, the open transaction and the `failed-txn` flag; `TcpServer::Connection` owns one and `Dispatch(line, session)` takes it. **A null session means autocommit through the dispatcher's own**, which is what makes every pre-transaction caller behave identically. `failed-txn` admits only `ROLLBACK`/`ABORT`/`SYNC`/`STOP`/`PING` — a whitelist, so a statement added later is refused by default — and closing a connection with a transaction open rolls it back. **Undo is InnoDB-shaped** (`include/kds/txn/undo_page.hpp`, `undo_log.hpp`): headered `PageType::kUndo` pages, a 24-byte page header, 28-byte unpadded records, `undo_ptr = (page_id << 16) | offset` with 0 meaning "no predecessor" — unambiguous *structurally*, since page 0 is the superblock and offset 0 is inside the page header. Two chains that are not the same chain: `prev_page_id` links the log's pages in creation order for a purge that does not exist, `prior_undo_ptr` links one tuple's versions for readers. **An undo page is shared by every transaction** — one current page, appended to until it fills (2026-08-05). It was one page per transaction, and since an autocommitted statement *is* a transaction that cost a fresh 8 KB page per `UPDATE` for one ~88-byte record: 132 MB of data file for 16,414 updates, and the instance's whole ~510 MB page-id space exhausted after ~65,000 of them, after which every write failed. The same 45-second workload now writes 19 MB and sustains 1,344 TPS against 716 with 97,826 failures (`bench/results-txn-layer-budget.md` §3). Nothing was relying on the exclusivity — readers follow `undo_ptr` to a page and offset, rollback replays the in-memory trail, redo names each record's offset — and the header's `owner_trx_id` is now `first_trx_id`, a diagnostic that grants nothing. The layout did not move, so no format version did either. **INSERT writes no undo record** — `undo_ptr == 0` plus an invisible writer already means "no visible version" — so insert cost is unchanged and rollback of an insert reads the in-memory trail; `UndoRecordType::kInsert` is defined and never written so persisting that trail is a code change, not a format event. An undo page is FPI-exempt on the merits: `PAGE_INIT` plus its `UNDO_WRITE`s rebuild it exactly, and a test asserts that against the live page byte for byte. **The visibility predicate lives at one site**, `ChainRunner::AcceptTupleAt` — chain walk, btree descent, probe memo, Waystone replay and Cabin resolve all funnel through it, which makes Waystone §3.1 rule 2 structural rather than remembered. It is **split in two** because stepping back an undo record is a page fetch and `parser-v2.md` I15's R1 forbids one under a live span: `Classify()` answers with no fetch, `ResolveThroughUndo()` walks after the span is released over a fixed-size copy — taken *only* when the writer is invisible, so the ordinary read path pays one integer comparison. Measured at **1-2% on a full-relation scan and nothing on the write path** (`bench/results-txn.md`). **`trx_id == 1` (`kBootstrapXid`) is visible to every read view, permanently**, which is what makes every catalog row readable; `next_trx_id` is a superblock field (**format version 9**) seeded at 2 and handed out in blocks of 4096 `[PROPOSED]`, so a crash burns the remainder — ids are unique and monotonic, never gapless. Exhaustion is `OutOfRange`, never wrapped. **Write conflicts are first-updater-wins** — no lock manager, no waiting, no deadlock detection, and the Keystone lock byte stays unused; the loser gets `StatusCode::kTxnConflict` and the wire spelling `ERR TXN_CONFLICT retryable=1 row id=<n> was written by transaction <n>`, which is a compatibility surface and not a diagnostic. **Failure atomicity is per transaction, not per statement**: a statement failing inside an explicit transaction poisons the session and leaves earlier rows written, while an autocommit statement *is* its transaction and so unwinds. **`DELETE` exists now** (it did not before this work) and is a delete-mark, never a removal — first caller of `PageView::DeleteMark`, `RecordType::kHeapDeleteMark` and `UndoRecordType::kDeleteMark`, whose image is empty because a mark changes no tuple bytes. It does **not** touch the Cabin write hook: removal is forbidden by `feat-cabin.md` §5, because an older snapshot may still match through the undo chain. **`UPDATE` is logged now** (`UNDO_WRITE` then `HEAP_OVERWRITE`), where it was previously unlogged entirely and carried the old header forward. **Version identity is per logical tuple**, forced by the pk being unupdatable, `OverwriteTuple` keeping `(page_id, slot)`, and undo versions having no address. **Nothing purges**: readers are deliberately unregistered, so undo grows monotonically and `SnapshotTooOld` is structurally unreachable. **DDL is still not transactional** (§7) — catalog rows are stamped `kBootstrapXid` and catalog reads bypass the predicate, so `CREATE TABLE` inside a transaction is not rolled back. **The known gap this ships with (§8): MVCC ships before recovery, so an uncommitted row surviving a crash reads as *committed* on the next boot** — its `trx_id` is below the new high-water mark and in no live set. There is no cheap mitigation; closing it requires a persisted commit watermark, i.e. recovery. Do not attempt a partial one.
- **Cabin** (`docs/feat-cabin.md`, workplan `docs/cabin-workplan.md` `CB01`-`CB11`): a per-`(relation, non-pk column)` store that is **authoritative only for the values queries have observed** - the third trust class, between the clustered pk tree (always authoritative, always maintained) and the Waystone trail (never authoritative, free). The invariant is **observed ⇒ complete, superset form, per snapshot**: an observed value's entry set is a *superset* of the qualifying visible pks, and the surplus is subtracted at read time by verification - MVCC plus a re-check of the key equality, which is sitting in `Step::residual` because the compiler deliberately left it there. Three consequences, none of them preferences. **Maintenance is append-only**: INSERT appends if the value is observed, DELETE does nothing, UPDATE v→v′ appends to v′ and leaves v alone, and removing on the hot path is *incorrect* rather than merely unnecessary, since an older snapshot may still match through the undo chain. **A cap refuses to observe and never truncates a set**, because a truncated set marked authoritative is a wrong answer. **Un-observing is always legal** (§1's corollary), which is what lets an authoritative structure be evictable and is the correct response to any failure in the write hook. What it buys that nothing else can: an observed value with no matching rows returns **zero rows without opening the relation**, because absence has a witness - the write hook - where a trail has none. Soundness rests on exactly two external contracts and dies if either changes: **core-ownership dispatch (D3)** makes scan + record + mark-observed atomic, and the **Keystone issue-once invariant (K1)** makes a stored pk a name that can dangle but can never mis-attribute. **Status: v1 is built (CB01-CB11).** `AccessKind::kCabinProbe` is emitted by the compiler from `TableAccess::cabin_mask` (catalog state, so the plan stays `f(shape, catalog)`) and is **search-class** - `IsTrailReplayable` is unchanged, because invariant 9's line is *lookup versus search*, not *authoritative versus advisory*. The read path is `ChainRunner::RunCabinStep()`: a hit serves the entry set in two phases - resolve every entry, *then* emit - which is what lets a heap relation abandon the Cabin and walk on a failed hint without duplicating a row, since a heap has no pk descent to heal with (a btree resolves through `BtreeLookup` and heals the hint in place). A miss walks and records while scanning, and **only a completed walk may be committed**. C6's location hints go through `exec/tuple_verify.hpp`, the one verifier Waystone replay also uses - "not a parallel implementation" made structural. The store is `include/kds/stats/cabin_store.hpp` (core-local, never fails a statement, `TrailRecorder`'s shape); the sets are **memory-resident and do not survive a restart**, which §9 already declares - only the `sys.cabins` row persists, and `PageType::kCabin` is phase 2. Recording is **n=2 observed / n=1 declared**, the same split `CREATE PATTERN` settled and for the same reason. **C7, the per-column policy**: a column declares at `CREATE TABLE` who may give it a Cabin - `NO CABIN` (never, by any route), `CABIN AUTO` (the engine may, at a threshold - *named and stored, not built*), `CABIN` (created now, n=1), or nothing, which reads as auto. Stored on `sys.columns`, enforced at exactly two doors: CREATE TABLE creates what an enabled column asks for, and `Catalog::CreateCabin` refuses a disabled one whoever asks. Two engine gaps it is honest about: **there is no page epoch**, so `CabinEntry::page_epoch` is written 0 and the check passes trivially - Cabin is now the *second* subsystem waiting on the epoch that must land with relayout - and **"per snapshot" is now literal** — `docs/txn.md` is built, and a Cabin resolve reaches the visibility predicate at `ChainRunner::AcceptTupleAt` like every other read, so §1's surplus is subtracted by MVCC as well as by the key re-check. DELETE, which now exists, deliberately does **not** touch the write hook: removal stays forbidden, because an older snapshot may still match through the undo chain. `cabins`, `cabin_max_values` and `cabin_max_entries_per_value` are the switches; `CREATE CABIN` / `DROP CABIN` / `SHOW CABINS` the surface. **Measured (`bench/results-cabin.md`, via `tools/scenario0_stockmarket.py --cabin`): on the disk-backed 10,000-user run it is a wash - TPS +3.2%, `profit-scan` mean -20%, p50 flat.** The -20% is the feature working exactly as specified at a 23.9% hit rate (a quarter of probes served, the median still in the walking majority); the +3.2% is what that is worth when the scan is 63s of a 380s run and the WAL-logged inserts are 311s. **The hit rate is a property of the workload, not the structure**: 5,900 probes drawn uniformly from 10,000 users predicts ~1,443 repeats and 1,413 were measured, so a Cabin pays in proportion to how often a value is probed *again*. An earlier tmpfs run showed +27% TPS and -90% scan p50 at 2,000 users; **that TPS figure is a tmpfs artifact** - with fsync free the scan was the bottleneck, and on a real device it is not. The write hook is at or below noise (`account-update` p50 +1.7%), which depends on section 5's third row being implemented: an UPDATE that does not change the key column **must not append**, or the set grows by an entry per write until the cap un-observes it - correct, by the superset rule, and useless. `CabinContractTest.AnUpdateThatDoesNotTouchTheKeyColumnAppendsNothing` pins it.
- **Foreign keys** (`docs/impl-foreign-keys.md`, decisions F1-F6, milestones `FK-M1`-`FK-M6`): **FK-M1 through FK-M5 are built - declared and enforced**; FK-M6 (CASCADE/SET NULL) is out of v1 by F2. A foreign key is a child column whose value is the **parent's Keystone id** and never a business key (F1), which is what makes `ON UPDATE CASCADE` unnecessary rather than deferred: the referenced key is immutable (invariant 11) and issue-once (K1), so a stored reference can dangle but can never mis-attribute. v1 is **RESTRICT only** (F2), **fail-fast** rather than blocking (F3), and **same-core only** (F5). The catalog half is `sys.fkeys` on fixed page 13 (`SysFkeyRow`, 28 bytes - **no parent column**, because F1 fixes that side for every foreign key there can be, and **no action field**, because F2 leaves exactly one legal value), declared by `<col> <type> REFERENCES <parent>` at `CREATE TABLE` and listed by `SHOW FKEYS`. It cost a **superblock format bump, 10 → 11**, so every pre-existing data file stops mounting - the fourth new-bootstrap-relation break, and the one where mounting anyway would be worst, since an older file reads an empty foreign-key list and enforces nothing. **The checks are `include/kds/exec/fk_check.hpp`**, one implementation each, called from `InsertInner` (before the row id is allocated), `UpdateInner` (when the SET list touches an fk column) and `DeleteInner` (before the mark). Six things to know. **F4's mechanism could not be built**: INSERT compiles to no step chain and UPDATE/DELETE walk a single `Step` outside the step VM, so F4's *intent* survives - one checker, no trigger subsystem, no second evaluator - and its mechanism does not, which costs the probe memo (N children of one parent pay N descents) and free ANALYZE integration (`RecordFkAccess` does it by hand instead, FK-M4). **Check visibility is latest state and never walks undo** (`txn::CheckVisibility`): the answer is the version on the page, so it is a pure sibling of `Classify` over a view minted *at check time*, disagreeing in exactly one case - an in-flight **insert** of the parent is *busy*, not a violation. **`kConstraintBusy` was not added**: a violation is the new non-retryable `kFkViolation` (`ERR FK_VIOLATION retryable=0`) and an in-flight writer reuses `kTxnConflict`, which keeps the wire's `retryable` bit one code wide. **A heap parent is refused** at declaration, because F1 references the parent's pk and a heap relation has no pk index, so every check would scan it. **The reverse check stops at the first live child**, so a violation costs a prefix and only a pass costs the relation - which is the asymmetry F6's Cabin fast path exists for, and an observed value's exhausted, all-non-matching entry set is an authoritative "no children". And **F6's nomination half is corrected, not deferred**: the reverse check *reads* a Cabin and never fills one, because the value it would record is the pk being deleted and a pk is deleted once - a dead value spending a `cabin_max_values` budget that refuses to observe once full. Its values arrive the ordinary way, from queries filtering children by parent id.
- **Secondary indexes** (`docs/feat-index.md`, decisions IX1-IX14, workplan `IX01`-`IX16`, **all built**): `CREATE INDEX <name> ON <t> (cols) [COVERING (cols)]`, `DROP INDEX`, `SHOW INDEXES`, multi-column keys and covering columns. **IX1 is the whole design: an index is a Cabin that observed everything.** `feat-cabin.md` §1's invariant carries over verbatim with the observation precondition struck out — an index's entry set for a key is a **superset** of the qualifying visible pks, and the surplus is subtracted at read time by MVCC plus a re-check of the key predicate, which is sitting in `Step::residual` because the compiler deliberately left it there. So the read-time verification, the append-only maintenance and "removal is forbidden" are all *already proved* rather than new mechanisms. **Maintenance is append-only**: INSERT appends, UPDATE appends for the new key and leaves the old one, DELETE does nothing — and an UPDATE that moved no key or covered column **must append nothing**, or the index grows by an entry per write forever (correct by the superset rule, and useless). A failed append **fails the statement**, which is the one place an index is not a Cabin: un-observing is unavailable, because an index missing an entry is *wrong* rather than slow. **Only a btree-clustered relation may carry one** (IX3, `impl-foreign-keys.md` F1's argument): an entry's payload is the pk alone, so nothing dangles, nothing needs healing, the index is **not** waiting on the page epoch, and relayout cannot invalidate it. **Index pages are their own class** (`PageType::kIndexInternal = 11`/`kIndexLeaf = 12`, `include/kds/storage/index/`) and **split by dividing** — which decides nothing about the heap page split policy, because an index page holds entries rather than tuples and has no `min_key`, so invariants 2 and 3 have nothing to be about in it. That is why `storage/btree/` is not reused: its split refuses any key below its target leaf's contents *on purpose*, and a secondary key is not monotonic. **The tree routes on the whole `(key, pk)` sort key** (§4b) and a probe that knows less is **zero-padded, never shortened** — a separator carrying only the key routes a probe past a duplicated key's left half, leaving rows reachable by walk and unreachable by descent. The key encoding is `include/kds/exec/index_key.hpp`: one order-preserving byte string compared by `memcmp` alone, accepting only a column's **storage form**, so skipping `CoerceLiteralToColumn` is a compile error and not a silently wrong key. A string key is stored **truncated**, which costs false positives only, because the read path re-checks the predicate anyway. **There is no index-only scan and cannot be one** (§7): visibility comes from the tuple's undo chain and no witness exists outside it, so covering buys the base *descents avoided* and nothing else — `ANALYZE`'s `index_filtered` is the honest price. **Both new access kinds are search-class** — `IsTrailReplayable` did not move, because invariant 9's line is lookup versus search and an index probe answers with a *set*. Selection is `f(shape, catalog)`: longest usable key prefix, ties broken by lowest `index_oid`, tried after the pk kinds and **before** the Cabin. **An index step emits in primary-key order** (§8a, found by the equivalence test): the walk collects in index-key order and a scan emits in pk order, so without the sort an index would **reorder a reply** — failing the standard invariant 8 sets for Waystone, which an authoritative structure does not get to fall below. The read path is `ChainRunner::RunIndexStep`, two phases (walk collecting pks, then resolve each through the clustered tree) because `AcceptTupleAt` may fetch and an index-leaf span held across emission is the span `parser-v2.md` I15's R1 forbids; it **never decides visibility** and **never emits from an entry**. The write hook is `include/kds/exec/index_maintain.hpp`, called beside the Cabin witness and before the log; **DELETE deliberately does not call it**. The **backfill walks each tuple's undo chain**, not only its current version (§10a) — DDL is not transactional, so the index becomes visible to every reader at once and an older snapshot must find *its* version through it — and it runs **before** the `sys.indexes` row exists, so an index is complete or absent and never partial. `RecordType::kIndexInsert = 17` is emitted *before* the `HEAP_INSERT`/`HEAP_OVERWRITE` it points at (a dangling entry is dropped by verification; a row with no entry is lost), and a **split logs full page images and no `INDEX_INSERT`** — so §12.1's proposed `INDEX_PAGE_INIT` was **not** assigned, a dividing split leaving its new sibling holding half the entries, which only an image describes. `Catalog::UpdateIndexRoot` updates the cached entry **in place** rather than bumping (§12a), because a split republishes a root from inside an ordinary INSERT and a global drop would dangle the `const TableAccess*` the statement holds. It cost the **superblock format bump 11 → 12** — the fifth such break, and the first whose reason runs the *opposite* direction: no old file misparses anything, because nothing ever wrote a `sys.indexes` row; what the version refuses is an **older binary opening a newer file**. **Nothing is reserved** — `index`, `covering` and `unique` are ordinary identifiers, `kFingerprintVersion` did not move, and the golden corpus gained 26 lines and modified none. `indexes` (default on) is the **read-path** switch and does not change the compiled chain; there is deliberately **no switch for maintenance**, because turning the write cost off is `DROP INDEX`. `tests/index_contract_test.cpp` keeps it honest — four configurations compared byte for byte, plus a corrupted index page that must **fail** rather than mis-answer (the opposite outcome from the waystone suite's corrupted trail, because an index has no fall-through that could be correct) — and it is **mutation-tested**: the spilled-covered case exists precisely because the first mutation run showed the suite could not see it. **Measured (`bench/results-index.md`): 9.7x on a selective equality over 10,000 rows, 1.9x over 1,000, 1.11x over 200 — and an 11% *loss* on a range at 200 rows**, the crossover IX9's stable-plan rule deliberately cannot see (PostgreSQL declines its own index at that size; KDS cannot, because declining needs the cardinality estimate a stable plan refuses). §7's covering claim survived in both directions, pricing a base descent at **0.58-0.76 us**; the absence of an index-only scan is *measured*, `COUNT(*)` costing the same as fetching the rows where PostgreSQL's `Index Only Scan` is 10% cheaper. Write side: **+4.5 us for the first index, +2.5 for the second**, which is 0.9% of a default INSERT **only because a batch of one is a batch** — under concurrency the fsync amortizes and it becomes visible, and that measurement does not exist. Both kinds reach `sys.access_stats` through the same call with no per-kind branch, so `SHOW ACCESS` now distinguishes "searched every row for a few" from "descended an index for them" - the first pair a physical optimizer could act on that `heap-and-tuple.md` §7 did not already describe.
- **Aggregation** (`docs/feat-aggregate.md`, decisions AG1-AG15, workplan `AG01`-`AG10`, **built**): `GROUP BY` plus `COUNT`/`SUM`/`MIN`/`MAX`, `DISTINCT` included. **AG1 is the whole design: the fold lives outside the executor.** The dispatcher already owns a statement's `RowSink`, so an aggregated statement's sink body becomes `Aggregator::Accumulate(frame)` and `Finish(emit)` produces the output rows - the same seam Waystone lives outside of, and for the same reason: a second place that reasons about statement shape is a second answer to "what does this statement do". What that buys is stated so it can be tested, and is: **the chain compiled for `SELECT b, COUNT(*) FROM t GROUP BY b` is byte-identical to the chain for `SELECT b FROM t`** - steps, kinds, residuals, access columns and class - so trail replay, Cabin probes, access statistics, the scan/probe equivalence and "downgrading any step to a scan cannot change the result" all hold for an aggregated statement **with no new proof**, and `IsTrailReplayable` and `HasReplayableStep` did not move. The contract suite pins that over eight shapes, and the aggregated statements were added to `waystone_contract_test.cpp`'s own query set so all five of its configurations cover them. **The step VM is off-limits by construction** - a change to `step_vm.cpp` or `AccessKind` in service of aggregation means the placement decision was violated - and it needed none, because `AcceptTupleAt` already completes a surviving row's decode, so the fold reads every column through `ChainFrame::Get`. Eight things to know. **Nothing is reserved**: a function head is an unqualified name from the set *followed by* `(`, no production puts a paren after a column reference, so a column may still be named `count` or `group`, `kFingerprintVersion` did not move and no stored `pattern_id` changed - the golden corpus is the evidence, where eight lines were added and three verdicts flipped without one hash moving. **The compiled form is `StepChain::aggregate`**, an `optional<AggregateSpec>` of resolved items and group keys, and `star()` became "projection empty **and** no aggregate" in both the AST and the chain, or an aggregated statement reads as `SELECT *` and answers with whole rows. **Zero allocations per row** into an existing group (measured, not asserted): a reused key-encoding scratch, a heterogeneous map probe, states folded in place; the global form skips the key and the map entirely. **The key encoding tags null/int/str**, which is what makes two NULL keys one group *without* touching `CompareValues` - predicates compare, grouping encodes identity - and strings are length-prefixed so `('a','bc')` and `('ab','c')` cannot collide. **SUM is checked int64**: an overflow fails the statement naming the aggregate and the group, `SUM` over `uint64` is `Unsupported` at compile (half the range does not fit, and a sum of Keystone ids is a statement nobody meant) while `MIN`/`MAX` over one are exact through the digit-text path. **AG-M, the merge invariant, is built and tested and called by nothing** - it is what lets `crosscore.md`'s pipeline ship *partial* aggregates without touching the step VM, and its ordering half holds only for a partition with a defined order, which a contiguous split has and an interleaving does not. **A cap fails the statement**, never truncates or spills, because a truncated group set is a wrong answer with a right answer's shape - the opposite of the Cabin caps, which fall back to a scan because a Cabin is only ever a shortcut. **`AVG` folds since 2026-08-07** (`feat-aggregate.md` §3.4, closing §10's item): one principle — never invent digits, never drop declared ones — so `AVG(DECIMAL(p,s))` answers at scale `s`, rounded **half to even** on the exact integer pair, and an integer column is **refused at compile** naming the two honest options (declare a decimal, or compute SUM/COUNT); `DECIMAL(p,0)` averages to whole units, `AVG(DISTINCT)` divides the distinct sum by the distinct count over one set, the state is the `(sum, count)` pair AG-M reserved (divide once, in `Finish` — merging quotients would be unrecoverable rounding), and the "no guard digits" line is load-bearing: a client that has seen `avg(amt)` at scale `s` parses it at scale `s` forever. And **v1 refuses, each with an exact byte**: `HAVING`, `ORDER BY` over aggregated output, a bare column not in `GROUP BY` (AG5 - there is no "any row" mode), aggregates in subqueries (AG8, permanent for v1) and aggregation over `sys.*` (AG12 - a view's rows come from the catalog's readers, so there is no sink to wrap). **Measured (`bench/results-aggregate.md`, on a block device): the fold's cost tracks *group count*, not row count** - free at one group (the global form is -3.2% over 20,000 rows, since it folds every row and serialises one), +8% to +16% on a 20,000-row scan as groups go 2 to 1,024, +0.4% on a point lookup, and +44% on a grouped range producing 64 groups from 101 rows, which is the shape where a fold buys least rather than a per-row cost. `aggregate_max_groups` is ratified at 65,536; `aggregate_max_distinct` is deliberately not.
- **Types: DATE, TIMESTAMP and DECIMAL** (`docs/spec-types.md`, workplan `docs/workplan-types.md` `TY01`-`TY09`, **built 2026-08-07**): three types beyond the integers and strings the engine started with, added on the claim that **a type is four things here and no more** - a width, a literal parser, a comparison and a rendering. That claim is the design, and `tests/types_e2e_test.cpp` exists to falsify it: the join, the fold, the Cabin and the Waystone trail all run over the new types with no code of their own, and the one place it failed is recorded below. Six things to know. **A DATE and a TIMESTAMP *are* integers** - epoch days and epoch microseconds, decoded as `ValueType::kInt` - so ordering, `kRange` bounds, `MIN`/`MAX`, grouping, Cabin keys and probe keys all take the int arm with no new code; `kDecimal` is the one `ValueType` added, because an unscaled integer means nothing without the scale beside it. **`(p, s)` rides in `SysColumnRow::len`** (§4a), packed with explicit shift/mask helpers, which is why the whole feature cost **no format change and no version bump** - `len` was read only for `char` and was dead weight for every other type. **Coercion is a compile-time act**: `WHERE amt = '12.34'` against `DECIMAL(10,2)` compiles to a comparison against the scaled integer 1234, so per-row evaluation stays an int64 compare and a literal that does not parse is a *positioned compile error*, never a row-by-row false. **One coercion function, `exec::CoerceLiteralToColumn`** - and this is the rule that matters: **any path turning a written literal into a value the engine compares or keys on goes through it.** There were briefly two, and the Cabin's write hook keyed on the raw literal while the read path keyed on the coerced one, so an observed DATE value silently stopped seeing rows inserted after it was observed - fewer rows, a plausible-looking answer, exactly the failure `feat-cabin.md` §5 calls invisible without a baseline. **Encode is the only gate** (TY7): the three parsers are shared with the compiler, decode re-validates nothing and allocates nothing, and rendering happens at the emission boundary through `FormatValue(type_val, value)` - whose single-argument form is *deleted*, not defaulted, so a caller that should pass a column type cannot silently render an epoch day. **`float` is still refused** at `CREATE TABLE`: nothing settled its encoding. What v1 is not: no arithmetic or expressions (the grammar has none), no cross-scale comparison (refused, never rescaled - rescaling either drops digits or invents them), and no cross-type `AVG` beyond what `feat-aggregate.md` §3.4 decided 2026-08-07 (decimal columns at their declared scale, half-even; integers refused). **The wide decimal is built (2026-08-07, spec §2a / workplan TY11)**: `decimal(p, s)` with `19 ≤ p ≤ 38` is a **separate 16-byte int128 type** (`kTypeValDecimalWide = 13`, also declarable as `decimal128(p, s)`), selected by the declared precision at the one DDL site — never a widening of the 8-byte type, whose contracts (including SUM's int64 accumulator) are untouched. `kDecimalWide` is a `ValueType` of its own so the compiler surfaced every switch, the digit-walk parser is one template body at both widths, cross-width column comparison is refused at compile like cross-scale, SUM/AVG fold through a checked int128 accumulator, and the wire carries 16 LE bytes under type_oid 13 with `(p, s)` in `type_mod`. Building it caught a live narrow bug: an integer literal that wrapped int64 in the lexer coerced as its wrapped value, so `= 36893488147419103232` against a narrow decimal *matched 0.00* — wrapped literals are now refused at coercion for date/timestamp/decimal, while uint64's digit-text path is untouched. What remains out: `p > 38` (no representation) and cross-width comparison. **TY10 (2026-08-07) added TY3's phase 2, the bare numeric literal**: `12.34` lexes as one `kNumLit` token and is **the quoted string of its spelling, exactly** - same AstValue, same fingerprint argument bytes, so `= 12.34` and `= '12.34'` are one pattern, one arg_hash, one meaning, with no new `ValueType` and no carve-outs (a bare `1.5` into a varchar stores the string `1.5`). Digits are required on both sides of the point - `12.` and `.5` lex as they always did, which keeps every previously-parsing statement token-identical. **`kFingerprintVersion` did not move, and the argument is the part worth knowing**: `12.34` lexed before (int, dot, int), so its statements were *fingerprintable* and their hashes moved - but never *storable*, since int-dot-int parses in no production and only executed statements are recorded. That refinement of the bump rule ("already fingerprintable" means "already storable") is written into `fingerprint.hpp` and pinned by the golden corpus, whose every pre-existing line passed unchanged.
- **Access statistics** (`include/kds/stats/access_stats.hpp`, `sys.access_stats`): one row per access *shape* - `(kind, rel_id, column_mask)` - with `use_count` and `last_seen`, written for **every** access kind through one call with no per-kind branch, so the numbers are comparable across kinds. This is the first implementation of `docs/heap-and-tuple.md` §7's "KDS collects access statistics", which sat beside "*Nothing here is implemented*" until 2026-08-03 - and engine-driven physical optimization is one of the two things this project exists for, so it had been running with no input data. **Keyed by columns, never values**: `WHERE flag = 1` and `WHERE flag = 2` are one shape with two uses, which bounds the relation by the schema instead of the data and is why it needs no eviction policy. The unbounded axis - *which arguments repeat* - is Waystone's `arg_hash` and stays there; the two layers answer different questions and are deliberately not merged. Read with `SHOW ACCESS`, switched by `access_statistics` (default on), and costs +1-2% on a point lookup and nothing measurable on anything slower. **Nothing consumes it yet** - no physical optimizer exists, and relayout still needs the page epoch that also gates Waystone's replay rule 2.
- **Catalog relations are page chains** (2026-08-06). Every `sys.*` relation is a chain of heap pages linked through `next_page_id`, exactly as a user relation is: the fixed page id in `well_known.hpp` is the chain **root**, and a full page links to the next. They were single fixed pages until now, which capped the whole instance at **~68 `sys.columns` rows** - measured on disk, 68 slots per page - so a third consecutive run of `tools/scenario0_stockmarket.py` on one data file failed its `CREATE TABLE` with `heap page has no room for this tuple`. Three things to know. **Growth takes pages from a reserved low range** (`kCatalogOverflowFirst`..`kCatalogOverflowLimit`, ids 14..127), never from the free map's general supply, and that is correctness rather than tidiness: a peer core may fault only pages below `system_page_limit_` read-only (`DevicePageStore::MayFault`), so a catalog page at a general-supply id would be one a peer could not read - and a peer that cannot read the catalog cannot resolve a relation at all. It also lets the flush that precedes `kCatalogInvalidate` name every catalog page as a bounded range (`kEveryCatalogPage`) instead of tracking a set. **The append is not `heap::ChainInsert`**: a catalog row has no Keystone word, so there is no key to order pages by and every page carries `min_key = 0` - the chain is an append list, not a semi-sorted heap. And **one walk replaced six loops**: every catalog mutator (`AllocateRowId`, `UpdateRelationDescPage`, `MutatePatternRow`, `RetirePattern`, `RecordAccess`, `DropCabin`) used to spell out its own scan of one page's slots, and they now share `ForFirstRow`. **No format change** - an existing file's catalog pages already carry `next_page_id = kInvalidPageId`, which reads as a one-page chain. What this does *not* fix: nothing reclaims a catalog row, so the ceiling is on columns ever created rather than live ones, and the O(relations) catalog scan that one page's capacity used to bound is now genuinely unbounded by page count.
- **Catalog cache** (`include/kds/catalog/catalog_cache.hpp`): catalog reads are served from a core-local in-memory cache instead of re-scanning a catalog page per statement — `name → oid`, `oid → TableAccess`, `pattern_id → PatternAccess`, the `sys.types` snapshot, and the table list. One question decides what may live there: *can the fact change without DDL?* If yes, it is not cacheable. Three rules follow. (1) **Sequences and heat are never cached** — `GetSysTableRow()`/`AllocateRowId()` and `GetSysPatternRow()` always read the page, which is what lets a statement hold a cached `TableAccess` across its own insert. (2) **Absences are never cached**, which is also why registering a pattern invalidates nothing and is safe on the statement path. (3) **One invalidation choke point**, `Catalog::BumpVersion()`, which also advances `Catalog::catalog_version()` — the counter `docs/parser-v2.md` I5 stamps bound statements with. There are two exceptions, `SetPatternWaystoneRoot()` and `SetPatternOrigin()`, which update their cached entry in place: the fact belongs to one pattern and is read by nothing else, so a global drop would dangle every other held pointer for nothing. `RetirePattern()` — `DROP PATTERN`'s catalog half, and the **first path in the engine that removes a catalog row** — does bump, because there is no in-place update for a row that no longer exists. It retires the slot rather than delete-marking it, since catalog reads have no snapshot to filter a mark against and a marked row would still be found by every lookup. **`sys.pattern_defs` is the one catalog relation stored in ordinary user tuple format** — a Keystone word, tagged cells, a var-heap — because it stores a pattern's source text and the fixed-length rule already answers where arbitrary-length values go; every other catalog relation is a fixed-offset typed row codec, deliberately (`exec/catalog_view.hpp`). The price is that its rows cannot be read from `catalog/` at all, since decoding them needs the row codec that sits above it, so the readers live in `include/kds/stats/pattern_defs.hpp`. Coherency is **instance-scoped**: two `Catalog`s over one `PageStore` do not see each other's DDL, which is sound only while catalog mutation stays append-only and dies with `DROP`/`ALTER TABLE`.
- **Task representation: C++20 stackless coroutines** (`include/kds/sched/coro.hpp`, `docs/sched.md` §3, decided 2026-08-05). `sched.md` left this open between callbacks, coroutines and fibers, and `docs/rules.md` §7 listed coroutines under the undecided language-feature whitelist; both are now settled. **What forced it**: every cross-core operation is a request whose answer arrives later, and the engine had no way to spell "wait" that was not blocking the reactor or hand-rolling a call chain into a state machine - `crosscore.md`'s step pipeline could not be written at all. Callbacks would have inverted the executor and all 22 allocation sites; fibers cost a stack per in-flight statement. **The scheduler needed no change** - `Task::Poll()` returning `kSuspended`/`kDone` was already a coroutine's resume protocol, which `task.hpp` had predicted in as many words. `Coro` is the return type (lazily started, carries a `Status`), `CoroTask` the adapter that **owns the frame**, so dropping an abandoned statement destroys a coroutine suspended anywhere rather than leaking it. Two awaitables: `Yield` is §3's mandatory cooperative yield, finally spellable; `WaitFor{&flag}` is the cross-core request/response shape. **The wait re-test lives in `CoroTask::Poll()`, not in `await_ready`** - an awaitable's ready check runs once, at the `co_await`, so a naive version suspends once and then resumes regardless of the condition; the flag is recorded on the promise and re-tested each poll, which is also what makes a long wait cost a predicate call rather than a resumed frame. **The cost is a heap frame per coroutine**, so this is for suspendable work - a statement, a pipeline step, a lease - and never the per-tuple path. Resumption is polled, not event-driven; making the resumer re-submit the task is strictly better and deliberately deferred until a real pipeline can answer the lifetime question. **Its first production use is the page-id lease refill** (`include/kds/server/extent_lease_service.hpp`, workplan P5): a peer at `low_water()` sends `kExtentLease` and `co_await`s the grant, which P2 had to leave out because it could not be written. Three rules that came out of building it — the refill runs *beside* allocation and never inside it (`CreateNew()` is called from 22 non-coroutine sites, which is why leases exist at all), **one request in flight per core** or the low-water check burns an extent per tick, and an exhausted free map replies with a **zero-page grant** rather than dropping, because a dropped reply parks the waiter forever.
- **Cross-core execution** (`docs/crosscore.md`, workplan `docs/workplan-crosscore.md` `P0`-`P8`, decisions `CC1`-`CC6` and `M1`-`M9`): how one statement touching relations owned by different cores runs — a **step pipeline**, each step executing on the core owning its relation, intermediate rows flowing as KWP row batches under credit-based flow control, final rows framed by the session core. Two decisions bound the whole thing. **v1 is read-only cross-core** (CC3): a transaction's writes bind to one home core and a write to another core's relation is a retryable error, which is what keeps commit single-stream and the 2PC door closed. And **there is no cross-core ReadView** (CC4): a remote step reads the owning core's latest committed snapshot, so READ COMMITTED is unchanged and **REPEATABLE READ is knowingly weakened across cores** — RR holds per core, the server does not error, and the client manual has to say so. **Status: P0, P1, P2, P6's catalog half and P4's restriction half are built; the pipeline is not, and is blocked on an open decision.** P0 is the durable half — `cores` is a config key **pinned into the superblock** (format version 9 → 10) and validated at every mount naming both numbers, because WAL streams are per core and recovery under a changed count is `[OPEN]`; and `sys.tables` gained **`owner_core`**, since M1 rejected page/extent hashing outright (a btree descent cannot cross cores per hop) and guideline 4 forbids deriving ownership from a page id, a hash, or the topology anywhere. `cores` is bounded by `kMaxWalCores` — the anchor table is indexed by `core_id`, so 64 is a ceiling rather than a preference — and by `hardware_concurrency()`, since pinned never-blocking reactors overcommitted to fewer cores serialize whole workloads. Placement is `catalog::AssignOwnerCore()` (`include/kds/catalog/core_placement.hpp`), a free function **outside `Catalog`** so the policy can be replaced without the catalog learning how many cores exist. **M1's `[PROPOSED]` round-robin was performed from P0 and was wrong**: a relation's owner must be *the core that allocates its pages*, and DDL allocates from the system core's free map — so a relation placed on core 1 was built from core 0's pages and no core could reach it. Nothing compared the two facts until P4's affinity check asked, at which point every statement on a two-core instance failed. It now returns the creating core, with the rotation written out in the header as what it becomes once CREATE TABLE can allocate from the *owner's* lease. A `[PROPOSED]` policy nothing consumes is not inert if something else already depends on the fact it sets. **Co-location needed no encoding at all**: a relation's indexes, Cabin, Waystone pages and var-heap hang off its own row and have no owner field, so M1's rule is structural. P1 is the transport — `sched/spsc_ring.hpp`, the `RingTransport` seam with real (N² per ordered core pair) and simulated implementations, `sched/ring_message.hpp`'s central kind enum, `sched/send_retry.hpp` for M7, and **`Scheduler::RunOnce()` phase 3, which was a comment until now**. Four things to know. **The two transports agree per *edge*, not per inbox** — one edge is FIFO, but two peers' messages have no defined relative order and the real transport (rotating peer sweep, anti-starvation) and the simulation (by injected deadline) deliberately disagree; that is what the reorder injection exists to prove, and nothing above may depend on it. **A handler runs in phase 4, inside a task**, never in the drain, which is bounded by its own loop budget for the reason phase 4 has one. **The scheduling group travels in the message**, designated by the sender, because the same kind can be foreground or maintenance work. And **a message with no handler is dropped and logged, not fatal** — the same case as a tag matching no live state, which guideline 5 calls normal operation. `[OPEN]` and deliberately unsettled in M7's helper: no backoff, no retry ceiling, no deadline, because each would settle sched.md §10 and they belong with the credit accounting that actually bounds buffering. At `cores = 1` **nothing is constructed at all** — no transport, no thread — so the single-core path costs one null test per reactor iteration and is otherwise the code it always was. **P2 made the engine multi-threaded**: `server::CoreRuntime` is one core's stack (reactor, `FileLogDevice(core_id)` + `WalManager`, drain cadence), `Expeditor::Serve()` spawns and pins workers 1..N-1 and runs core 0 on the calling thread, and `RemoteCheckpointAnchor` carries a peer's anchor to core 0 over `kAnchorWrite` — **fire-and-forget on the merits**, since an anchor is published only after `CHECKPOINT_END` is durable, so losing one costs a longer replay and never an answer. That is the one cross-core operation needing no reply, which is exactly why it is the one P2 wires. Five things to know. **Cores above 0 come up alive and idle, deliberately** — `Catalog` reads the catalog's fixed pages through its `PageStore&` and M5 gives those to core 0, so until P6 a peer cannot resolve a relation, dispatch, or log anything. **Allocation could not cross cores per call**, so the extent-lease half of P5 moved into P2 (`include/kds/storage/extent_lease.hpp`): 22 synchronous allocation sites sit deep in the storage layer and nothing can suspend mid-call, so converting them would settle `sched.md` §3's open task-representation decision by precedent — a core leases a run of ids up front instead, and a leased store **never touches the free map**, which is what keeps that one durable page single-owner. **A leased store answers `IsAllocated` from its lease**, because a peer reads the map at `Open()` and core 0 sets the lease's bits later in its own copy. **Shutdown is a message** (`kShutdown`, added by P2), since `Scheduler::Stop()` writes a plain bool owned by its reactor's thread and making it atomic would put an atomic outside the ring indices. And **the ownership check is debug-only** (`DevicePageStore::MayFault`): core 0 may fault anything, a peer only ids in an extent it was granted. Verified under ThreadSanitizer, which found one race — in a *test*, reading a running core's `stopped_`, i.e. the precise access the design forbids. **P2's fourth bullet is vacuous and stays so: there is no WAL recovery to distribute**, and single-core recovery is a prerequisite no milestone owns. **P6's catalog half is built**: a peer opens its own `DevicePageStore` over the shared device, faults the catalog's fixed pages **read-only** (`MayFault` and `MayWrite` are now separate questions - the system range is readable by every core and writable only by core 0), and resolves a relation by name and schema; core 0's `BumpVersion()` flushes the catalog pages and broadcasts `kCatalogInvalidate`, and a peer receiving it evicts the page *frames* as well as its `CatalogCache`, because dropping derived facts while the stale bytes stay resident is a no-op. Three findings came out of it. **The workplan's premise was wrong** - `sys.patterns` and `sys.access_stats` are catalog pages written on the *ordinary statement path*, so a peer cannot write them and cannot ship the writes either (`RegisterPattern` returns a pointer its caller uses at once); **peers therefore run with `waystone_recording` and `access_statistics` off**, which is sound only because both are advisory and costs speed and optimizer input, never a row. **Catalog reads used to dirty the catalog** - `ScanAll` called `Get()`, so every lookup dirtied a page and every checkpoint wrote all nine back unchanged; it is `GetForRead()` now, a bug long predating multicore that the ownership check surfaced. And **a peer's view starts at core 0's first flush**, since it builds "which pages exist" from the free map on the device at `Open()`. **P6 stops at a blocker that is a design decision, not an omission: relation ownership and page ownership are different facts and nothing reconciles them.** `sys.tables.owner_core` names a relation's core; a page belongs to whichever core's lease it came from - and every relation's pages are allocated by core 0, because DDL is core 0's, so a relation the catalog says core 1 owns is built entirely from core 0's pages and core 1 may not fault one. Either `CREATE TABLE` allocates from the *owner's* lease (making DDL a cross-core allocation) or page ownership becomes a function of the catalog. Behind it sits a second: **a peer cannot INSERT**, because `AllocateRowId()` bumps `next_id` on a catalog page - P5's shape, a leased range of row ids. **P4's restriction half is built** (`include/kds/server/core_affinity.hpp`): a transaction's writes **bind to a home core** on the first write, a write to another core's relation is refused with `kTxnConflict` - the retryable spelling first-updater-wins already uses, so a client that retries on `TXN_CONFLICT` needs no new code - and every refusal is counted by `(home, target, relation)`, which is §6's stated input to the 2PC design. `CheckReadAffinity` is the planner half: all-local is the fast path, a chain spanning cores is refused with an exact reason instead of surfacing as a page-store fault naming a page id. The two halves age differently - **the write restriction survives the pipeline** (it is what keeps commit single-stream, since LSNs are stream-local and never compared across cores), while the read refusal is exactly what the pipeline replaces. **The pipeline's blocker is removed and the statement path is suspendable** (2026-08-05): task representation is **C++20 stackless coroutines** (`include/kds/sched/coro.hpp`), and `CommandDispatcher::DispatchAsync()` is a coroutine that `TcpServer` submits as a task, appending the reply on completion. Nothing suspends yet - the executor is still synchronous - which is what made the change verifiable: *when* a reply is produced has not moved, so the whole suite behaves identically. Three properties the seam preserves: **one statement in flight per connection** (forced by a stateful session and by a protocol with no request ids, so replies must leave in arrival order - pipelining is unchanged), **the statement text outlives the statement** (parser tokens are views into it, so each line is copied out of the inbox first), and **a connection that goes away mid-statement is deferred rather than destroyed**, since the coroutine holds a pointer to its session. It also surfaced a pre-existing bug: `FlushOutbox` used `::write`, so a client hanging up without reading raised SIGPIPE and **killed the server** - now `::send(..., MSG_NOSIGNAL)`. **The suspension-safety rule is now mechanical** (2026-08-05): `exec::InstallSuspendAudit()` registers the executor's "is it safe to be parked right now?" into `sched::SetSuspendAudit` - a hook, because `sched/` sits below `exec/` and must not know what a page is - and `CoroTask::Poll()` consults it in debug builds at the moment a coroutine suspends. What it forbids is **suspending while holding a page span**: I15's R1 already forbids a page *fetch* under a live span because nothing pins the frame, and suspending under one is strictly worse, since the span stays live for arbitrary wall time across every other statement on that core. Installed **per core, on the thread that runs statements**, because the guard's counters are core-local. What P4 still needs is the suspension point itself: `ChainRunner` walks a chain start to finish, so a step cannot yet await a remote batch - a viral conversion of `Execute`/`RunStep`/`RunWalkStep`/`AcceptTupleAt` into coroutines, the largest single change left, and the one this rule exists to keep honest. **P4's other prerequisite is built** (2026-08-05): `include/kds/wire/row_codec.hpp` is the KWP D5 row encoding — row descriptions and `{i32 len | -1 = NULL, bytes}` batches per `docs/protocol.md` §6. It sits *below* both the wire path and the pipeline and knows about neither frames nor cores, which is what makes CC2's "one encoder, two consumers; no second row format" literal: it exists before either consumer, which is the only way that rule survives whichever gets built first. It covers exactly the types the engine can store — `date`, `timestamp` and `decimal` included as of 2026-08-07, when the `DECIMAL` wire `[OPEN]` was decided: the unscaled **int64 LE**, with the scale carried **once in the row description** (`FieldDescription::type_mod`, literally the catalog's packed `(p, s)` word read through the same `DecimalPrecisionOf`/`DecimalScaleOf` helpers — one packing, two readers), and a value whose scale disagrees with its column refused at encode, never rescaled. Only `float` is still refused: nothing can store one. `DecodedField` views the payload and the rvalue `DecodeRowBatch` overload is **deleted**, so decoding a temporary is a compile error rather than a garbage row.
- **Wire protocol (KWP/1)** (`docs/protocol.md`, `docs/protocol-wp.md`): length-prefixed binary frames, a version/capability handshake, and an extended PARSE/BIND/EXECUTE model over server-side statement and portal handles. All-binary little-endian; results stream as row batches with portal suspension; durability class is a per-transaction protocol field; cross-core access is server-side forwarding, so clients are topology-unaware. **Status: only the frame codec exists** (`include/kds/wire/kwp.hpp`, `src/wire/frame_codec.cpp`), and nothing calls it — the server speaks the newline text protocol (`docs/client-manual.md`), which KWP/1 demotes to an off-by-default loopback debug surface.
- **Query language** (`docs/parser-v2.md`, tasks in `docs/parser-v2-workplan.md`, `V00`-`V32`): the parser runs at KWP `C_PARSE` only, never per execution, and **every SELECT-class statement compiles to a *step chain*** — an ordered list of steps, each reading one relation with one access kind (`Lookup`, `Probe`, `Range`, `FilterScan`, `Scan`). Written order is execution order: *the statement is the chain*, a documented client contract, never silently reordered, and **decorrelation rewrites are forbidden** rather than merely unimplemented. The chain carries the shape, so classification is absorbed into `kJoinSelect` and the class enum does not grow (J3). The step-kind table *is* Waystone's trust model — lookup-class steps are trail-replayable, search-class steps never are, and negation steps are search-class by definition. **The grammar is joins and predicate-position subqueries**: inner equi-join chains with `AS` aliases, plus scalar / `IN` / `NOT IN` / `EXISTS` / `NOT EXISTS` subqueries, correlated included, nesting to a depth cap. Table-position nesting (derived tables, CTEs) answers `Unsupported` with an exact position — it would need the inner result to become a relation with a schema, which breaks pk-direct probing and puts a temp relation in the storage layer. Also specified: literals parameterized at parse (so `pattern_id` falls out of the parse and inline/bound forms converge), flat index-based AST in a per-session arena, zero-copy tokens, name resolution before execution, 40-bit pk enforcement at the front door, and three rules for the nested access chains force (I15) — **decode before descending** (no page-frame span live across a nested fetch; safe today only because nothing evicts), **nested steps are read-only**, recursion bounded at both ends, and walks must be **stoppable**. **Status: the language runs, joins and subqueries included (V01-V18).** What remains in phase V-4 is the written-order contract's documentation (V20). `StatusCode::kUnsupported` and `kCardinalityViolation` exist and are non-retryable (V02). Both relation walks are stoppable (V03): `ChainVisit`/`BtreeVisit` take a visitor returning `StatusOr<storage::VisitControl>` (`include/kds/storage/visit.hpp`), where `kStop` ends the walk with `Status::OK()` without fetching the next page — so "did it fail or did it finish?" is answerable at the call site, and `Exists`, `LIMIT` and cost guards are no longer blocked on the primitive; no caller stops yet. The lexer reserves keywords, lexes `.`, and carries a byte range on every token (V04), and the grammar takes `FROM a [AS x] JOIN b ON a.c = b.c` chains in written order (V05) plus explicit select lists and qualified column names anywhere a column appears (V06), plus the four predicate-position subquery forms — scalar, `IN`/`NOT IN`, `EXISTS`/`NOT EXISTS`, correlated included, capped at `kMaxSubqueryDepth = 4` (V07). Outer joins, a FROM list with duplicate bindings, `SELECT *` over more than one relation, a subquery in FROM or join position, `WITH`, and over-depth nesting all answer `Unsupported` with an exact position; a bare column in a multi-relation list is accepted and left for V14's resolution. The one J2 form that still gives a bare syntax error is a subquery containing an aggregate — blocked on I14, see Open Decisions. A correlated scan is bounded by a per-statement row-touch budget (V19, `include/kds/exec/budget.hpp`): `max_rows_touched` tuples, default 100M `[PROPOSED]`, 0 = unlimited, refused with `StatusCode::kResourceExhausted`. It is per *statement* and shared into every sub-chain — a per-chain budget would let a correlated subquery spend the whole allowance once per outer row — and counted in tuples rather than wall clock, so a statement's success does not depend on what else the machine was doing. A one-entry probe memo caches the last descent's *location* (never the row), so a hit re-reads and re-filters identically to a miss - and it is **keyed by step as well as by key**, which it was not until 2026-08-02: a `ChainRunner` owns one memo but runs every step through it, so a chain with two pk-descending steps whose keys coincided served the second step the *first* relation's location. Relations of different row widths gave a `Corruption` error and equal widths returned a silently wrong row. **`kFingerprintVersion` is still 1 and no `pattern_id` has moved**: a keyword hashes exactly as the identifier it used to be, which is why all keywords share one token type. **Execution:** the dispatcher is now parse → compile → execute. `Compile(AST) → StepChain` (`src/exec/step_compiler.cpp`) resolves relations to oids and columns to `ColumnRef{up, rel_slot, col_pos}`, assigns an access kind, and numbers steps globally; the step VM (`src/exec/step_vm.cpp`) runs linear chains, with `Lookup`/`Probe` descending and the rest walking. **Five access kinds, all emitted** since 2026-08-03: `kRange` for a pk `BETWEEN` (the parser half of V08; `IN (list)` is still open) and `kFilterScan` for a walk driven by an equality on a non-pk unindexed column. Both are **search-class** - `IsTrailReplayable` is unchanged - which is what made them safe to add without touching Waystone's trust model. A `BETWEEN` **lowers to its two ordinary conjuncts** and the range on the step is a hint on top of them, so downgrading any step to a plain `kScan` still cannot change the result; the same relationship `Step::key` has to a lookup's repeated equality. `kRange` walks with **`min_key` tail pruning** - the first page whose `min_key` passes the high bound ends the walk, which is `VisitControl::kStop`'s first production caller (V03 built it for exactly this). It prunes the tail and **not the head**: a range near the start of a relation is cheap, one near the end reads everything before it, and skipping leading pages needs a seek that does not exist yet. `kFilterScan` executes identically to `kScan` - the split is a *statistics* distinction, and `Catalog::FindIndexOnColumn` finally has a production reader deciding it. **No identifier survives onto an execute path** and the name-matching evaluator is deleted — a `ChainFrame` is one values buffer with per-step base offsets, so a scan allocates O(1). Two equivalences are pinned by test: heap×btree in all four combinations return identical rows in identical order, and a chain forced down `Scan` matches `Probe` row-for-row — the latter is what makes invariant 9's fall-through safe, and the compiler buys it by keeping the probe key in the residual list. Sub-chains execute too: uncorrelated `EXISTS`/`NOT EXISTS` are hoisted and run once — a false one answers the statement without opening the outer relation at all — while value-bearing forms (`IN`, `NOT IN`, scalar) attach to the step holding their outer column, since their *set* is row-independent but their comparison is not. `NOT IN` is tri-state with a **single collapse point**, so it is not `!IN` and stays correct when NULLs become storable; a scalar subquery returning two rows is `CardinalityViolation`, never a first-row pick. R1 (no page-frame span live across a nested fetch) is enforced by a guard rather than by discipline: a step registers its span, decodes, releases, *then* descends. The AST is still owning, but the lexer no longer copies: `Token::text` views the statement (2026-08-03), so lexing allocates nothing and the AST's own copies are the only ones - which is I4's copy-at-the-boundary rule doing exactly what it was for. The vehicle is a **bolt-on to that parser** (J4) with the `Compile(AST) → StepChain` contract as the seam; the blueprint-parser rewrite lands behind the language and must emit identical chains. `docs/parser.md`, `docs/parser-workplan.md`, `docs/step-chains.md` and `step-chains-workplan.md` are superseded and kept only as history.

## Hard Invariants — never violate, never "temporarily" bypass

Numbered to match `docs/heap-and-tuple.md` §8.

1. 8192-byte pages; `uint32_t` page ids; `0xFFFFFFFF` reserved as invalid.
2. `min_key` is immutable after page creation.
3. No tuple with `id < min_key(page)` in that page, ever — including by relayout.
4. Tuples within a heap page are unordered.
5. The Keystone column is exactly `id:40 | flags:8 | reserved:16`.
6. The Keystone word is read and written as an atomic `uint64_t` (CAS for updates) and its fields never tear; on-disk encodings use **explicit shift/mask helpers only — compiler bitfields are forbidden** for any persisted format, since their layout is implementation-defined and KDS must be architecture-portable.
7. Ids stored outside the tuple header (B+ tree keys, `min_key`, Waystone entries) are zero-extended `uint64_t`; the upper 24 bits are always 0.
8. Waystone is advisory: deleting it wholesale may cost performance but must never change a query result. This is the invariant that matters.
9. Waystone is never **authoritative**. A reader may consult it for *where to look*, provided it (a) treats a missing or stale entry as a miss, (b) checks the Keystone id of the tuple actually at the reported `(page_id, slot)` and treats a mismatch as a miss too, (c) applies MVCC visibility exactly as the authoritative path would, and (d) falls through to that path — a btree descent on a btree relation, a chain scan on a heap one — on any of those. It chooses where to look, never what is visible.
10. No single canonical in-memory tuple is enforced; consistency comes from page pin and latch discipline (shared latch for reads, exclusive for structural mutation).
11. **Every** relation requires system-generated, autoincrement `id` values — a caller-supplied pk on insert is a defect, not a feature. The sequence is persistent (`sys.tables.next_id`, issued by `Catalog::AllocateRowId()`), never derived as `max(id)+1`, which would hand a new tuple the identity of a deleted one. Ids are unique and monotonic, not gapless. The pk is carried only by the Keystone word — never also as a body column — and cannot be updated: it is the tuple's identity, not a field of it. A relation's first column must be declared with an integer type (`catalog::CheckKeystoneColumn`), checked at `CREATE TABLE`.
12. The tuple MVCC header is exactly `trx_id:48 (zero-extended to 64) | undo_ptr | data_len | flags` = 20 bytes. There is no `xmax`.
13. **Every tuple is fixed-length.** A relation's row size is a schema constant; every variable-width value occupies one tagged cell of exactly `kds.inline_cell_width` bytes, and that width is instance-pinned in the superblock. No code path produces a tuple whose size differs from its relation's constant. A slot's `length` and the header's `data_len` therefore carry no new information — they are **checked redundancy**, and a value disagreeing with the schema constant is `Corruption`, never interpreted.
14. **Var-heap values are immutable per version** and `kVarHeap` pages are never relocated. The class is logged, headered and checksummed — authoritative data, not advisory. Advisory rules do not apply to it: losing a var-heap value loses a value, not a hint.

## C++ Working Rules

- Fresh codebase: do not copy kernel-style C wholesale; port ideas, write idiomatic modern C++.
- Prefer a disciplined subset: RAII for every resource (page pins, latches, file descriptors); no raw `new`/`delete` in engine logic; `std::atomic<uint64_t>` for the Keystone word.
- On-disk structs: `static_assert` sizes and offsets; fixed-width integer types only (`uint32_t`, `uint64_t`); explicit serialization, no `#pragma pack` reliance for format definition.
- Every size/offset constant gets a named `constexpr` with the derivation in a comment (e.g., entries-per-page chosen as a power of two for shift/mask addressing).
- Concurrency: document the lock/atomic protocol at the top of each subsystem file, as the previous codebase did. State what each lock protects and the acquisition order.
- Tests accompany every subsystem: page encode/decode round-trips, invariant checks (min_key rule, Keystone-word tearing), and crash-consistency tests for WAL-touching code.

## Open Decisions — DO NOT assume or silently pick

**Storage**
- Heap page split policy — how a full page's contents are divided and the new `min_key` chosen. Chain growth by tail append deliberately avoids deciding it. Free-space reuse on non-tail pages and page compaction are open with it, and both need reader registration first.
- Per-page epoch counter storage (header field vs core-local table), width, and wraparound.
- `kds.inline_cell_width` default value (64 bytes `[PROPOSED]`) — settle against measured string-length distributions of target schemas. The semantics of §3.3 hold regardless of the number; only the padding/spill ratio moves. It is a config key threaded through `catalog::RowLayout` and pinned per instance, never a compiled-in constant, so every value stays viable — but nothing may *depend* on it being 64.
- ~~Var-heap page organization~~ — **decided and built 2026-08-01 (`docs/rule-fixed-length-tuple.md` §8b): a per-relation chain** rooted at `sys.tables.varheap_page_id`, grown by tail append like `heap_chain.cpp`. Chosen for per-relation locality and so a future `DROP TABLE` reclaims one chain rather than sweeping a shared one; it cost a catalog row format change.
- Spilled-value size cap — **still open**, and the implementation deliberately does not settle it: one var-heap page (8144 bytes) is what fits without a multi-page representation, and anything larger is `Unsupported` rather than chained. A future cap can be lower (policy above `varheap::ChainAppend`) or higher (chaining behind the same `Append`/`Fetch` pair).
- The trigger for revisiting prefix-inlining (adopt only if string-equality steps become a measured cost).
- Purge-cadence sizing metric for var-heap headroom — churn-heavy string updates consume space until purge catches up, which makes purge cadence a capacity input rather than a background detail.
- Repurposing of the 16 reserved Keystone bits.
- Id-reuse / low-range reclamation for high-churn relations.
- Buffer-pool page-frame reclamation policy (pin refcount vs epoch-based eviction) under the page-latch model.
- I/O backend abstraction (plain `O_DIRECT` vs `io_uring` vs pluggable).
- Whether to relax invariant 3 (`min_key`) or invariant 11 (system-generated ids). Waystone no longer needs a dense, monotonically issued pk sequence, so arbitrary pk values are *possible* — but `min_key` exists for lock-free range pruning and `next_id` for tuple identity, and neither was ever about Waystone. Permitted by the design, not performed by it.

**Waystone** (`docs/waystone-concpets.md` §9)
- Retention and eviction per pattern. The catalog bounds patterns; nothing yet bounds *instances* per pattern.
- ~~Recording policy~~ — **decided 2026-08-01 (`docs/parser-v2.md` J5): `n = 2`.** An instance's first execution only counts; the second records. Sightings live in a bounded core-local table whose eviction merely restarts the count, which is a performance event. What is still open is that table's size.
- ~~The implicit-conversion matrix for `CREATE PATTERN`~~ — **decided 2026-08-02** at the spec's proposed v1 baseline (`spec-create-pattern-user-defined-patterns-v1.md` §6 check 6): numeric↔numeric and bool↔int coerce with a warning, text against either is an error. Implemented as three type *families* in one function (`src/exec/pattern_ddl.cpp`), not a pairwise table.
- Persistence class of waystone pages (WAL-logged vs unlogged). `sys.pattern_defs` and every `CREATE PATTERN` catalog write are unlogged, like all other DDL.
- `arg_hash` collision handling beyond the header check.
- Decay function and cadence; ring sampling policy under pressure.
- Whether invariant 9 is ever amended to permit trusting a cached result set as complete — which needs a per-relation change stamp bumped at *commit*, not at write.

**Transactions and WAL** (`docs/txn.md` §9, `docs/wal.md` §15)
- Undo retention policy and `SnapshotTooOld` surfacing (error class, retryability). Structurally unreachable today: nothing purges, because readers are deliberately not registered. **Still open after the transaction work** — building the manager did not make purge possible, and `TransactionManager` deliberately registers no reader.
- 48-bit `trx_id` wraparound and epoch handling. Exhaustion is `OutOfRange`, never wrapped — implemented that way in `txn::TrxIdSequence`; what stays open is what an operator does about it.
- The transaction-id block size (`kTrxIdBlockSize`, 4096 `[PROPOSED]`). A **floor** established by measurement (`bench/results-keystone-alloc.md`), not a preference: below ~4096 the durable write stops amortizing. Raising it costs only ids burned by a crash, which are free.
- Cross-core transaction commit protocol; recovery under a changed core count.

**Protocol** (`docs/protocol.md`)
- TLS activation phase and mode (direct vs upgrade); SCRAM parameters.
- `kMaxFrame`, default row-batch size target, session and portal idle-timeout defaults.
- ~~`DECIMAL` wire encoding~~ — **decided 2026-08-07**, the type system it depended on having been built: unscaled int64 LE with the scale in `S_ROW_DESC.type_mod` (`docs/protocol.md` §6). Additional wire types stay open; `p > 18` landed as that separate type (`DECIMAL128`, type_oid 13, 16 bytes — built 2026-08-07).
- Compression capability; credit-based flow control; topology/smart-routing extension.
- The authorization model (roles, permissions). The protocol only reserves the handshake stage.

**Parser** (`docs/parser-v2.md`)
- ~~Aggregates (I14)~~ — **decided and built 2026-08-06** (`docs/feat-aggregate.md`, AG1-AG15). Neither of I14's two options was taken: aggregates are neither excluded nor reserved-and-rejected, but built as a fold outside the executor. V07's done-condition is met — a subquery containing one answers `Unsupported` with a position (AG8), permanently for v1. See the Aggregation entry under Core Architecture; what is still open lives under **Aggregation** below.
- Ratification of the `[PROPOSED]` statement-class list — note v2 makes the class a property of a **query block** rather than a statement, which changes I2's shape, not just its contents.
- Per-statement slot-table size cap, which must now also decide whether `kOuterRef` (correlation) slots count against it: they consume arena but contribute nothing to `arg_hash`.
- Whether `kUnclassified` is permitted in production builds or gated. A subquery-bearing statement is its likeliest inhabitant, so gating it out means either every subquery shape gets a class or the parser rejects what it cannot classify.

**Cabin** (`docs/feat-cabin.md` §11)
- The per-cabin budget: page budget, per-value set caps, and demotion of write-hot values whose sets churn. Held behind `cabin_max_values` / `cabin_max_entries_per_value` (`[PROPOSED]`, 4096 each) so every option stays viable - nothing may depend on the numbers, only on the rule they enforce: **a cap refuses to observe a value and never truncates its entry set.**
- The `CABIN AUTO` threshold (§8.1): what `use_count` × cardinality earns a column a Cabin, and what un-earns it. The policy has a name, a grammar and a stored value; **nothing consumes them**, and a column declared `auto` behaves exactly as an undeclared one. Belongs with the promotion pipeline of §7 and the retention/policy spec.
- Background pruning cadence and batching. §5 fixes the two gates - dangling entries are droppable on sight (K1), non-matching ones only past the oldest-active horizon undo truncation already uses - and nothing prunes today, so a superseded entry costs memory and a read-time skip.
- Persistence of the entry sets (`PageType::kCabin`, §9's unlogged-authoritative class). v1 keeps them in memory, which §9 licenses; making them durable is a new storage class, not a new page type.
- Expression / predicate-scoped cabins, multi-column keys, range observation (C3 - revisit after v1).

**Aggregation performance** (`docs/workplan-aggregate-perf.md`, `AP01`-`AP06`)
- **AP01, AP02 (partly) and AP03 are built; AP05 is next.** The workplan's own "Where to pick this up" section is the resumption point and carries the cumulative numbers. What the measurements settled: **the fold is not the bottleneck** - it already scales better with group count than PostgreSQL's HashAggregate (+46% against +454% from 1 group to 7,560) - and what was, was the walk underneath decoding columns nothing reads.
- The rule that workplan earned twice: **re-measure the premise before building the fix.** AP02 blamed `AstValue` construction and it was a per-column-per-row `std::string` of the column *name*; AP03 blamed constructing an `Aggregator` per statement and hoisting it changed nothing, the cost being a second `std::ostringstream`. Both causes were plausible, both were written against an engine the previous task had already changed. AP04's and AP05's numbers are pre-AP02 and should be assumed stale.
- Measure per-statement fixed costs as **server CPU** (`/proc/<pid>/stat`), paired A/B **interleaved** - client latency cannot resolve them, since ~85% of a 115 µs pk lookup is the Python client, and a non-interleaved pair drifts enough between server restarts to invent a result.
- **`./build` is Debug** (`CMakeLists.txt`'s default) and a Debug measurement is wrong in *both* directions - it reported +7.9% where Release reports -3.7%, and +0.4% where Release reports +30.1%. Use `build-release`.

**Aggregation** (`docs/feat-aggregate.md` §10)
- `aggregate_max_distinct` (1,048,576 `[PROPOSED]`). Its sibling `aggregate_max_groups` is **ratified at 65,536** by measurement (`bench/results-aggregate.md`): the fold's cost is proportional to *group count*, so a statement near the cap is already visibly slow, and the ceiling is about 27 MB. This one is not — the same arithmetic puts it near **84 MB per statement**, the largest allocation any statement in this engine can ask for, and no measured workload argues for a number. Settling it needs a genuinely high-cardinality `COUNT(DISTINCT)` measured for *resident memory* rather than latency.
- `MIN`/`MAX` with `DISTINCT`: accepted as the standard's no-op (`[PROPOSED]`), since an extreme of a set equals the extreme of its support — or refused, on the grounds that a truthful error beats silently ignoring a word the client wrote. Built as accept-as-no-op, and no set is allocated for one.
- Lifting `ORDER BY` over aggregated output, and `HAVING` with it. Both are post-fold consumers and should share the wrapper seam AG1 established, so they are one decision rather than two; both need an output sort, which does not exist.
- Pre-aggregation below a join is **rejected for v1, not open**: it needs an operator inside the chain, which means teaching the step-kind trust table about a step that reads no relation. Revisit only if measured traffic presents the shape.

**Cross-core and multicore** (`docs/crosscore.md` §9, `docs/workplan-crosscore.md`)
- The cross-core **commit protocol (2PC)**, and everything gated behind it: cross-core FK, RR snapshot forwarding, and write shipping inside an explicit transaction. §6's rejected-write counters are the input this is meant to be designed from, so the decision wants data before it wants a design. v1's restriction — writes bind to one home core, a second core's write is a retryable error — is what keeps commit single-stream in the meantime.
- **Batch size and initial credit** (`[PROPOSED]` 32 KiB and 4 batches per edge). Both are parameters of `SpscRing::Create()` and `RealRingTransport::Create()` rather than constants, so every value stays viable; nothing may depend on either number. Ring **capacity sizing** is `[OPEN]` in `docs/sched.md` §10 alongside them — `server::kCoreRingSlots`/`kCoreRingPayloadBytes` (256 × 1 KiB) are what P2 picked to get the fan-out running, deliberately *not* the 32 KiB batch target, since sizing every ring for a message that does not exist would cost 8 MiB per pair on a promise.
- **Extent size** (`storage::kDefaultExtentPages`, 64 pages / 512 KiB, `[OPEN: size]` from `docs/page.md` §5). A batching knob: larger burns more on a crash and messages core 0 less often. Nothing may depend on it — it is a parameter everywhere. Nothing reclaims an extent either, and that stays open with page reclamation generally, which does not exist.
- The **`ring_full` suspension/retry protocol** (sched.md §10). M7 fixes only the shape — the task yields and retries — and `sched/send_retry.hpp` deliberately adds no backoff, no retry ceiling and no deadline, because each would settle this. It belongs with crosscore.md §4's credit accounting, which is what bounds per-request buffering.
- **Core-count changes and WAL stream reassignment** (wal.md §3). Today a mismatch refuses the mount, naming both counts. What an operator does about it — and what recovery does with |N − M| orphaned streams — is undecided, and the refusal exists so nothing decides it silently.
- **Relation placement policy.** `AssignOwnerCore()`'s round-robin is `[PROPOSED]` and lives outside the catalog so it can be replaced. Pattern/Waystone-driven placement is named in crosscore.md §9 and is explicitly an optimization concern: cross-core execution is the correctness path regardless of placement. Skew is observed and never rebalanced in v1 (M3), which is also what makes `owner_core` cacheable.


**Foreign keys** (`docs/impl-foreign-keys.md`)
- **How the forward check is expressed**, now that F4's mechanism is unavailable: a shared check helper called from the write paths, or converting INSERT to a step chain first. The second is the larger change and is what would restore the probe memo and free ANALYZE integration; the first is what FK-M2 can ship. Do not build a second evaluator either way — that is the part of F4 that is not up for discussion.
- **The status code for a check that meets an in-flight writer.** F3 proposes `kConstraintBusy`, which would be the **second** retryable code, and `IsRetryable` maps onto the wire's `retryable` bit that `docs/protocol.md` §11 calls a compatibility surface. Reusing `kTxnConflict` keeps that surface one code wide and still distinguishes retry from wrong, since the violation gets its own non-retryable code. Settle at FK-M2, not before.
- **Whether a heap parent stays refused.** FK-M1 refuses one because a check against a pk-indexless relation is a scan. Relaxing it adds a case and changes no format, so every option stays viable — but nothing may assume a parent is a btree relation for any reason other than this refusal.
- The `[PROPOSED]` `kFkNullable` semantics, which no writer sets and nothing can exercise until NULLs are storable. Until then a foreign key is unconditionally checked, and a stored 0 means exactly that.
- CASCADE / SET NULL (F2), which need the budget-interaction design a long cascade under run-to-completion demands, and cross-core foreign keys (F5), which sit behind the 2PC decision with everything else cross-core.

**Secondary indexes** (`docs/feat-index.md` §13)
- `kIndexStringKeyBytes` (`[PROPOSED]` 32) — how many bytes of a string column ride in the key. Same axis as `inline_cell_width` and settled by the same measurement: it trades entry width, and so leaf fan-out, against how often a probe pays a base descent it did not have to. Nothing may depend on the number; every caller reads it back from `IndexKeyColumnWidth`.
- The index leaf **split point** (`[PROPOSED]` the midpoint) and fill factor — a parameter of the split function, never a constant.
- `kMaxIndexKeyColumns` / `kMaxIndexCoveredColumns` (`[PROPOSED]` 4 / 8). Both are **refusals, never truncations**: a truncated index declared complete is a wrong answer with a right answer's shape.
- **Reclamation of superseded entries.** Rides on purge with everything else, and purge needs reader registration, which `txn.md` §9 deliberately does not do. Until then an index grows monotonically with writes.
- **The index-only scan**, gated entirely on a visibility witness (§7). Measured at 10% against PostgreSQL's `Index Only Scan`, so the prize is known. Do not attempt a partial one — the same instruction `txn.md` §8 gives about recovery, and for the same reason.
- **`UNIQUE`** (IX11), and with it whether a unique index probe could ever be **lookup-class** for Waystone — which would be the first amendment to invariant 9's trust table since it was written, and wants the argument in full before the code.
- **Descending, partial and expression indexes**, and multi-column *covering* semantics beyond filtering (§11).
- **Whether the crossover is ever acted on.** Measurement (`bench/results-index.md`) puts an index at an 11% *loss* on a range over 200 rows and a 9.7× win over 10,000. IX9 refuses to see it, because a plan that changes with the data stops `pattern_id` naming a plan. Revisiting means deciding what a *stable* form of that choice would look like — not adding an estimator. **It is not a tuning problem, and that was tested** (§1a): a phase-2 leaf memo removed 95% of the descents at 200 rows and moved the latency **not at all**, then cost **42%** at 10,000 rows where a secondary index's pks are scattered by construction. The 19 µs is the walk's 0.46 µs per row examined against the index's 1.85 µs per row resolved, at 30% selectivity — the ordinary shape of the result, which is why PostgreSQL picks a `Seq Scan` there too.
- **Index maintenance cost as an input to `CABIN AUTO`.** A column with an index should presumably never earn a Cabin; that belongs with the promotion policy in `feat-cabin.md` §8.1, which nothing consumes yet.

**Project**
- C++ standard/toolchain pin, build system, and test framework (propose, don't decide).

When work touches an open decision, stop and ask, or implement behind an interface that keeps every listed option viable.

- `docs/keystoneid-invariant.md` / `docs/keystoneid-k0-findings.md` — the **Keystone id issue-once contract** (K1-K5 decided; milestones `K-M1`-`K-M6`) and what auditing it against the code found. Read the findings before quoting the invariant: **K1 does not hold across a crash today** — the durable log names ids that the unlogged `sys.tables.next_id` has forgotten, so K-M2's bump-ahead allocator cannot close it at any chunk size and sits behind logged catalog writes and recovery. The findings also measure the cost (`bench/results-keystone-alloc.md`): the allocator is ~4.5% of an unlogged INSERT, crash-safe bump-ahead is **1.24×** its cost at N=4096 but **43×** at N=64, and forcing durability per id is **2629×** — so `N` is settled at 4096 by measurement and belongs as a floor rather than a default. Two further findings are other documents' to own: object oids are re-issued on every boot (`kUserOidStart`), which falsifies §1.2's "(oid, pk) is forever-unique" with no crash involved, and the catalog's fixed pages did not chain, so the whole instance held **~62 columns across all user relations** - **fixed 2026-08-06: catalog relations chain now**, each fixed page id being a chain root that links into a reserved range of low page ids, which moves the ceiling to ~7,800 columns and is why a data file no longer refuses the third run of `tools/scenario0_stockmarket.py`. Four amendments landed 2026-08-03: **K3 is now "No density promise"** — it forbids relying on contiguity and states that ordering is provided-but-not-promised, because four subsystems rely on ids being *ordered* and the btree refuses a non-monotonic one outright; §1.2 states an objective rather than a property; §1's "the min_key heap keys off values, not issuance order" is struck as false; and **K-M2a ("make the ceiling durable") is a new milestone**, with K-M2's acceptance criterion no longer claiming a crash property it cannot deliver. Order is now `K-M1 (done) → K-M4 (done) → K-M3 → K-M2a → K-M2 → K-M5`. **K-M4 is built**: `SHOW BUDGET` lists every relation's id consumption with `warning=`/`exhausted=` counts on the summary line, and `DESCRIBE` carries `ids_issued`/`ids_remaining`/`budget_used` beside the `next_id` they derive from. The arithmetic is `catalog::BudgetOf()` (`include/kds/catalog/keystone_budget.hpp`), a pure function of one sequence position so K-M2 changes its *source* and none of its math — and it is the one place that knows **issued counts ids spent, not rows living**, that capacity is one short of 2^40 because id 0 is reserved, and that exhaustion is a flag rather than a rounded 100%. The 90% threshold stays `[PROPOSED]`, named as `kKeystoneBudgetWarnFraction`.
