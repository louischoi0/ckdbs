## 1. What this version delivers, and the numbers that justify it

**Statement shipping, autocommit scope**: a single-statement transaction
arriving on a core that does not own its target relation is executed on the
owner core and answered through the arrival core, instead of refused.

The measured case, one line each:

- **Demand**: an unrouted client has **80–92% of its write statements
  refused** today (pretasks §9b; counters and driver agreeing exactly).
  Every one of those is a statement shipping converts into work.
- **Mechanism**: concentrating commits on one core beats spreading them
  whenever any core carries more than one committing session, by up to
  **1.98×** at load (pretasks §6a); shipping re-concentrates onto owners
  exactly what placement disperses.
- **Budget**: a statement costs 21–23 µs; a sync costs ~0.9 ms (pretasks
  §4). The design budget goes to joining the owner's group commit, not to
  shaving wire bytes.
- **Device**: sync overlap on this volume peaks at four streams and
  declines past it (§3a) — concentration is where the device is fastest,
  which the memo (§5) elevates from tolerable to preferred.

**The build is checked against the memo, not against intuition.**
`docs/inflight/in-progress/memo-shipping-and-group-commit.md` §8 states three claims for exactly
this purpose, and SS-B is structured to mark each right or wrong:

1. shipping is throughput-positive where more than one session targets an
   owner, with margin growing in the session count;
2. shipping is throughput-**negative** at or below one session per owner
   core (R1), where rotation already wins 2.00× and shipping adds only a
   round trip and a waiter;
3. the binding constraint under shipping is the **owner's execution
   capacity**, not its sync rate.

And the reason the build still does not start at the wire: the pretask run
drove the one shipped path that exists today — owner-built `CREATE INDEX`,
the exact shape shipping generalises — and broke the engine twice (§8d).
The memo lists those defects as **preconditions, not predictions**
(falsifier 5). They are this version's opening gates.

## 2. Decisions this order takes (operator-delegated unless marked)

- **D1 — Scope: autocommit, single-relation, one statement.** Read or
  write. A statement inside an explicit transaction targeting a foreign
  core's relation stays refused with the CC3 spelling naming R6; likewise a
  multi-relation statement spanning owners. Nothing touches transaction
  state across cores. Reads are included because pretasks §8c-1 measured
  that a wrong-core session cannot read a foreign relation either (the P4
  pipeline is not reachable from dispatch for a plain statement); shipping
  the whole statement covers both verbs through one mechanism. If the read
  diff grows past reuse, cut reads and record it; do not let them gate
  writes.
- **D2 — The wire shape is 6b's**, generalised: POD request carrying the
  bound statement, parked waiter on the arrival core with a deadline,
  `Status::FromWire` on the reply, the PW6-(2) retryable bit preserved.
  New ring kinds for the DML request/reply pair; no pipeline involvement.
- **D3 — Execution semantics on the owner**: the shipped statement runs
  under the owner's ordinary local implicit transaction, commits through
  the owner's group committer (this is the entire performance thesis, memo
  §3), and advances owner-local state — the per-relation high-water mark
  above all — on the owner, never on the arrival core.
- **D4 — Outcome integrity over retry convenience.** A lost reply after
  execution must not become a silent double-execute. Each shipped statement
  carries a (session, sequence) id; the owner keeps a bounded
  per-arrival-core last-executed record and answers a duplicate with the
  recorded outcome, not a re-execution. Where bounding forces a gap, the
  arrival core surfaces **unknown outcome** as a distinct non-retryable
  status rather than guessing. Engine-issued pks make blind retry a
  double-insert; this is the one place the design must be pessimistic.
- **D5 — Refusals never allocate.** Generalising G2's fix: any check that
  can refuse a shipped statement runs before any allocation on the owner,
  or the refusal path returns what it took. Stated as an invariant, tested
  by the G2 reproduction adapted to DML.
- **D6 — Ship unconditionally; route later.** The memo's claim 2 predicts
  shipping is a small net loss in R1 (≤ 1 session per owner). This version
  still ships unconditionally, because the alternative — a load-aware
  ship-or-refuse decision — is placement policy (`crosscore.md` §9's open
  decision) and does not ride along (rev 1's D7). What changes: **SS-B1
  measures the R1 cell explicitly**, so the cost of unconditional shipping
  is a number the §9 decision inherits, not a surprise. The honest
  "before" in R1 is a refusal, not a slower statement (memo §5), so even a
  small R1 loss converts a failure into work — but it must be priced.
- **D7 — Observability crosses the era boundary explicitly.**
  `cross_core_write_refusals` keeps its exact semantics (post-shipping it
  reads the residue — the 2PC evidence). New fields: `shipped_statements`,
  `shipped_replies`, `shipped_refusals`, `shipped_wait_us_max`, per core,
  absent where no reactor is attached. The §8a scheduler block
  (`polls`/`polled_us`) is the instrument for pricing the waiter
  population shipping creates — the measurement T4 could not fake is the
  one SS-B4 takes for real.

## 5. SS-B — the measurement, structured as the memo's trial

Run on the pretask host or better; **every A/B divided by a null cell**
(pretasks §7a: ~10% ordering bias); named by the tag current at the run.
Each cell states which memo claim or falsifier it judges.

1. **The R1 cell** (memo claim 2, D6's price): one session per owner,
   shipped from a foreign arrival core, against the same session seated on
   the owner. The predicted small loss becomes a number — the input §9's
   routing decision inherits.
2. **The R2 curve** (memo claims 1 and 3): S = 2, 4, 8, 14 sessions on
   foreign arrival cores, all targeting one owner's relation. Prediction:
   throughput tracks T1b's ≈ 590 × S with per-statement latency near two
   syncs, and the ceiling reached is execution, not sync. Compare against
   the same S seated locally (T1b re-run on this tree) — the gap **is** the
   wire + waiter cost at scale.
3. **The tail-page cell** (memo falsifier 3 — new in rev 2): every shipped
   INSERT in cell 2 lands on one btree's ascending tail; commits batch but
   the tail page does not. If the measured curve departs from ≈ 590 × S,
   separate page-level serialization from sync and from wire before naming
   a cause: same S over 1, 2 and 4 relations on the same owner isolates
   the per-page component. This is the cell that says whether the stride
   question returns.
4. **The waiter population, finally priced** (memo falsifier 2, the open
   one): K concurrent shipped statements are K parked waiters per arrival
   core. §8a's `polls`/`polled_us` on the arrival cores at K = 1, 4, 16 —
   the spin signature (polls climbing, polled flat) either appears or it
   does not, and either answer closes pretasks §8c honestly.
5. **The demand conversion.** `refusal_baseline_probe.py` unchanged: the
   80–92% refusal rate must go to ~0 shipped-and-executed for autocommit,
   with `cross_core_write_refusals` flat at zero in the same run — the
   two-era counter reading its second era.
6. **Recovery.** Kill −9 mid-burst on both sides of the wire; restart;
   every relation's count = accepted acks, no shipped statement half-alive,
   the D4 unknown-outcome path exercised once deliberately.
7. **Correctness throughout**: rows in = rows out per relation in every
   cell; a run that loses a row reports a blocking finding and stops.
