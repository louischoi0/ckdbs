## 1. What this version delivers, and the numbers that justify it

**One mechanism, missing at both ends: a core that is asleep is not woken by
the message that has work for it, and a core that holds only parked
coroutines is not allowed to sleep.** SS-B finding 3 calls these "the same
missing wake path seen from opposite ends", and they must be built together —
see D4, which is the reason.

The measured case, one line each:

- **The block is the whole cost of statement shipping.** A shipped
  statement's p50 tracks the owner's idle block over a fivefold range —
  1.08 / 2.10 / 3.11 / 5.12 ms at `wal_drain_interval_us`
  1000/2000/3000/5000, throughput the exact reciprocal, seated control flat
  at 23 µs (SS-B §4a, **measured**). The shipped-minus-seated delta is a flat
  **1,064 µs under `group` and 1,068 µs under `relaxed`** — the same constant
  with the device in the path and without it.
- **Nothing wakes the sleeper.** `Scheduler::RunOnce` blocks in
  `io_backend_.PollReady(IdleTimeoutMs(), …)`
  (`src/sched/scheduler.cpp:319` → `src/sched/epoll_io_backend.cpp:88`'s
  `epoll_wait`), and a ring message touches no fd in that epoll set: the ring
  is discovered only by `Scheduler::DrainInbox()`
  (`src/sched/scheduler.cpp:62`, called at `:353`), *after* the block
  returns. `grep -rn "eventfd\|EFD_\|Wake"` over `src/` and `include/` finds
  no mechanism (**source-read** at `bce12d0`, re-run on this tree).
- **One millisecond is the floor, and it is an artifact.** `IdleTimeoutMs`
  is an `int` of milliseconds and rounds *up* —
  `(deadline - now + 999'999) / 1'000'000` at
  `src/sched/scheduler.cpp:196-214` — so a timer 50 µs away yields a 1 ms
  block. That is why SS-B's first four sweep rows are identical and read as
  a failed experiment.
- **A single parked waiter costs a whole core.** At K = 1 the arrival core
  is **89% busy** asking a predicate 3.1M times a second whether a reply has
  arrived; K = 16 takes it to 93% while the cost per poll holds at
  0.059–0.068 µs (SS-B §7, **measured**). The mechanism is `IdleTimeoutMs`'s
  first line — `if (HasReadyTask()) return 0;`
  (`src/sched/scheduler.cpp:196-199`) — and a parked coroutine sits in a
  ready queue answering `kSuspended` forever (`RunReadyTasks`' re-push at
  `src/sched/scheduler.cpp:283`, `include/kds/sched/coro.hpp:425`'s
  `WaitUntil`). In SS-B's `b2-s14` shipped arm two arrival cores sat at
  **0.921 and 0.921** busy against **0.058 and 0.051** seated: two entire
  CPUs converted into spin.
- **The spec already specifies the fix and it was never built.**
  `docs/spec/sched.md` §7's blocking mode is *"arm eventfd/ring wakeups and
  block until an event"*. This version is that bullet, not a new idea; §7
  today describes a mode the code does not have.

**Three claims, stated so RW-B can mark each right or wrong** (SS-B's own
form, and the reason its verdicts are trustworthy):

1. **The R1 penalty is the block.** Removing it takes shipping's corrected
   ratio at one session per owner from **0.526 / 0.429 / 0.531** (SS-B B1,
   B4 K = 1, B6) to **≥ 0.90**, and the shipped p50 stops depending on
   `wal_drain_interval_us` altogether. Falsifier: the p50 still tracks the
   knob → the wake is not on the path and the diagnosis was wrong.
2. **The wake costs nothing at load.** Cells already at 0.93–0.99×
   (SS-B §5's curve, B4 at K = 4/16) do not regress, and single-core
   throughput does not move at all. Falsifier: a per-send syscall on the hot
   path shows up as a loss anywhere the target was never asleep — which is
   what D3 exists to prevent and what this cell is the check on.
3. **The arrival core's 89% is the ready-queue misclassification alone.**
   With parked tasks excluded from `HasReadyTask()`, K = 1 arrival CPU falls
   below **0.10** at unchanged throughput. Falsifier: it does not — then
   something else in the shipped path is spinning, and this order has found a
   second defect, which is reported rather than absorbed.

**What this is not**: shipping's problem. Any cross-core message to an idle
core pays the block today; shipping is simply the first feature to put one on
a client's critical path twice per statement. The fix therefore lands in the
scheduler and is priced on shipping's cells because those are the ones that
can see it.

## 2. Decisions this order takes (operator-delegated unless marked)

- **D1 — Scope: the wake path and the park classification. Nothing else in
  the reactor.** No busy-poll mode (`sched.md` §7's first bullet stays
  unbuilt), no loop-budget retuning, no change to the PW7 floors, no
  hierarchical timing wheel (§6's min-heap stays, with `SubmitAt`'s comment
  intact), no group-accounting policy change. §4's charging question is
  *instrumented* by D7 and **not decided here**.
- **D2 — The wake is an injected seam, never a syscall in engine logic.**
  `sched.md` invariant 8 forbids direct syscalls outside injected
  interfaces, and §8 requires a failure to reproduce from `(seed, build)`
  alone. So the wake is a method on the **`IoBackend`** seam
  (`include/kds/sched/io_backend.hpp`), implemented by `EpollIoBackend` with
  its own eventfd registered in its own epoll set, by `NullIoBackend` as a
  no-op, and by the simulation backend as an event on the injected clock. A
  `write(2)` reached from `RealRingTransport::TrySend`
  (`src/sched/ring_transport.cpp:26`) directly would violate both.
- **D3 — Wake only a core that is actually asleep.** A per-core
  `std::atomic<bool>` published immediately before the block and cleared
  immediately after; the sender pushes to the ring, then tests the flag, and
  issues the wake only if it reads *sleeping*. Two consequences, both
  binding: the sleeper must **re-check its inboxes after publishing the flag
  and before blocking** (the classic double-check; without it the message
  that arrived in the window is missed), and the flag's ordering must be
  written down as an ordering argument in the file, per the "document the
  lock/atomic protocol at the top of each subsystem file" rule — not left to
  be re-derived. Cost model: an unconditional wake is a syscall per send on
  the hot path, which is exactly the regression claim 2 tests for.
- **D4 — The block always has a ceiling. `PollReady(-1)` is forbidden.**
  This is the decision the two halves depend on each other for. Today a
  missed wake costs **one millisecond**, because the spin and the 10 ms
  `max_idle_block_ms` backstop both paper over it; after D5 a missed wake
  would cost **forever**. The ceiling keeps a lost wake a bounded latency
  bug — `max_idle_block_ms` = 10
  (`include/kds/sched/scheduler.hpp:79`) — instead of a hang, and it is what
  makes this version safe to land before every park in the engine has been
  audited for a wake source. Stated as an invariant in `sched.md` §7 and
  tested.
- **D5 — Parked is not ready, and "parked" means the last full iteration
  changed nothing.** `IdleTimeoutMs` must stop treating a suspended
  coroutine as runnable, but "no `kDone` this round" is *not* a safe
  predicate on its own, and the counterexample is the commit path: the group
  committer is a **post-task hook** run once per iteration
  (`src/server/expeditor.cpp:1723`), and a committing statement parks on
  `durable_lsn` waiting for exactly that hook. A rule that blocks while a
  just-staged commit is parked adds the drain interval to **every commit** —
  turning a 1 ms shipping penalty into a 1 ms durability penalty, which
  would be a worse engine. So the permission to block requires a full
  iteration in which nothing happened: no I/O event, no timer fired, no
  message drained, no task completed, no task submitted, **and the post-task
  hook did no work**. The last clause needs the hook to say so —
  `SetPostTaskHook`'s `std::function<void()>`
  (`include/kds/sched/scheduler.hpp:240`) becoming a `bool` return is the
  recommended shape, and `WalManager::DrainOnce` already knows whether
  anything was staged. If the build finds a cheaper predicate that provably
  covers the commit case, take it and say why in the review.
- **D6 — Sub-millisecond blocks are conditional on measurement, not built up
  front.** `epoll_pwait2` (timespec, Linux ≥ 5.11) or a timerfd would remove
  the 1 ms rounding floor. After D2/D3 a ring message no longer waits for a
  timer at all, so the floor may cease to matter; building it first would be
  fixing a premise the fix itself removes. RW6 opens **only if RW-B cell 2
  shows a residual that the rounding explains** — the measure-the-premise
  rule applied to this order's own tail.
- **D7 — The idle block becomes accountable.** New `SHOW META` fields beside
  T4's existing block: `sched_idle_blocks`, `sched_idle_block_us`,
  `sched_wakes_sent`, `sched_wakes_received`, `sched_spurious_wakes`. This
  does not decide `sched.md` §4's charging question; it makes
  `sched_wall_us − Σ sched_*_polled_us − sched_idle_block_us` the real
  remainder, so the 92–96%-charged-to-nobody figure (SS-B claim 3) can be
  read as sleep versus work rather than as one lump.
- **`[OPERATOR]` — the idle-policy mode of `sched.md` §7.** §7 says the mode
  is a per-reactor runtime option and *"code must not assume either mode"*;
  the engine has only ever had the blocking half, and this order builds the
  blocking half properly. Whether busy-poll ships as a deployment option —
  and whether an appliance default flips to it — is not CLA's to pick and is
  not attempted.

## 5. RW-B — the measurement

`build-release`; every A/B divided by a **null cell** (the pretask harness's
~10% ordering bias, SS-B finding 10 — a per-arm process removes it, so use
the SS-B drivers, not `tools/multicore_benchmark.py`); each cell named by
`git describe --tags` at the run; results in `bench/v2.3.0/` with the raw
driver output archived beside it. Each cell states which §1 claim it judges.

1. **The R1 cell** (claim 1). `bench/single_relation_probe.py`, one session
   per owner, shipped from a foreign arrival core against seated. Today
   0.526 (B1) / 0.429 (B4 K = 1) / 0.531 (B6). Target ≥ 0.90, and the
   shipped p50 falls from ~1,085 µs toward the seated 23 µs plus the wire.
   **This is the number `crosscore.md` §9's routing decision inherits** —
   the shipping order's D6 priced unconditional shipping at a 2× penalty in
   the R1 regime, and this cell is what re-prices it.
2. **The knob sweep** (claim 1's falsifier, and RW6's gate).
   `wal_drain_interval_us` 1000 / 2000 / 3000 / 5000, both arms at every
   point. **The shipped p50 must become independent of the knob.** If it
   still tracks it, the wake is not on the path — report that and stop. If
   it is independent but a flat residual remains, measure the residual
   against the 1 ms rounding floor: that residual, and only that, opens RW6.
3. **The waiter population** (claim 3). `bench/parked_coroutine_probe.py`
   and `bench/idle_cpu_probe.py` at K = 1, 4, 16 on one arrival core.
   Arrival CPU 0.893 / 0.925 / 0.929 → target < 0.10 at K = 1 with
   throughput unchanged; polls/s down an order of magnitude while
   `polled_us` holds (the spin signature read backwards). `idle_cpu_probe`'s
   three windows also say what an idle *instance* costs after RW3 — today a
   peer with nothing to do still wakes ~100×/s on the 10 ms backstop.
4. **The hot-path cost of the wake** (claim 2). The cells that must not
   move: `cores = 1` single-core throughput (D3's flag is what keeps the
   syscall off it); B4 at K = 4 and 16 (0.951, 0.976); SS-B §5's R2 curve
   (521–547 × S). A loss here is D3's gate failing and is reported with its
   number, never absorbed.
5. **The commit path** (D5's hazard, the one that would be a worse engine).
   PW6's four-writer cell (1.030×, longest refill wait 3.0–3.3 ms) and the
   point-SELECT-beside-a-committing-session cell (1,088/1,083 µs against
   37/35 alone). Neither may regress at any drain interval. If the wake
   *improves* the second one — plausible, since it is the same class of
   missing wake — say so with the number rather than leaving it as a happy
   accident.
6. **Correctness.** The full suite green (the step gate, unsuspended);
   `scripts/sim.sh` 95 cells green with RW4's new case; rows in = rows out
   in every throughput cell. **A hang is a blocking finding and stops the
   chain** — this version's failure mode is not a slow statement, it is a
   statement that never answers.

An unrun cell is reported as unrun. A cell this host cannot build — SS-B's
harness could not saturate an owner, and that ceiling has not moved — says so
and names what it would take.

## 6. Interactions

- **`docs/spec/crosscore.md` §9's routing decision** is waiting on cell 1's
  number; SS-B handed it a 2× R1 penalty and this order may hand it back a
  ~1.0. Nothing here decides the routing policy itself.

- **PW7's two floors** are load-bearing under `sched.md` §4 and are not
  reopened. D5 changes when the reactor blocks, not how it picks; a review
  that finds the floors and the quiescence rule interacting reports it
  rather than adjusting either quietly.
- **File contention**: RW1–RW3 sit in `src/sched/` and `include/kds/sched/`,
  which no other in-progress workplan is writing to at `bce12d0`. If one
  appears, this order's row lands first — the wake seam is a dependency of
  anything cross-core.
